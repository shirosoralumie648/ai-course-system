## 上节课回顾

第 14 周我们把产品的一条核心路径迁移到 PWA、小程序或移动端。那一周强调平台选择、路径压缩、失败状态和验证证据。它解决的问题是：你的产品能不能在另一个平台上保持清晰边界。

第 15 周要解决另一个问题：当期末项目已经进入最后修复和交付阶段，AI 到底应该怎么参与？

很多团队到这个阶段会出现三种极端：

1. 完全不用 AI，靠人工赶工，最后没有自动化验证。
2. 把所有问题丢给 AI，导致 AI 修改范围失控。
3. 开很多 Agent 并行写代码，最后不知道谁改了什么。

这三种都不可靠。本周的目标是给 AI 工程建立一套可执行的规则：谁能做什么，哪些地方必须人工确认，工具有哪些权限，失败如何记录，结果如何验证。

本周不是让学生炫耀 Agent，而是让学生证明自己能管理 Agent。

## 1. 小哲的最后一周事故

小哲的 AI 校园活动助手已经有了 Web 版、小程序最小版本和后端 API。期末前一周，他想让 AI 帮他做最后优化。他打开聊天工具，输入：

> 帮我把项目优化一下，把 AI 推荐做得更稳定，顺便修一下报名和部署问题。

AI 很快开始工作。它做了很多看起来合理的事情：

- 修改了推荐 Prompt。
- 调整了报名接口。
- 改了数据库字段。
- 添加了一个缓存逻辑。
- 删除了一个失败测试。
- 改了 `.env.example`。
- 升级了依赖。
- 修改了部署配置。

结果项目坏了：本地能跑，线上报名失败；测试少了一条；数据库旧数据读不出来；小程序接口返回 403；AI 推荐成功率没有证据。

小哲的问题不是 AI 不够强，而是任务没有边界。他没有告诉 AI：

- 哪些文件允许修改。
- 哪些文件不能碰。
- 哪些操作需要人工审批。
- 什么叫"更稳定"。
- 改完要跑哪些验证。
- 失败测试不能删除。
- 数据库和生产配置属于高风险区域。

这就是本周要解决的问题。

## 2. 从"让 AI 帮我做"到"让 AI 在规则内做"

Rules、Skills、MCP 和 Agent Team 不是四个互相独立的概念。它们可以组合成一个期末项目的交付控制系统。

| 概念 | 解决什么问题 | 本周产出 |
|---|---|---|
| Rules | AI 应该遵守什么项目规则 | `AGENTS.md` 或等价规则文件 |
| Skills | 常见任务如何按固定流程执行 | 任务流程卡，例如 debug、review、deploy |
| MCP | AI 能使用哪些外部工具和资源 | MCP 工具权限表 |
| Agent Team | 多角色如何分工和交接 | Planner/Coder/Tester/Reviewer 角色表 |
| Human Gate | 哪些地方必须人类确认 | 审批点清单 |
| Trace | AI 实际做了什么 | 一次执行记录 |

如果只写"使用 Agent Team"，没有 Rules 和 Human Gate，Agent Team 只是分工口号。如果只接很多 MCP 工具，没有权限表，MCP 会变成风险来源。如果只写规则但没有 trace，教师无法判断规则是否真的执行。

本周要求这几件事连起来。

### 3.1 读 spec-kit：不是先写代码，而是先写约束

spec-kit 的核心启发是：AI 编程不能只靠聊天上下文。项目需要 constitution、spec、plan、tasks 和 checklist。

课堂里不要求完整复刻 spec-kit，但可以借鉴这个顺序：

```text
项目规则 -> 本次任务规格 -> 小步计划 -> 执行任务 -> 检查清单 -> 实现记录
```

对期末项目来说，最小版本可以是：

- `AGENTS.md`：项目规则。
- `FINAL-FIX-SPEC.md`：最后一周只修哪些问题。
- `FINAL-FIX-PLAN.md`：允许修改哪些文件。
- `TRACE.md`：执行记录。
- `REVIEW.md`：人工复核结果。

这比"我让 AI 帮我改了"可信得多。

### 3.2 读 mcp-servers：工具必须有边界

MCP server 的关键不是"工具越多越好"，而是每个工具都有明确输入、输出和权限。

例如 filesystem 工具看起来只是读写文件，但风险很大：

- 可能读到 `.env`。
- 可能覆盖用户未提交改动。
- 可能改错目录。
- 可能删除项目文件。

所以课堂里的 MCP 工具卡必须写清：

| 字段 | 说明 |
|---|---|
| 工具名 | 例如 filesystem、git、fetch、database |
| 可以做什么 | 明确允许操作 |
| 禁止做什么 | 明确红线 |
| 输入 | 需要哪些参数 |
| 输出 | 返回什么 |
| 失败模式 | 常见失败和处理 |
| Human Gate | 什么时候必须人工确认 |

### 3.3 读 openai-agents-python：guardrail、handoff、trace

Agent 框架里常见的三个概念非常适合课堂：

- guardrail：防止 Agent 做危险或越界的事。
- handoff：一个角色把任务交给另一个角色时，必须说明上下文和边界。
- trace：记录 Agent 的计划、工具调用、改动和验证结果。

学生不需要实现完整 Agent 框架，但必须能在项目文档中体现这三个概念。

## 4. AGENTS.md：项目级规则文件

`AGENTS.md` 是本周最重要的产物之一。它不是写给人看的口号，而是写给 AI 和团队成员看的操作协议。

### 4.1 最小合格结构

```markdown
# AGENTS.md

## 项目目标
- 本项目是：一句话说明产品、用户、核心路径。
- 本周交付边界：只允许围绕期末验收修复和补证据，不做新大功能。

## 当前高风险区域
- 认证：
- 支付：
- 数据库/RLS：
- AI API Key：
- 文件上传：
- 部署配置：

## 允许 AI 做的事
- 修改指定目录内的前端页面、API route、测试和文档。
- 生成小步计划，列出将修改的文件。
- 运行本地测试、构建、lint，并保存命令输出。
- 总结失败原因和下一步建议。

## 必须人工审批的事
- 删除文件、大规模重构、安装依赖、修改 lockfile。
- 修改认证、支付、RLS、webhook、生产环境变量。
- 读取或处理 API Key、Token、密码、真实用户数据。
- 跳过测试、删除失败用例、把失败测试标记为通过。
- push、deploy、数据库迁移、生产操作。

## 验证要求
- 每次实现后记录：命令、结果、失败原因或通过证据。
- 最终答辩前必须有：运行截图、测试日志、AI 调用/RAG eval 证据、人工 review 记录。

## 输出格式
- 每次修改前列出计划和文件范围。
- 每次修改后列出实际改动、验证命令和剩余风险。
```

### 4.2 不合格规则

这些规则不合格：

- 注意代码质量。
- 不要出错。
- 保证安全。
- 多测试一下。
- 尽量别改太多。

原因是它们不能执行，也不能审计。

### 4.3 合格规则

合格规则必须具体：

| 不合格 | 合格 |
|---|---|
| 注意安全 | 不允许读取 `.env`、API Key、数据库导出文件 |
| 多测试 | 修改 API 后必须运行 `npm test -- api` 和一次 curl |
| 不要乱改 | 未经审批不得修改 `schema.sql`、`supabase/migrations/*`、`package-lock.json` |
| 优化 AI | 只能修改 `app/api/recommend/route.ts` 的错误处理，不改模型供应商 |
| 完成后总结 | 必须记录命令、输出、失败或成功证据 |

## 5. Human Gate：人工审批点

Human Gate 是本周第二个关键概念。它不是"人类最后看一眼"，而是在危险操作发生前停下来。

### 5.1 Gate 分级

| 等级 | 示例 | 是否必须审批 |
|---|---|---|
| G0 低风险 | 修改文案、补 README、增加展示截图 | 可自动执行 |
| G1 中风险 | 修改普通页面、增加非关键测试、调整样式 | 执行前列计划，执行后验证 |
| G2 高风险 | 修改 API、数据库查询、认证状态、文件上传 | 必须人工审批 |
| G3 禁止自动执行 | 删除数据、操作生产库、暴露密钥、真实扣费、强制 reset | 禁止，除非课堂教师明确授权 |

### 5.2 项目 Human Gate 清单

```markdown
## Human Gate 清单

### 必须先问再做
- 安装新依赖。
- 修改 lockfile。
- 修改数据库 schema 或迁移。
- 修改认证、支付、RLS、webhook。
- 删除文件或重命名目录。
- push、deploy、发布小程序或 App。

### 必须停止并报告
- 发现 API Key、Token、密码或真实用户数据。
- 测试失败但任务要求继续。
- 修改范围超过计划文件数。
- AI 建议删除失败测试。
- 工具返回权限错误或路径异常。
```

### 5.3 审批记录格式

审批不能只在口头里发生。至少要记录：

```markdown
## Human Gate Record

- 时间：
- 操作：
- 风险等级：
- 申请原因：
- 允许修改文件：
- 禁止事项：
- 审批人：
- 结论：允许 / 拒绝 / 修改后允许
```

期末答辩时，这份记录能证明团队知道哪些地方危险。

## 6. Skills：把常见任务变成流程卡

Skill 可以理解为"某类任务的固定操作流程"。课堂里不要求实现真实插件，但要求学生能写出任务流程卡。

### 6.1 Debug Skill

```markdown
## Skill: debug-api-error

### 适用场景
API 返回 4xx/5xx 或前端显示空结果。

### 步骤
1. 记录用户操作和请求路径。
2. 查看浏览器 Network：URL、method、status、response。
3. 查看后端日志：requestId、错误消息、堆栈。
4. 区分是前端参数、认证、数据库、AI 服务还是部署问题。
5. 只修改定位到的文件。
6. 运行最小验证命令。
7. 写入 trace。

### 禁止事项
- 不能直接删除错误处理。
- 不能跳过认证。
- 不能把失败状态隐藏成成功。
```

### 6.2 Review Skill

```markdown
## Skill: review-final-diff

### 适用场景
期末提交前检查最后一次 diff。

### 步骤
1. 查看 `git diff --stat`。
2. 列出高风险文件。
3. 检查是否包含密钥、真实用户数据、无关重构。
4. 检查测试和构建证据。
5. 记录必须修复和可接受风险。

### 输出
- Blocking issues：
- Non-blocking risks：
- Verified commands：
- Final recommendation：
```

### 6.3 Deploy Skill

```markdown
## Skill: deploy-preview

### 适用场景
部署预览或正式站点前。

### 步骤
1. 确认当前分支和未提交改动。
2. 运行构建命令。
3. 检查环境变量占位。
4. 部署到 preview。
5. 用真实 URL 验证核心路径。
6. 记录部署链接和回滚方式。

### Human Gate
- 正式生产部署前必须人工确认。
```

这些 Skill 不一定被工具自动调用，但它们能让团队在最后一周不靠临场发挥。

## 7. MCP 工具权限表

MCP 的教学重点不是"连上越多工具越好"，而是每个工具都要有输入、输出、权限和失败处理。

### 7.1 最小工具表

| 工具 | 可以做什么 | 禁止做什么 | 失败模式 | Human Gate |
|---|---|---|---|---|
| filesystem | 读取/修改指定项目目录 | 读取家目录、系统目录、`.env`、密钥文件 | 改错文件、覆盖用户修改 | 写入前列文件清单 |
| git | 查看 diff、status、log | 强制 reset、删除历史、覆盖分支 | 混入无关改动 | revert/reset 必须审批 |
| fetch | 访问公开文档或测试接口 | 请求内部系统、带密钥请求第三方 | 网络失败、返回不稳定 | 涉及真实用户或账单需审批 |
| database | 读取测试库、执行迁移草案 | 操作生产库、导出隐私数据 | RLS 绕过、误删数据 | 写操作必须审批 |
| payment | 读取测试模式状态 | 触发真实扣费、改生产 webhook | 金额错误、状态不同步 | 必须使用测试模式并保留日志 |

### 7.2 工具卡模板

```markdown
## MCP Tool Card

- 工具名：
- 用途：
- 输入：
- 输出：
- 允许范围：
- 禁止范围：
- 失败模式：
- Human Gate：
- 本项目是否实际使用：
- 证据：
```

### 7.3 文件系统工具示例

```markdown
## MCP Tool Card: filesystem

- 用途：读取和修改项目源码。
- 输入：项目根目录内的文件路径。
- 输出：文件内容、diff 或写入结果。
- 允许范围：`src/`、`app/`、`components/`、`tests/`、`docs/`。
- 禁止范围：`.env`、`.ssh/`、家目录、系统目录、数据库导出。
- 失败模式：路径错误、权限不足、覆盖未提交改动。
- Human Gate：删除、移动、大范围格式化前必须审批。
- 证据：每次写入后记录 `git diff --stat`。
```

### 7.4 Git 工具示例

```markdown
## MCP Tool Card: git

- 用途：查看状态、diff、提交历史。
- 输入：仓库路径和 git 命令。
- 输出：status、diff、log。
- 允许范围：`git status`、`git diff`、`git log`、`git show`。
- 禁止范围：`git reset --hard`、`git clean -fd`、强制 push。
- 失败模式：混入无关改动、分支不对、未拉取最新代码。
- Human Gate：commit、push、revert、reset 前必须人工确认。
- 证据：提交前后记录 commit hash。
```

## 8. Agent Team 最小设计

Agent Team 不一定是四个真实 AI 进程。它可以是一套角色化工作流程。一个人也可以按四个角色做事。

### 8.1 四角色模型

| 角色 | 输入 | 输出 | 不能做什么 | Human Gate |
|---|---|---|---|---|
| Planner | 需求、当前代码状态、限制 | 小步计划和验收标准 | 不能直接改代码 | 计划超过 6 个文件时需审批 |
| Coder | 已审批计划、允许修改范围 | diff 和实现说明 | 不能改密钥、账单、生产配置 | 碰认证/支付/权限立即停止 |
| Tester | 测试命令、验收标准 | 测试日志和失败分析 | 不能把失败测试改成通过 | 测试失败但仍想交付时需审批 |
| Reviewer | diff、测试日志、需求 | 风险清单和是否通过建议 | 不能代替人类最终批准 | 高风险问题必须人工判定 |

### 8.2 角色交接格式

```markdown
## Handoff

- From：
- To：
- 任务：
- 已知上下文：
- 允许文件：
- 禁止文件：
- 验证命令：
- 未解决风险：
- Human Gate：
```

没有 handoff 的 Agent Team 容易变成多人抢同一个文件。

### 8.3 单人团队如何使用

如果项目只有一个学生，可以这样模拟：

1. Planner：先写计划，不改代码。
2. Coder：按计划改，不扩大范围。
3. Tester：只看验证，不美化结果。
4. Reviewer：看 diff 和风险，决定是否交付。

这比"我自己看过了"更可复盘。

## 9. 一次合格的执行 trace

trace 不是聊天截图，而是能审计的工作记录。

### 9.1 trace 必须回答的问题

1. AI 被要求做什么？
2. AI 被允许改哪些文件？
3. AI 禁止做什么？
4. 人类在哪里审批？
5. 实际改了什么？
6. 跑了什么验证？
7. 结果是否通过？
8. 剩余风险是什么？

### 9.2 trace 模板

```markdown
## Week 15 Agent Trace

### 1. 任务
- 目标：
- 背景：
- 允许文件：
- 禁止事项：
- 验收标准：

### 2. Agent 计划
- Step 1：
- Step 2：
- Step 3：
- Step 4：

### 3. Human Gate
- 风险等级：
- 审批人：
- 审批结论：
- 补充限制：

### 4. 执行结果
- 修改文件：
- 关键 diff：
- 测试命令：
- 测试结果：
- 部署或运行证据：

### 5. Review
- Blocking issues：
- Non-blocking risks：
- 是否需要二次修复：
- 最终结论：
```

### 9.3 合格 trace 示例

```markdown
## Week 15 Agent Trace

### 1. 任务
- 目标：修复 AI 推荐页在接口 500 时没有错误提示的问题。
- 背景：期末 Demo 中如果模型供应商失败，页面会一直 loading。
- 允许文件：`app/recommend/page.tsx`、`app/api/recommend/route.ts`、`tests/recommend-error.spec.ts`
- 禁止事项：不改模型供应商，不改数据库 schema，不安装依赖。
- 验收标准：
  1. API 返回 500 时前端显示错误消息。
  2. 用户可以重新提交。
  3. 测试覆盖失败返回。

### 2. Agent 计划
- Step 1：阅读推荐页和 API route。
- Step 2：补 API 错误响应结构。
- Step 3：补前端错误状态。
- Step 4：新增失败测试并运行。

### 3. Human Gate
- 风险等级：G1。
- 审批人：项目负责人。
- 审批结论：允许修改上述三个文件。
- 补充限制：不要改 Prompt 和模型参数。

### 4. 执行结果
- 修改文件：3 个。
- 关键 diff：新增 `errorMessage` 状态和 API 500 JSON。
- 测试命令：`npm test -- recommend-error`。
- 测试结果：通过。
- 部署或运行证据：本地截图 `evidence/recommend-500.png`。

### 5. Review
- Blocking issues：无。
- Non-blocking risks：尚未区分供应商超时和额度不足。
- 是否需要二次修复：不需要，本周答辩可接受。
- 最终结论：通过。
```

这个 trace 能被教师追问，也能被队友复盘。

## 10. 课堂练习：把模糊请求改成可执行任务

原始请求：

> 帮我把项目优化一下，顺便让 AI 功能更稳定。

课堂改写：

```markdown
目标：修复 AI 问答页在接口失败时没有错误提示的问题。
允许范围：`app/api/chat/route.ts`、`app/chat/page.tsx`、`tests/chat-error.spec.ts`
验收标准：
1. API 返回 500 时，前端显示可理解的错误消息。
2. 用户可以重新提交。
3. 测试覆盖失败返回。
4. 不修改模型供应商、数据库 schema、支付或认证。
Human Gate：如果需要新增依赖或修改 env，先停止并询问。
```

### 10.1 分组练习

每组拿自己的期末项目写三个任务：

1. 一个低风险任务：文案、空状态、README。
2. 一个中风险任务：页面逻辑、普通 API、测试。
3. 一个高风险任务：认证、支付、数据库、AI Key 或部署。

然后为每个任务写：

- 允许文件。
- 禁止文件。
- 验收标准。
- Human Gate。
- 验证命令。

### 10.2 教师点评标准

教师重点看：

- 范围是否小。
- 验收是否可测。
- 风险是否分级。
- 是否出现"优化一下"、"完善一下"、"提高质量"这种空话。
- 是否明确禁止危险操作。

## 11. 高风险模块的特别规则

最后一周最容易出事故的模块包括认证、支付、权限、数据库、文件上传、AI API、部署。

### 11.1 认证

认证相关变更必须回答：

- 登录态从哪里来？
- 前端是否能伪造用户身份？
- 后端是否重新校验？
- 退出登录后缓存是否清理？
- 双用户测试是否通过？

禁止：

- 为了 Demo 暂时绕过登录。
- 前端传 `userId` 后端直接相信。
- 把管理员权限写死在客户端。

### 11.2 支付

支付相关变更必须回答：

- 是否使用测试模式？
- 金额单位是否明确？
- webhook 是否幂等？
- 支付成功后谁更新订单状态？
- 失败和取消状态如何展示？

禁止：

- 真实扣费。
- 在前端保存支付密钥。
- 手动把订单改成 paid 当作完成。

### 11.3 数据库和 RLS

数据库相关变更必须回答：

- 修改了哪些表？
- 是否有迁移文件？
- 是否影响旧数据？
- RLS 或权限边界是什么？
- 是否有双用户访问测试？

禁止：

- 期末前大改 schema。
- 删除旧数据。
- 用 service role 绕过所有权限当作产品功能。

### 11.4 AI API

AI 调用相关变更必须回答：

- 模型供应商和模型名是什么？
- API Key 在哪里？
- 超时、失败、额度不足如何处理？
- 是否记录成本或用量？
- Prompt 修改前后是否有样本对比？

禁止：

- 客户端直连模型供应商并暴露 Key。
- 把一次成功截图当作稳定性证据。
- 删除失败样本。

### 11.5 部署

部署相关变更必须回答：

- 部署平台是什么？
- 环境变量是否配置？
- 构建命令是什么？
- 部署 URL 是否可访问？
- 回滚方式是什么？

禁止：

- 未构建就部署。
- 把本地能跑当作线上可用。
- 忽略部署日志里的错误。

## 12. 测试和证据要求

Agent 工程的重点不是"AI 说完成了"，而是证据。

### 12.1 命令证据

每次任务至少记录一个命令：

| 任务类型 | 推荐命令 |
|---|---|
| 前端页面 | `npm run build` 或页面测试 |
| API 修复 | 单元测试 + curl |
| RAG 调整 | eval 脚本或问题集 |
| 支付/认证 | 测试模式日志 + 双用户测试 |
| 部署 | 部署日志 + 线上 URL curl |

### 12.2 截图证据

截图不是为了好看，而是证明状态：

- 成功状态。
- 失败状态。
- 空状态。
- 权限不足状态。
- 部署链接可打开。
- 小程序/移动端/ PWA 运行证据。

### 12.3 Diff 证据

最终答辩前，学生应该能展示：

```bash
git diff --stat
git log --oneline -5
```

如果项目使用 GitHub，也可以展示 PR 或 commit。关键是能说明最后一周改了什么。

## 15. 常见失败案例

### 15.1 失败：规则文件写得像宣言

表现：

- "AI 应保证质量。"
- "注意安全。"
- "认真测试。"

纠偏：

改成具体文件、命令和禁止事项。

### 15.2 失败：Agent Team 角色重叠

表现：

- Planner 也改代码。
- Tester 也修实现。
- Reviewer 只写"不错"。

纠偏：

明确每个角色的输入、输出和不能做什么。

### 15.3 失败：MCP 工具没有权限边界

表现：

- 工具可以读写整个电脑。
- 没有禁止 `.env`。
- 没有写失败模式。

纠偏：

工具卡必须列出允许范围、禁止范围和 Human Gate。

### 15.4 失败：trace 只有聊天截图

表现：

- 截图很多。
- 没有文件列表、命令、测试结果。

纠偏：

trace 必须能审计：任务、范围、审批、diff、验证、风险。

### 15.5 失败：为了赶进度跳过测试

表现：

- AI 说测试应该通过。
- 学生没有命令输出。

纠偏：

没有验证命令，就不能声称修复完成。

1. `AGENTS.md` 或等价规则文件。
2. Agent Team 角色表。
3. Human Gate 清单。
4. MCP 工具卡：至少 2 个工具，写清输入、输出、权限、失败模式。
5. 一次执行 trace：计划、diff、测试日志、人工审批记录。
6. 一条真实验证证据：测试命令、构建命令、线上 URL 或截图。

## 17. 验收标准

| 维度 | 满分表现 | 常见扣分 |
|---|---|---|
| Rules | 具体到文件、命令、禁止事项 | 只有原则口号 |
| Human Gate | 覆盖认证、支付、数据库、部署、密钥 | 只写"重要操作先问" |
| Agent Team | 角色少而清晰，输入输出明确 | 角色重叠、没有交接 |
| MCP 工具卡 | 有输入、输出、权限、失败模式 | 只列工具名 |
| trace | 能审计任务、范围、审批、diff、验证 | 只有聊天截图 |
| 验证证据 | 有命令和结果 | 只有"AI 说完成" |
| 安全边界 | 不接触真实密钥、账单、生产数据 | 为了 Demo 绕过权限 |

## 19. 教师课堂流程：从规则到 trace

这一节给教师组织课堂使用。Week 15 很容易讲成概念课，所以课堂必须让学生现场产出文档。

### 19.1 0-10 分钟：展示事故案例

教师先展示一个失控请求：

```text
帮我优化项目，让 AI 功能更稳定，顺便修一下登录和部署。
```

让学生判断 AI 可能会做什么危险操作。学生通常能说出：

- 改很多文件。
- 碰认证。
- 改数据库。
- 改部署。
- 删除测试。

然后教师把问题归纳成一句话：

> 任务没有边界，工具没有权限，结果没有证据。

### 19.2 10-25 分钟：写 AGENTS.md

每组打开自己的期末项目，现场写 `AGENTS.md` 的四个部分：

1. 项目目标。
2. 允许 AI 做的事。
3. 必须人工审批的事。
4. 验证要求。

教师巡视时重点看：

- 是否写了具体目录。
- 是否列了高风险模块。
- 是否禁止了密钥和生产数据。
- 是否写了测试命令。

### 19.3 25-40 分钟：设计 Human Gate

每组把最后一周可能做的任务分级：

| 任务 | 风险等级 | 是否审批 | 允许文件 |
|---|---|---|---|
| 修改按钮文案 | G0 | 否 | 页面文件 |
| 增加错误状态 | G1 | 执行前列计划 | 页面和测试 |
| 修改推荐 API | G2 | 是 | API route |
| 改数据库 schema | G2/G3 | 是 | migration |
| 部署生产 | G3 | 是 | workflow / 平台 |

这个表会让学生意识到：不是所有 AI 操作都同等风险。

### 19.4 40-60 分钟：写一次 trace

每组选一个真实小任务，例如：

- 补 README 运行说明。
- 修复空状态。
- 给 AI 接口加失败提示。
- 补一条 RAG eval。

要求按 trace 模板写，不一定真的改完代码，但必须写清：

- 目标。
- 允许文件。
- 禁止事项。
- 人工审批。
- 验证命令。

### 19.5 60-90 分钟：互评

两组交换 trace，互相找问题：

- 范围是否过大？
- 是否漏掉 Human Gate？
- 验证命令是否具体？
- 是否有不可审计的表述？
- 是否把失败状态写清楚？

互评时可以用一句话标准：

> 如果明天换一个同学接手，他能不能根据这份 trace 知道 AI 做了什么？

## 20. 团队协作矩阵

多人项目最容易在 Week 15 失控。下面的矩阵可以帮助团队分工。

### 20.1 角色和责任

| 团队成员 | 负责模块 | 可审批范围 | 不可审批范围 |
|---|---|---|---|
| 产品负责人 | Demo 路径、文案、证据包 | 页面文案、路径删减 | 数据库、支付 |
| 前端负责人 | 页面、状态、移动适配 | 前端组件、样式 | 后端权限、密钥 |
| 后端负责人 | API、数据库、AI 调用 | API 错误处理、测试接口 | 生产数据删除 |
| 质量负责人 | 测试、trace、review | 测试补充、证据整理 | 绕过测试 |

如果团队只有 2 人，也要明确谁审批什么。

### 20.2 每日收口模板

最后一周建议每天用 10 分钟同步：

```markdown
## Daily Delivery Check

- 今天只做的任务：
- 使用 AI 的任务：
- 触发 Human Gate 的地方：
- 修改文件：
- 验证命令：
- 当前 blocking：
- 明天不做的事：
```

最后一项"明天不做的事"很重要，它能阻止期末前无休止加功能。

### 20.3 冲突处理

如果两个 Agent 或两个人同时改同一文件：

1. 停止继续修改。
2. 查看 diff。
3. 由文件 owner 决定保留哪个方向。
4. 重新跑验证。
5. 在 trace 里记录冲突和处理方式。

不要让 AI 自动合并高风险文件，尤其是认证、支付、数据库和部署配置。

## 21. 长版 trace 示例：从失败到通过

下面是一个更完整的 trace，适合学生模仿。

```markdown
## Trace: RAG 引用缺失修复

### 1. 背景
期末 Demo 中，知识库问答能回答问题，但没有显示引用来源。教师无法判断回答是否基于文档。

### 2. 任务
- 目标：让 RAG 回答显示引用来源。
- 允许文件：
  - `app/api/rag/route.ts`
  - `app/rag/page.tsx`
  - `tests/rag-citations.spec.ts`
- 禁止事项：
  - 不更换向量数据库。
  - 不重新切分全部文档。
  - 不修改认证。
  - 不删除现有 eval。

### 3. Human Gate
- 风险等级：G2，因为涉及 RAG 后端逻辑。
- 审批结论：允许修改上述文件。
- 补充限制：如果需要迁移数据，必须停止。

### 4. Planner 输出
- Step 1：查看 API 返回结构。
- Step 2：检查检索结果是否包含 `source`。
- Step 3：让 API 返回 `citations` 字段。
- Step 4：前端展示引用。
- Step 5：补测试。

### 5. Coder 执行
- API 增加 `citations` 数组。
- 前端在答案下方展示来源标题和片段。
- 未修改数据库 schema。

### 6. Tester 验证
- 命令：`npm test -- rag-citations`
- 结果：第一次失败，因为 mock 数据没有 source。
- 修复：补 mock source。
- 再次运行：通过。

### 7. Reviewer 结论
- Blocking：无。
- Risk：引用片段过长，可能影响 UI。
- 决策：可答辩，后续优化引用折叠。
```

这个 trace 的价值在于它记录了失败到通过，而不是只记录成功。

## 22. trace 反例

### 22.1 反例 A：只有聊天记录

```markdown
我问 AI 怎么修，它说要改 API，然后我让它改了，最后好了。
```

问题：

- 没有文件范围。
- 没有审批。
- 没有测试。
- 没有 diff。

### 22.2 反例 B：范围过大

```markdown
目标：优化所有页面、修复后端、完善部署。
允许文件：全部。
验证：看起来能跑。
```

问题：

- 没有边界。
- 没有可测验收。
- 没有 Human Gate。

### 22.3 反例 C：AI 自己审批

```markdown
AI 判断可以修改数据库，所以继续执行。
```

问题：

- Human Gate 必须由人类或团队规则审批，不能由执行 Agent 自批。

### 22.4 反例 D：删除失败测试

```markdown
测试失败原因是旧测试不适合新逻辑，所以删除。
```

问题：

- 删除失败测试是高风险操作，必须人工审批。
- 更好的做法是解释测试为何过期，并提交替代测试。

## 23. 项目 profile：不同项目的 Agent 规则重点

### 23.1 AI 创作工具

重点风险：

- Prompt 改动不可追踪。
- 模型输出质量没有样本集。
- API Key 暴露。
- 成本失控。

规则重点：

- Prompt 修改必须记录前后样本。
- 模型供应商变更必须审批。
- 前端不得保存 Key。
- 至少保留 3 个失败样本。

### 23.2 RAG 知识库

重点风险：

- 检索权限错误。
- 文档版本混乱。
- 回答编造。
- 引用缺失。

规则重点：

- 不允许绕过权限过滤。
- 不允许删除失败 eval。
- 修改 chunk 或 embedding 需要记录。
- 答案必须带引用或拒答。

### 23.3 支付或会员项目

重点风险：

- 真实扣费。
- webhook 状态错乱。
- 订单金额单位错误。
- 前端伪造会员状态。

规则重点：

- 必须测试模式。
- 不能触发真实支付。
- webhook 修改必须审批。
- 订单状态必须由后端更新。

### 23.4 小程序/跨平台项目

重点风险：

- 登录身份混乱。
- 请求域名和环境不一致。
- 平台限制被忽略。
- Web 逻辑直接搬迁。

规则重点：

- 平台接口失败必须记录错误码。
- 登录 mock 必须标注。
- 发布或上传审核必须审批。
- 不承诺未验证的平台能力。

## 24. 期末提交前的 AI 使用禁区

最后 24 小时，建议禁止 AI 做这些事：

- 大规模重构。
- 升级框架。
- 更换 UI 库。
- 重写数据库 schema。
- 更换模型供应商。
- 引入新支付流程。
- 批量格式化全仓库。
- 删除测试。
- 删除历史证据。

最后 24 小时适合 AI 做：

- 补 README。
- 整理证据包。
- 写失败状态说明。
- 生成答辩提纲。
- 检查链接。
- 总结风险。
- 补小范围测试。

## 25. Week 15 如何进入最终答辩

答辩中 Agent 工程部分可以用 40 秒讲清：

```markdown
最后一周我们没有让 AI 任意改项目，而是写了 `AGENTS.md`。
AI 被允许修改页面、API 错误处理、测试和文档。
认证、支付、数据库、密钥和部署都需要 Human Gate。
我们记录了一次 trace：修复 AI 推荐失败状态。
trace 包含任务、允许文件、审批、diff、测试命令和剩余风险。
```

然后展示 trace 文件的一页即可。不要放 20 张聊天截图。

## 26. 本周回顾

本周的核心不是让 Agent 变多，而是让责任边界变清楚。一个可信的 AI 工程工作流应该能被复盘：谁提出任务，谁批准边界，工具有什么权限，AI 产生了哪些改动，验证证据在哪里，人类最终判断了什么。

期末项目越接近交付，越不能把 AI 当成万能助手。AI 可以帮你计划、修改、测试、总结，但不能替你承担产品责任、安全责任和真实性责任。

如果 Week 14 证明了你的产品能走到另一个平台，Week 15 就要证明你的团队能用 AI 稳定地完成最后交付。

## 20. 下周预告

第 16 周是期末答辩与技术评审。你需要把 Week 14 的跨平台证据、Week 15 的 Agent trace、前面几周的数据库/AI/RAG/部署证据整合成一个 final evidence package。

答辩不是展示"我做了很多页面"，而是证明一个 AI 全栈产品能运行、能解释、能验证、能承认边界。
