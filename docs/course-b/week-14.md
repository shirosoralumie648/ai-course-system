## 上节课回顾

第 13 周我们做的是"小程序后端开发"，重点不是把所有业务都放进云开发，而是看清楚小程序生态里哪些事情必须由后端承担：身份识别、数据库读写、文件上传、内容审核、支付签名、权限控制和日志追踪。

这一周要把视角再拉高一层。你的产品可能已经有 Web 版本，也可能刚完成一个小程序页面，还可能只有一个后端 API 和一套原型图。现在的问题不是"我能不能再做一个 App"，而是：

1. 用户为什么会在另一个平台使用它？
2. 哪条路径最值得迁移？
3. 迁移之后，原来的数据、AI、支付、认证、RAG 或文件能力还能不能工作？
4. 哪些能力必须承认暂时做不到？

很多项目在这个阶段翻车，不是因为学生不会写代码，而是因为目标过大。一个团队说"我们要做 Web、PWA、小程序、App 四端统一"，听起来很完整，但只要问一句"本周你要演示哪一个用户在什么场景完成哪一个动作"，就会发现答案是空的。

本周的核心动作是把"多端"重新翻译成"一条跨平台用户路径"。

## 1. 小哲的跨平台误区

小哲的期末项目是一个 AI 校园活动助手。Web 版已经能完成三件事：

1. 浏览活动列表。
2. 输入兴趣，让 AI 推荐活动。
3. 点击活动，提交报名。

第 13 周他用云开发做了一个小程序后端 demo，能读取活动数据。但到了第 14 周，他打开项目计划，写下了这样一段目标：

> 本周完成小程序版、PWA 版和移动 App 版，所有功能和 Web 版保持一致。

这句话看起来积极，实际是失控信号。教师追问他：

- 你的小程序用户是谁？
- 用户为什么不用 Web？
- 第一次演示要跑哪条路径？
- 登录、活动数据、AI 推荐、报名状态、消息通知都要迁移吗？
- 如果小程序接口失败，你怎么展示？
- 如果 PWA 离线，用户能看到什么？
- 如果移动端真机权限失败，怎么解释？

小哲答不上来。他把"跨平台"理解成"复制所有页面"，没有把它理解成"为新的使用场景重新设计一条路径"。

### 1.1 跨平台不是复制屏幕

Web 页面通常有更大的空间，可以放筛选、列表、卡片、侧边栏、弹窗和后台入口。小程序和移动端的空间小得多，用户打开场景也不同：地铁上、排队时、微信群里、扫码后、课堂中、线下活动现场。

所以迁移时不能问：

> Web 有哪些页面，我逐个搬过去？

而应该问：

> 用户在这个平台上最急着完成什么？

举例：

| 产品 | Web 主路径 | 跨平台最小路径 | 平台价值 |
|---|---|---|---|
| AI 校园活动助手 | 搜索活动、AI 推荐、报名、管理后台 | 扫码进入活动页，查看 AI 推荐理由，提交报名 | 线下活动现场扫码 |
| 简历诊断工具 | 上传简历、AI 批注、历史记录、导出 | 手机上传一份简历，得到三条修改建议 | 移动端文件选择和即时反馈 |
| 企业知识库 | 管理文档、问答、权限、统计 | 手机输入一个问题，得到带引用的答案 | 外勤或会议中快速查资料 |
| 预约排班工具 | 创建服务、设置时段、客户预约、后台统计 | 查看可预约时段，提交预约请求 | 微信分享和轻量下单 |
| 图片生成工作台 | Prompt 管理、批量生成、资产库 | 手机选择模板，生成一张预览图 | 移动端快速创作 |

如果你迁移的是"所有功能"，这周就会变成赶工。如果你迁移的是"一条路径"，这周才有可能形成可信证据。

### 1.2 最小跨平台版本的定义

本课程中的最小跨平台版本必须包含四个部分：

1. 一个目标平台：PWA、小程序或移动端 App，不能三者都做。
2. 一条核心路径：用户从入口到结果的 3-6 个动作。
3. 一个数据或 AI 连接点：真实接口、mock 接口或静态数据必须说清。
4. 一组验证证据：成功截图、失败状态、限制说明和下一步计划。

它不要求：

- 完整账号系统。
- 完整支付链路。
- App Store 或小程序正式发布。
- 与 Web 版完全一致的 UI。
- 所有历史数据同步。
- 所有平台能力一次性接入。

学生可以选择 PWA，只做安装、离线首页和核心页面访问；可以选择小程序，只做一个页面和一次接口调用；也可以选择移动端，只做一个核心页面和一次导航。关键是证据清楚。

## 2. 先做平台决策，而不是先装框架

很多学生一进入本周就会问：

- Expo、Taro、uni-app 选哪个？
- 小程序是不是一定要用云开发？
- PWA 是不是只要加 manifest？
- React Native 和 Flutter 哪个更好？

这些问题都不是第一问题。第一问题是平台使用场景。

### 2.1 三类平台的核心差异

| 平台 | 用户入口 | 适合产品 | 技术重点 | 最大风险 |
|---|---|---|---|---|
| PWA | 浏览器、桌面图标、手机主屏 | 原本就是 Web，想提升访问便利和离线体验 | manifest、service worker、响应式、缓存策略 | 只加图标，没有离线和失败体验 |
| 小程序 | 微信/支付宝/字节等生态、扫码、分享 | 需要社交传播、扫码、轻量表单、平台支付或生态入口 | 平台组件、请求域名、登录、云函数、审核 | Web 代码不能直接搬，接口和权限限制多 |
| 移动端 App | 应用安装、真机、推送、相机、定位 | 高频使用、需要设备能力、长期留存 | Expo/React Native/Flutter、权限、构建、调试 | 模拟器能跑，真机和发布成本被低估 |

判断时可以用一个很简单的决策树：

```text
用户是否主要从微信/支付宝生态进入？
  是 -> 优先小程序
  否 ->
    是否已有 Web 产品，且移动端只需要更易访问/离线？
      是 -> 优先 PWA
      否 ->
        是否需要相机、定位、推送、传感器或长期安装？
          是 -> 考虑移动端 App
          否 -> 继续优化响应式 Web，不强行跨平台
```

这棵树不完美，但能防止最常见的冲动：为了展示技术栈而做平台迁移。

### 2.2 平台选择说明模板

每个团队本周必须写一段平台选择说明。可以直接使用下面模板：

```markdown
## Week 14 平台选择说明

- 原产品核心路径：
- 本周迁移的平台：
- 目标用户和使用场景：
- 为什么选择这个平台：
- 为什么暂不选择 PWA：
- 为什么暂不选择小程序：
- 为什么暂不选择移动端 App：
- 本周只迁移哪一条路径：
- 这条路径需要的数据或 AI 能力：
- 暂不迁移的能力：
```

注意：就算你选择 PWA，也要解释为什么不做小程序和移动 App。这个动作会迫使团队把选择说清，而不是默认"哪个简单做哪个"。

### 2.3 教师现场追问

教师可以用下面问题快速判断学生是否真的做了平台决策：

1. 如果用户只是在手机浏览器打开，你为什么需要小程序？
2. 如果你的核心能力是微信分享，你为什么选择 PWA？
3. 如果你没有使用相机、定位、推送或长期安装，你为什么要做 App？
4. 如果只迁移一个页面，这个页面如何证明产品价值？
5. 如果接口失败，用户看到什么？
6. 你的跨平台版本和原 Web 版本共享什么：数据、接口、设计、业务规则，还是只共享名字？

答不上来的团队，不应该马上开始写代码，而应该回到路径设计。

## 3. reference 拆解：从成熟项目读平台边界

本周的 reference 不是让你运行大型框架仓库，而是学习成熟跨平台项目如何说明自己的目标平台、模块边界和发布路径。

| 参考项目 | 建议阅读 | 借鉴到课堂 |
|---|---|---|
| `reference/repos/cross-platform/expo/README.md` | Expo 如何把 Android、iOS、Web 放在 universal app 叙事下，并区分 SDK、Router、templates、EAS 等模块 | 判断什么时候应该做移动端 App，以及移动端交付不只是页面，还包括构建、真机、发布和迭代 |
| `reference/repos/cross-platform/taro/README.md` | Taro 面向小程序、H5、React Native 等多端，强调一套代码适配多端，也列出 UI 库、版本迁移和社区案例 | 判断 Web 思维迁移到小程序时会遇到组件、路由、构建和平台 API 限制 |
| `reference/repos/cross-platform/uni-app/README.md` | uni-app 强调 Vue 技术栈、一套代码、多平台发布，并区分 uni-app 与 uni-app x | 设计"先最小版本，后多端扩展"的迁移策略，避免一开始追求全平台 |

### 3.1 读 Expo：移动端交付不是一个页面

读 Expo 时不要只看"可以写 React"。重点看它的工程叙事：

- SDK 提供设备能力。
- Router 处理页面组织。
- Templates 降低起步成本。
- EAS 处理构建、发布和更新。
- Android、iOS、Web 都是目标平台，但每个平台仍有差异。

课堂借鉴点是：如果你选择移动端 App，本周至少要说明运行环境、真机或模拟器、权限、构建路径和发布成本。不能只交一张浏览器截图说"这是 App 版"。

移动端路线的最小证据可以是：

```markdown
- 运行方式：Expo Go / 模拟器 / 真机
- 核心页面：`HomeScreen` 或 `RecommendationScreen`
- 设备能力：未使用 / 文件选择 / 相机 / 定位
- API 调用：真实接口 / mock 接口 / 静态数据
- 成功截图：
- 失败状态截图：
- 权限说明：
- 未做发布的原因：
```

### 3.2 读 Taro：小程序不是小屏 Web

Taro 的价值不只是"一套代码多端"。对学生更重要的是看到：

- 小程序有自己的组件和生命周期。
- 路由、状态、构建和平台 API 都有适配成本。
- 多端适配不是零成本，尤其是支付、登录、文件、地图、分享这些能力。

如果团队选择小程序，本周要交的不只是页面截图，还要交平台限制表：

| 限制 | 影响 | 本周处理 |
|---|---|---|
| 请求域名必须配置 HTTPS | 本地接口不能直接在真机访问 | 使用 mock 数据或部署测试接口 |
| 登录依赖平台身份 | Web 登录逻辑不能直接复用 | 本周先用 mock 用户或云函数获取 openid |
| 组件与 CSS 有差异 | Web 页面不能直接复制 | 只做一个核心页面，重新布局 |
| 支付/订阅需要审核 | 无法课堂内完整上线 | 只记录流程，不触发真实支付 |
| 文件权限受限制 | 上传和预览要单独处理 | 只验证一种文件类型或暂不迁移 |

### 3.3 读 uni-app：先最小版本，再多端扩展

uni-app 的 README 通常会强调一套代码发布到多个平台。课堂上要提醒学生：这个愿景很吸引人，但本周不要把"多平台发布"作为最低目标。

我们可以借鉴它的方式来写扩展路线：

```markdown
## 多端扩展路线

### 当前版本
- 只发布到：
- 只迁移路径：
- 数据来源：

### 下一步
- 可扩展到：
- 需要替换或重写的模块：
- 需要新增的平台能力：

### 暂不承诺
- 不承诺全平台 UI 一致。
- 不承诺所有平台能力一致。
- 不承诺所有业务流程一次迁移。
```

这比一句"未来可以多端发布"可信得多。

### 3.4 Reference 借鉴卡

```markdown
## Week 14 Reference 借鉴卡

- 来源：
- 阅读范围：
- 它解决的问题：
- 我借鉴的跨平台判断：
- 我在自己项目中的最小实现：

```

合格借鉴不是写"我参考了 Expo"，而是写"我从 Expo 看到移动端交付包含构建和真机验证，所以本周只做 Expo Go 真机预览，不承诺商店发布"。

## 4. 迁移一条用户路径

平台选完后，下一步不是搭项目，而是把 Web 路径压缩成跨平台路径。

### 4.1 路径压缩方法

把原 Web 路径写成表格：

| 步骤 | Web 版 | 是否迁移 | 跨平台改写 |
|---|---|---|---|
| 入口 | 首页导航进入活动页 | 是 | 扫码或首页卡片进入 |
| 搜索 | 输入关键词和筛选条件 | 部分 | 只保留一个关键词输入 |
| AI 推荐 | 调用推荐接口生成理由 | 是 | 保留一次接口调用 |
| 报名 | 填写完整表单 | 部分 | 只提交姓名和联系方式 |
| 历史记录 | 查看全部报名历史 | 否 | 本周不迁移 |
| 管理后台 | 管理活动 | 否 | 保留在 Web |

这个表格比原型图更重要，因为它让教师能看出团队的取舍。

### 4.2 三分钟演示路径

跨平台版本必须能在 3 分钟内演示：

```text
0:00 - 0:20 说明目标平台和用户场景
0:20 - 0:50 打开跨平台版本
0:50 - 1:40 跑核心路径
1:40 - 2:10 展示成功状态和数据/AI 证据
2:10 - 2:40 展示失败或空状态
2:40 - 3:00 说明未迁移能力和下一步
```

如果演示超过 3 分钟还没有到成功状态，路径太长。

### 4.3 数据连接点

跨平台版本可以使用三类数据，但必须说清：

| 数据类型 | 适合情况 | 必须说明 |
|---|---|---|
| 真实接口 | 原 Web 已有 API，跨平台能访问 | 请求路径、状态码、错误处理、是否需要登录 |
| mock 接口 | 域名、登录或审核限制暂时阻挡真实接口 | mock 的字段、和真实接口的差异、替换计划 |
| 静态数据 | 本周只验证界面和路径 | 静态数据来源、不能证明的能力 |

不允许只说"数据之后接"。如果本周没有真实接口，也要用 mock 或静态数据把字段和状态设计出来。

## 5. 路线 A：PWA 最小实现

PWA 适合那些已经有 Web 产品，并且本周目标是提升移动访问、安装和离线体验的项目。

### 5.1 PWA 最小交付内容

一个合格的 PWA 最小版本至少包含：

1. `manifest.webmanifest` 或等价 manifest 配置。
2. 移动端可读的核心页面。
3. 可安装证据：浏览器安装提示或安装后图标。
4. 离线状态：至少首页可打开，或明确展示离线提示。
5. 恢复联网后的刷新或重试路径。

如果只是加一个图标和主题色，没有离线和失败体验，不算合格 PWA。

### 5.2 manifest 示例

```json
{
  "name": "AI Campus Assistant",
  "short_name": "Campus AI",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#2563eb",
  "icons": [
    {
      "src": "/icons/icon-192.png",
      "sizes": "192x192",
      "type": "image/png"
    },
    {
      "src": "/icons/icon-512.png",
      "sizes": "512x512",
      "type": "image/png"
    }
  ]
}
```

课堂上不要求图标设计完美，但要求路径和图标文件存在，浏览器能识别 manifest。

### 5.3 service worker 的最小思路

学生不需要写复杂缓存策略，但要理解三层：

| 层 | 作用 | 本周最低要求 |
|---|---|---|
| App shell | 首页、CSS、JS、基础图标 | 离线时能打开基本页面 |
| 核心数据 | 活动列表、最近一次推荐、用户草稿 | 可以缓存，也可以明确不缓存 |
| 网络失败 | API 超时、离线、500 | 给用户可理解提示 |

简化 service worker 可以这样描述：

```js
const CACHE_NAME = 'campus-ai-v1'
const APP_SHELL = ['/', '/offline.html']

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(APP_SHELL))
  )
})

self.addEventListener('fetch', (event) => {
  if (event.request.mode === 'navigate') {
    event.respondWith(
      fetch(event.request).catch(() => caches.match('/offline.html'))
    )
  }
})
```

这段代码不是生产方案，但能帮助学生理解：PWA 的核心不是"像 App"，而是网络状态变化时还能给用户合理反馈。

### 5.4 PWA 验证证据

提交时至少包含：

- 手机浏览器或桌面浏览器访问截图。
- 安装提示或安装后图标截图。
- 离线打开截图。
- 核心页面成功状态截图。
- API 失败或离线提示截图。
- manifest 和 service worker 文件路径。
- 未缓存敏感数据的说明。

## 6. 路线 B：小程序最小实现

小程序适合依赖扫码、分享、微信生态、平台支付或线下触达的产品。

### 6.1 小程序最小交付内容

一个合格的小程序最小版本至少包含：

1. 一个页面。
2. 一个核心路径入口。
3. 一次数据读取或 mock 数据渲染。
4. 一个成功状态。
5. 一个失败或空状态。
6. 开发者工具运行截图。
7. 平台限制说明。

不要求正式上线，也不要求审核通过。

### 6.2 页面结构示例

以 AI 活动推荐为例，小程序页面可以压成：

```text
pages/recommend/index
  - 顶部：活动助手标题和场景说明
  - 输入：兴趣关键词
  - 主按钮：生成推荐
  - 结果：活动卡片 + AI 推荐理由
  - 状态：加载中 / 失败 / 空结果
```

小程序不是把 Web 版列表、筛选器、侧边栏都塞进去，而是优先保留主操作。

### 6.3 请求限制示例

小程序调用接口经常卡在域名、HTTPS、登录或 CORS。课堂里要把这些问题变成表格：

```markdown
## 小程序接口限制记录

- 请求地址：
- 是否 HTTPS：
- 是否配置 request 合法域名：
- 是否需要登录态：
- 成功状态码：
- 失败状态码：
- 错误消息：
- 本周处理方式：
```

这比一句"接口失败了"有价值。

### 6.4 mock 用户策略

如果完整登录来不及，可以先用 mock 用户，但必须写清楚：

```js
const demoUser = {
  id: 'demo-user-001',
  nickname: '课堂演示用户',
  role: 'student'
}
```

同时在限制说明里写：

- 本周没有完成真实微信登录。
- 报名记录使用 demo 用户身份。
- 下一步需要用 `wx.login` 或云函数获取用户身份。
- 后端必须根据真实身份做权限校验，不能相信前端传入的用户 ID。

这样 mock 才是教学取舍，不是糊弄。

### 6.5 小程序验证证据

提交时至少包含：

- 开发者工具运行截图。
- 页面成功状态截图。
- 接口调用日志或 mock 数据说明。
- 错误状态截图。
- 请求域名/登录/支付/文件限制表。
- 与 Web 版路径的差异说明。

## 7. 路线 C：移动端 App 最小实现

移动端 App 适合需要真机能力、长期安装、高频使用或系统通知的产品。

### 7.1 移动端最小交付内容

本课程不要求 App Store 或应用市场发布。本周最低要求是：

1. 使用 Expo、React Native、Flutter 或类似方案启动项目。
2. 有一个核心页面。
3. 有一次导航或状态变化。
4. 有一次 API 调用、mock 数据或静态数据渲染。
5. 有模拟器或真机运行证据。
6. 有权限和发布成本说明。

### 7.2 Expo 起步路径

如果使用 Expo，可以这样组织：

```text
app/
  index.tsx
  recommendation.tsx
components/
  ActivityCard.tsx
services/
  recommendation-api.ts
```

最小服务函数可以写成：

```ts
export async function fetchRecommendations(keyword: string) {
  if (!keyword.trim()) {
    return []
  }

  return [
    {
      id: 'demo-1',
      title: '摄影社新手工作坊',
      reason: `因为你关注 ${keyword}，这个活动适合作为入门体验。`
    }
  ]
}
```

如果真实接口还不能调用，这个 mock 函数也要和未来接口字段保持一致。

### 7.3 权限说明

移动端最容易被低估的是权限。即使本周没有使用设备能力，也要写清：

| 能力 | 本周是否使用 | 未来是否需要 | 风险 |
|---|---|---|---|
| 相机 | 否 | 可能用于扫码或上传 | 需要权限弹窗和失败提示 |
| 文件 | 是/否 | 简历、图片、文档上传 | 文件大小和格式限制 |
| 定位 | 否 | 活动推荐可能需要 | 隐私风险高，必须解释用途 |
| 推送 | 否 | 活动提醒可能需要 | 需要用户授权和服务端支持 |
| 通知 | 否 | 后续可做 | 不应课堂内承诺已完成 |

### 7.4 移动端验证证据

提交时至少包含：

- 模拟器或真机截图。
- 启动命令和结果。
- 核心页面成功状态。
- 错误或空状态。
- API/mock 数据说明。
- 权限和发布成本说明。

## 8. 课堂 Demo：同一条路径的三种改写

教师可以用"查看订单并获得 AI 建议"演示三种平台改写。学生不需要三种都做，但要看清楚差异。

原 Web 路径：

1. 用户登录。
2. 查看订单列表。
3. 点击订单详情。
4. 如果 AI 生成了建议，展示建议和来源。
5. 用户进入后台查看历史记录。

### 8.1 PWA 改写

PWA 版本保留 Web 路由和接口，但强调访问体验：

- 用户从手机主屏打开。
- 首页加载订单摘要。
- 离线时显示"当前无法同步订单，可查看最近缓存摘要"。
- 恢复联网后点击刷新。

PWA 的验证重点不是"页面一样"，而是安装、离线和恢复联网后的体验。

### 8.2 小程序改写

小程序版本压缩成两页：

- `订单列表页`：展示最近 3 个订单。
- `订单详情页`：展示 AI 建议和错误状态。

如果完整登录来不及，用 mock 用户；如果接口域名未配置，用 mock 数据；但必须写清限制。

小程序的验证重点是平台组件、调试工具、请求限制和页面跳转。

### 8.3 移动端改写

移动端版本用一个列表页和一个详情页：

- 首页展示订单卡片。
- 点击后进入详情页。
- 如果使用真机能力，可以加入扫码查订单；如果来不及，就明确不使用设备能力。

移动端的验证重点是设备适配、导航、权限说明和运行日志。

## 9. 成功状态、失败状态和空状态

跨平台作业不能只交成功截图。每个版本都必须有三种状态。

### 9.1 成功状态

成功状态回答：

- 用户做了什么？
- 系统返回了什么？
- 这个结果来自哪里？
- 是否能证明核心价值？

示例：

```markdown
成功状态：用户输入"摄影"，系统返回"摄影社新手工作坊"，并展示 AI 推荐理由。
数据来源：`GET /api/activities?interest=photo`
证据：开发者工具 Network 截图 + 页面截图
```

### 9.2 失败状态

失败状态回答：

- 哪一步失败？
- 用户看到什么？
- 是否可以重试？
- 开发者如何定位？

示例：

```markdown
失败状态：接口返回 500。
用户提示：活动推荐暂时不可用，请稍后重试。
开发日志：记录 requestId、status、message。
下一步：后端加入超时和供应商错误分类。
```

### 9.3 空状态

空状态不是错误。例如用户输入了一个没有匹配活动的兴趣。页面应该说：

- 暂时没有匹配活动。
- 可以换一个关键词。
- 可以查看全部活动或提交需求。

空状态能体现产品细节，也能防止答辩时只靠一次成功路径。

## 10. 安全和隐私边界

跨平台版本常常会碰到更敏感的数据，因为手机和小程序更容易接触用户身份、文件、定位、相机和支付。

### 10.1 API Key 不能放前端

无论是 PWA、小程序还是移动 App，都不能把 AI API Key、支付密钥、数据库 service key 放在客户端。

不合格做法：

```js
const apiKey = 'sk-...'
fetch('https://api.openai.com/v1/chat/completions', {
  headers: { Authorization: `Bearer ${apiKey}` }
})
```

合格做法：

```text
客户端 -> 自己的后端 API -> AI 服务商
```

客户端只拿到必要结果，密钥留在服务端。

### 10.2 文件上传要说明边界

如果跨平台路径涉及文件上传，例如简历、图片、PDF，需要说明：

- 允许上传哪些类型？
- 最大文件多大？
- 文件是否会被 AI 读取？
- 是否保存？
- 用户如何删除？
- 上传失败时如何提示？

课程项目不要求做完整隐私合规，但不能假装没有风险。

### 10.3 定位和相机要有理由

如果 App 或小程序请求定位、相机、通讯录、相册权限，必须写清使用理由。不允许为了"看起来像 App"随便申请权限。

合格说明：

```markdown
本周使用相机权限，是为了扫码打开线下活动页面。
不使用定位权限，因为活动推荐暂时只按用户输入兴趣，不按当前位置。
```

## 12. 常见失败案例和纠偏

### 12.1 失败：直接复制 Web 页面

表现：

- 页面挤在手机屏幕上。
- 表格横向滚动。
- 按钮太小。
- 重要操作藏在底部。

纠偏：

先把路径重画成移动结构：

```text
顶部：当前任务
主体：核心内容
主按钮：唯一主要操作
状态：成功/失败/空
次要信息：折叠或放到详情页
```

### 12.2 失败：三端一起做

表现：

- 每端都有一点截图。
- 没有一端完整跑通。
- 不能说明数据从哪来。

纠偏：

只保留一端，把另外两端写进"暂不选择理由"。

### 12.3 失败：接口失败只说平台问题

表现：

- 小程序请求失败。
- 学生说"微信限制"。
- 没有状态码、域名、日志。

纠偏：

填写接口限制记录表，明确是 HTTPS、域名白名单、登录态、请求头、CORS 还是后端错误。

### 12.4 失败：PWA 没有离线体验

表现：

- 加了 manifest。
- 能安装。
- 断网后白屏。

纠偏：

至少添加离线提示页，说明哪些数据不能离线使用。

### 12.5 失败：移动端只在网页里展示

表现：

- 用浏览器响应式截图冒充 App。
- 没有模拟器、真机或运行命令。

纠偏：

要么承认做的是 PWA，要么提交 Expo/React Native/Flutter 的运行证据。

## 13. 学生项目案例：AI 简历诊断

假设一个团队的 Web 产品是 AI 简历诊断工具。

### 13.1 原 Web 版本

能力：

- 上传 PDF 简历。
- AI 生成诊断报告。
- 展示历史报告。
- 导出修改建议。
- 后台查看用量。

### 13.2 平台选择

团队选择 PWA，不选择小程序和 App。

理由：

- 用户主要从浏览器打开工具。
- 文件上传和报告阅读更适合 Web/PWA。
- 本周不需要微信生态分享。
- 移动 App 发布成本过高。

### 13.3 最小迁移路径

```text
打开 PWA -> 上传一份简历 -> 看到三条诊断建议 -> 断网后看到离线提示
```

暂不迁移：

- 历史报告。
- 批量导出。
- 用量后台。
- 支付。

### 13.4 验证证据

合格提交：

- PWA 安装截图。
- 上传页面截图。
- AI 建议成功截图。
- 上传失败提示截图。
- 离线提示截图。
- 说明 API Key 在后端。
- 说明文件不会缓存在 service worker 中。

这个案例的亮点是边界清楚。它没有做小程序，也没有做 App，但能证明移动访问路径和失败状态。

## 14. 学生项目案例：AI 校园活动助手

另一个团队选择小程序。

### 14.1 原 Web 版本

能力：

- 活动列表。
- AI 推荐。
- 报名。
- 管理后台。
- 活动数据统计。

### 14.2 小程序最小版本

迁移路径：

扫码进入活动推荐页 -> 输入兴趣 -> 获取 AI 推荐 -> 点击报名

## 19. 教师演示脚本：30 分钟完成一次迁移决策

这一节给教师使用。目标不是现场写完一个完整跨平台产品，而是让学生看到完整决策流程。

### 19.1 演示准备

教师提前准备一个简单 Web 产品，例如"AI 校园活动助手"：

- 首页。
- 活动列表。
- 推荐输入框。
- 推荐结果卡片。
- 报名按钮。
- 一个 mock API 或静态 JSON。

不需要复杂后端，但要有清楚的数据字段。

### 19.2 0-5 分钟：展示 Web 路径

教师先跑 Web 版：

```text
打开首页 -> 输入兴趣 -> 得到推荐 -> 点击报名 -> 显示成功
```

然后问学生：

- 如果搬到小程序，哪些东西必须保留？
- 如果做 PWA，什么才算新增价值？
- 如果做移动 App，为什么用户愿意安装？

学生通常会说"都保留"。教师此时要停下来，指出跨平台第一步是删减，不是复制。

### 19.3 5-12 分钟：填路径压缩表

教师现场填表：

| Web 功能 | 是否迁移 | 原因 |
|---|---|---|
| 活动列表 | 是 | 用户需要选择活动 |
| AI 推荐 | 是 | 产品核心价值 |
| 报名 | 是 | 形成闭环 |
| 管理后台 | 否 | 不适合移动端用户 |
| 历史记录 | 否 | 本周不是核心演示 |
| 统计报表 | 否 | 保留在 Web |

让学生看到：删掉功能不是偷懒，而是工程判断。

### 19.4 12-20 分钟：三平台对比

教师用同一条路径解释三种方案：

| 平台 | 演示入口 | 本周目标 | 证据 |
|---|---|---|---|
| PWA | 手机浏览器安装 | 离线打开和移动访问 | 安装截图、离线截图 |
| 小程序 | 扫码打开 | 微信生态内报名 | 开发者工具、接口日志 |
| 移动端 App | Expo Go 打开 | 真机体验和导航 | 真机截图、权限说明 |

然后让学生投票：这个产品本周最适合哪条路线？

如果多数学生选择"三条都做"，教师要追问：

- 你们的演示时间是否允许？
- 你们是否有三套失败状态？
- 你们是否能解释三套限制？

### 19.5 20-30 分钟：写限制说明

教师现场写一段限制说明：

```markdown
本周选择小程序，因为活动报名主要发生在线下扫码和微信群传播场景。
本周只迁移"兴趣输入 -> AI 推荐 -> 报名"路径。
管理后台、活动统计和历史报名保留在 Web。
登录暂用 demo 用户，下一步接入微信身份。
AI 推荐由后端 API 调用模型，小程序不保存模型 Key。
接口请求需要 HTTPS 和合法域名配置，本周使用测试域名验证。
```

这段文字就是学生作业的标杆。

## 20. 项目 profile：不同产品如何选平台

不同项目不能用同一套跨平台策略。下面是几个典型 profile。

### 20.1 Profile A：AI 内容生成工具

特点：

- 用户主要在桌面或浏览器中写长文本。
- 移动端只需要轻量查看和快速生成。
- 文件和历史记录可能比较重要。

推荐：

- 优先 PWA。
- 移动端只做模板选择和结果查看。
- 不建议一开始做小程序，除非有强分享场景。

最小路径：

```text
打开 PWA -> 选择模板 -> 输入一句需求 -> 生成一段内容 -> 保存草稿
```

风险：

- 移动端输入体验差。
- 历史记录同步复杂。
- API Key 不能放客户端。

### 20.2 Profile B：校园/本地生活工具

特点：

- 用户来自微信群、二维码、线下活动。
- 表单和报名路径短。
- 分享很重要。

推荐：

- 优先小程序。
- Web 保留后台。
- PWA 可以作为备选。

最小路径：

```text
扫码 -> 查看活动 -> 输入信息 -> 提交报名 -> 收到成功状态
```

风险：

- 登录和手机号授权受平台限制。
- 接口域名需要配置。
- 支付和订阅需要审核。

### 20.3 Profile C：企业知识库或内部工具

特点：

- 权限和数据边界重要。
- 用户可能在会议或外勤中用手机查资料。
- RAG 引用和访问控制是关键。

推荐：

- 如果已有 Web，先做 PWA 或响应式 Web。
- 小程序只适合企业微信生态明确的场景。
- 移动 App 通常不是课程阶段首选。

最小路径：

```text
打开移动入口 -> 输入问题 -> 得到带引用答案 -> 查看无权限或无结果状态
```

风险：

- 离线缓存可能泄露资料。
- RAG 必须带权限过滤。
- 移动端不适合复杂文档管理。

### 20.4 Profile D：需要设备能力的工具

特点：

- 需要拍照、扫码、定位、推送或传感器。
- Web 难以提供完整体验。

推荐：

- 考虑移动端 App 或小程序。
- 如果只是扫码，小程序更轻。
- 如果需要长期安装和推送，考虑 App。

最小路径：

```text
打开 App -> 授权相机 -> 扫码/拍照 -> 上传 -> 得到结果
```

风险：

- 权限弹窗被拒绝。
- 真机和模拟器行为不同。
- 发布成本高。

## 21. 跨平台证据的命名和提交方式

学生经常把截图散落在聊天记录里，最后答辩找不到。建议统一命名。

### 21.1 文件命名

```text
docs/final-evidence/week-14/
  platform-decision.md
  path-comparison.md
  success-state.png
  empty-state.png
  error-state.png
  api-log.txt
  limitations.md
```

### 21.2 证据描述

每张截图旁边要有一句话：

```markdown
![小程序成功状态](./success-state.png)

用户输入"摄影"后，系统返回活动推荐和 AI 推荐理由。数据来自测试接口 `/api/activities/recommend`。
```

截图没有说明，评委仍然不知道它证明了什么。

### 21.3 录屏要求

录屏不需要精致剪辑，但要满足：

- 3 分钟以内。
- 从打开入口开始。
- 展示成功状态。
- 展示一个失败或空状态。
- 最后停在结果页或限制说明。

## 22. 验收反例：看起来完成但不合格

### 22.1 反例 A：三平台都有截图

学生提交：

- PWA 首页截图。
- 小程序首页截图。
- App 首页截图。

问题：

- 没有核心路径。
- 没有接口。
- 没有失败状态。
- 没有说明为什么做三端。

评分建议：不如一个平台完整。

### 22.2 反例 B：小程序页面很像 Web

学生把 Web 列表页完整搬到小程序：

- 10 个筛选条件。
- 横向表格。
- 管理入口。
- 很多小按钮。

问题：

- 移动端不可用。
- 用户场景不清。
- 平台价值不明显。

纠偏：删到一个入口、一个列表、一个主按钮。

### 22.3 反例 C：PWA 只加 manifest

学生交：

- manifest 文件。
- 图标。
- 首页截图。

问题：

- 没有安装证据。
- 没有离线证据。
- 没有失败提示。

纠偏：补离线页面和安装截图。

### 22.4 反例 D：移动端没有运行证据

学生说"我们做了 App 版"，但只有 Figma 图和浏览器截图。

问题：

- 没有模拟器或真机。
- 没有运行命令。
- 没有权限说明。

纠偏：要么改称移动端原型，要么补真实运行证据。

## 23. 期末衔接：Week 14 如何进入 final evidence

Week 14 的产物不要孤立提交。它要进入最终答辩证据包。

最终答辩中，跨平台部分可以这样讲：

```markdown
我们的原产品是 Web 版 AI 活动助手。
Week 14 我们选择小程序，因为主要使用场景是线下扫码和微信群传播。
我们只迁移了"兴趣输入 -> AI 推荐 -> 报名"路径。
Web 管理后台和统计没有迁移。
证据包括开发者工具截图、接口调用日志和失败状态截图。
当前限制是登录仍使用 demo 用户，下一步接入微信身份。
```

这段 40 秒就能讲清，比展示 5 张无说明截图更有效。

## 24. 本周回顾

本周的重点不是学会某个跨平台框架，而是学会用产品路径控制平台迁移的范围。一个可信的 Week 14 交付应该能回答：为什么是这个平台，为什么只迁移这条路径，哪些能力已经被验证，哪些能力还不能承诺。

跨平台不是让学生证明自己会更多技术名词，而是让学生证明自己能在新平台上保持产品判断、工程边界和验证证据。

如果你选择 PWA，就把安装、离线和移动访问体验证明清楚；如果你选择小程序，就把平台入口、接口限制和核心路径证明清楚；如果你选择移动端，就把真机或模拟器、权限和运行路径证明清楚。三者都不要求完整，但都要求诚实。

## 20. 下周预告

第 15 周会进入 Agent 工程。到那时，问题不再是"我能不能把产品迁到另一个平台"，而是"我能不能让 AI 在期末交付中按照明确规则工作"。

你需要为项目写规则文件、Human Gate、MCP 工具权限和 Agent 执行 trace。Week 14 的跨平台证据会成为 Week 16 期末答辩证据包的一部分，所以本周不要只追求跑通，要把限制和证据记录下来。
