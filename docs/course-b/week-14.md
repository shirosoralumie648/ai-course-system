# 第 14 周：小程序、移动端或 PWA 实现

> 第 13 周你已经做完平台决策，这周不再讨论"哪个平台最好"，而是选择一个平台做出最小可演示版本。目标不是重写整个产品，而是把最核心的一条用户路径带到新平台，并证明它和原 Web 产品共享同一套产品判断。

## 本周目标

1. 从决策矩阵中选一个平台方向，并说明不选另外两个方向的理由。
2. 做出一个最小可运行版本：一条核心路径、一个真实接口或模拟接口、一个可展示状态。
3. 说明哪些能力迁移了，哪些能力暂时保留在 Web。
4. 提交运行截图、限制说明、验证记录和下一步计划。

## 先定边界：不是重写，而是迁移一条路径

很多学生一开始会把跨平台理解成"我要把所有页面都变成 App / 小程序"。这会让两周后的期末项目失控。本周只做一条路径，例如：

| 原 Web 产品 | 可以迁移的最小路径 | 暂不迁移 |
|---|---|---|
| AI 简历诊断 | 上传一份简历，得到一次诊断摘要 | 会员体系、历史记录、批量导出 |
| 校园活动报名 | 查看活动列表，提交一次报名 | 管理后台、支付、复杂筛选 |
| 企业知识库 | 输入问题，返回一个引用答案 | 全量文档管理、权限后台、复杂 RAG 调参 |
| 预约工具 | 查看可预约时段，提交一次预约请求 | 日历同步、通知、多人排班 |

迁移时先问三件事：

1. 用户为什么会在这个平台打开它？
2. 这条路径是否能在 3 分钟内演示清楚？
3. 它依赖的平台能力是什么：扫码、定位、推送、相机、文件、支付、离线、分享，还是只是更方便打开？

如果答案只是"我想体验一下小程序"，本周产出就会变成平台练习，而不是产品迁移。

### Reference 借鉴卡

- 来源：`reference/repos/cross-platform/expo/README.md`、`reference/repos/cross-platform/taro/README.md`、`reference/repos/cross-platform/uni-app/README.md`
- 它解决的问题：帮助团队把"想做多端"改写成"为了某类用户选择一个交付平台"。
- 可借鉴做法：看 README 如何说明目标平台、项目结构、模板、构建/发布路径和社区生态。
- 我们课程中的用法：为自己的 Week 14 迁移写平台边界，不复制框架代码。
- 学生任务：选一个 reference，提交阅读范围、借鉴点、自己的最小实现截图或录屏。
- 不要照搬：不要把 Expo/Taro/uni-app 当成必须掌握的完整技术栈；本周只要求最小路径和验证证据。

本卡不是让你复制源码，而是训练你从成熟项目中提取可迁移的工程判断。

## 平台选择的实施矩阵

| 选择 | 最适合的场景 | 最小实现 | 常见风险 | 验证证据 |
|---|---|---|---|---|
| PWA | 原产品主要是 Web，用户需要收藏、离线打开、桌面/手机快速访问 | manifest、安装提示、离线首页、核心页面可访问 | 误以为 PWA 等于原网站；离线状态没有设计 | 安装截图、离线打开截图、网络失败提示 |
| 小程序 | 用户来自微信/支付宝等生态，需要分享、扫码、轻量触达 | 一个页面、一次接口调用、一个平台能力或分享入口 | Web 组件直接搬不动；登录、支付、文件权限受平台约束 | 开发者工具截图、接口调用日志、平台限制表 |
| 移动端 App | 需要真机体验、推送、相机、传感器、长期使用 | 一个核心页面、一次导航、一次 API 调用 | 模拟器能跑但真机权限失败；构建和发布成本被低估 | 模拟器/真机录屏、权限说明、构建命令日志 |

课堂上可以让学生先站队，再互相质询：如果你的产品只是"手机上也能打开"，为什么不用响应式 Web 或 PWA？如果你的产品必须在微信里传播，为什么不优先小程序？如果你需要相机/定位/推送，为什么 Web 足够？

## 课堂 Demo：把"查看订单"迁移成小程序/PWA/移动端

教师使用同一个产品路径演示三种改写方式，学生不需要三种都做，只需要看清楚差异。

原 Web 路径：

1. 用户登录。
2. 查看订单列表。
3. 点击订单详情。
4. 如果 AI 生成了建议，展示建议和来源。

### PWA 改写

- 保留 Web 路由和接口。
- 加 manifest，让用户可以安装到桌面或手机主屏。
- 离线时至少显示首页和"当前无法同步订单"。
- 验证重点不是"页面一样"，而是安装、离线和恢复联网后的用户体验。

### 小程序改写

- 把核心路径压成 1-2 个小程序页面。
- 先用 mock 用户身份，避免把完整认证系统带进课堂。
- 用一个接口读取订单列表，记录请求 URL、状态码、错误提示。
- 验证重点是平台组件、调试工具、接口域名限制和页面跳转。

### 移动端改写

- 使用 Expo 或类似框架做一个核心页面和一次导航。
- 如果使用真机能力，只选一个，例如拍照上传或推送占位。
- 不做完整 App Store 发布，只记录本地运行、模拟器或真机调试证据。
- 验证重点是设备适配、权限说明、运行日志和失败状态。

## 最小迁移检查表

| 检查项 | 合格做法 | 不合格做法 |
|---|---|---|
| 核心路径 | 只选一条，可在 3 分钟内跑完 | 把所有页面都列入计划 |
| 数据来源 | 明确是真实接口、mock 接口还是静态数据 | 截图能看但不知道数据从哪来 |
| 平台能力 | 说明用了哪个平台能力，或说明本周不需要 | 写"跨平台"但和 Web 无差异 |
| 限制说明 | 明确列出未迁移能力和原因 | 把未完成包装成"以后优化" |
| 验证证据 | 有截图/录屏、日志、失败状态 | 只有口头展示 |

## 常见失败案例

| 失败 | 课堂纠偏 |
|---|---|
| 直接复制 Web 页面，结果移动端文字、按钮、表格都挤在一起 | 先重画一条移动端路径：顶部信息、主操作、反馈状态、次要信息 |
| 小程序里接口请求失败，只说"平台问题" | 记录域名、HTTPS、请求头、状态码、错误消息，写成限制说明 |
| PWA 只改了 manifest，没有离线或安装验证 | 提交安装截图、离线首页截图、恢复联网后的刷新记录 |
| 移动端 App 模拟器能跑，真机权限失败 | 把权限写入风险表：需要什么权限、失败提示是什么、下一步如何申请 |
| 一周内试图同时做 PWA、小程序、移动端 | 砍到一个平台，把另外两个写进"为什么暂不选择" |

## 实验任务

选择一个方向完成：

| 方向 | 最小产出 |
|---|---|
| PWA | 可安装、可离线打开首页、能访问核心页面 |
| 小程序 | 能在开发者工具运行，至少完成一个核心页面和一次接口调用 |
| 移动端 | 能在模拟器或真机运行，至少完成一个核心页面和一次导航 |

提交时必须包含：

1. 平台选择说明：目标用户、平台理由、暂不选择的方向。
2. 核心路径说明：原 Web 路径和新平台路径的对照。
3. 运行证据：截图或录屏，至少包含成功状态和一个失败/空状态。
4. 参考借鉴说明：读了哪个 reference，借鉴了什么，哪些没有照搬。
5. 限制说明：未迁移能力、平台限制、下一步计划。

## 验收标准

- 有目标平台运行截图或录屏。
- 有一条核心用户路径说明。
- 有和原 Web 产品的差异说明。
- 有参考借鉴说明。
- 有失败状态或限制说明。
- 没有把所有功能一次性迁移作为本周目标。

## 本周回顾

本周的重点不是学会某个跨平台框架，而是学会用产品路径控制平台迁移的范围。一个可信的 Week 14 交付应该能回答：为什么是这个平台，为什么只迁移这条路径，哪些能力已经被验证，哪些能力还不能承诺。
