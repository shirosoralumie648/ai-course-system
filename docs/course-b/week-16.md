# 第 16 周：期末答辩与技术评审

> 最后一周不是"展示页面好不好看"，而是证明你真的交付了一个 AI 全栈产品：它能运行，有数据，有 AI 能力，有验证证据，有技术取舍，也知道自己的边界。

## 本周目标

1. 用 8-10 分钟证明产品核心路径可运行。
2. 用技术走查说明前端、后端、数据、AI、RAG、部署和跨平台取舍。
3. 用证据包支撑每个关键能力，而不是只靠现场演示。
4. 用 reference 借鉴说明展示你如何从成熟项目中提取工程判断。
5. 用风险清单说明产品边界和下一步迭代。

## 答辩结构

| 部分 | 时间 | 必讲内容 |
|---|---|---|
| 产品 Demo | 2 分钟 | 用户是谁、痛点是什么、核心流程怎么跑 |
| 技术走查 | 3 分钟 | 前端、数据库、后端 AI、RAG、部署、跨平台 |
| 证据展示 | 2 分钟 | 测试日志、真实调用、RAG eval、部署链接、diff |
| reference 借鉴 | 1 分钟 | 读了哪里、借鉴了什么、怎么简化到自己的项目 |
| 风险和边界 | 1 分钟 | 还不能做什么、下一步怎么补 |
| 问答 | 3 分钟 | 回答教师和同伴问题 |

建议顺序是"先跑通，再解释，再证明"。不要先讲 5 分钟架构图，让观众还不知道产品是否能用。

## 最终证据包

期末项目的证据包应该像一个小型 release package，而不是零散截图。

| 证据 | 必须包含 | 常见缺口 |
|---|---|---|
| 运行链接/录屏 | Web 部署地址；小程序/移动端提交录屏或真机截图 | 只能本地跑，部署链接打不开 |
| README | 安装、运行、测试、环境变量占位、核心路径说明 | 没写 env，别人无法复现 |
| 数据模型 | 表结构、关键字段、权限/RLS 或访问边界 | 只展示 UI，不知道数据如何保存 |
| AI 调用证据 | 请求路径、模型/供应商、错误处理、成本或用量记录 | 只说"接了 AI"，没有失败状态 |
| RAG eval | 至少 3 个测试问题、引用来源、失败样本和改进记录 | 只有一次成功问答截图 |
| 支付/认证/权限 | 测试模式日志、双用户权限测试、危险点说明 | 用管理员账号演示一切 |
| 跨平台证据 | Week 14 平台选择、最小版本截图、限制说明 | 只写"未来可做 App" |
| Agent 工程 | Week 15 规则、Human Gate、一次 trace | Agent 做了什么无法复盘 |
| reference 借鉴 | 至少 2 个来源，写清阅读范围和改造方式 | 只列链接，不说明借鉴点 |

如果某个能力不适用于你的产品，可以写"不适用"，但必须说明理由。例如一个纯创作辅助工具可能不需要支付；一个内部知识库可能不需要跨平台发布，但至少要有跨平台决策说明。

## 答辩示例：AI 校园活动助手

一个合格的答辩可以这样组织：

1. Demo：学生打开部署链接，搜索"本周适合摄影社新人的活动"，系统返回活动卡片和 AI 推荐理由。
2. 技术走查：前端是活动列表和问答页；后端有活动表和报名表；AI route 负责生成推荐摘要；RAG 从活动说明中检索；部署在 Vercel。
3. 证据：展示 3 个 RAG eval 问题，其中 1 个失败样本因为活动时间冲突，后续加了日期过滤；展示测试命令和部署截图。
4. reference 借鉴：从 `vercel-ai-chatbot` 借鉴后端 AI route 和错误状态，从 `supabase` 借鉴表结构/RLS 检查，从 `cal-com` 借鉴预约/日程类产品的边界意识。
5. 风险：没有接真实支付；权限只覆盖普通用户和管理员；跨平台只做了 PWA 安装，不承诺小程序发布。

这类答辩不一定技术最多，但证据链完整。

## 技术评审问题

答辩时会围绕这些问题追问：

1. 你的数据模型为什么这样设计？如果用户量扩大，哪个表最先出问题？
2. 哪些逻辑必须在后端，为什么不能放在前端？
3. AI 调用失败、超时或费用过高时，用户会看到什么？
4. RAG 的失败样本是什么，你怎么定位是检索问题、生成问题还是数据问题？
5. 支付、认证、权限里最危险的点是什么？你用什么证据证明它没有被忽略？
6. 跨平台版本为什么选择这个平台？你明确放弃了哪些平台能力？
7. Agent 帮你做了什么，哪些地方必须人工审批？
8. 你从 reference 借鉴了什么，为什么没有直接照抄？
9. 如果下周继续做，你会先补用户价值、工程稳定性还是商业能力？为什么？

## 常见扣分点

| 问题 | 为什么严重 | 如何补救 |
|---|---|---|
| Demo 只展示静态页面 | 不能证明是全栈产品 | 至少展示一次数据读写或 AI 调用 |
| AI 成功一次就算完成 | 没有失败处理和可信边界 | 补错误状态、日志、失败样本 |
| RAG 只展示漂亮回答 | 无法判断检索是否有效 | 补问题集、引用、失败案例和改进 |
| reference 只列链接 | 没有体现借鉴能力 | 写阅读范围、借鉴点和改造方式 |
| 跨平台只写未来计划 | 和 Week 14 断裂 | 补最小 PWA/小程序/移动端证据或清晰决策 |
| Agent 记录只有聊天截图 | 无法审计工作流 | 补任务边界、diff、测试、Human Gate |
| 追求技术堆叠 | 宽而浅，关键路径不稳 | 选择一个最终项目 profile，交付深证据 |

## 最终验收标准

- 产品能演示核心用户路径。
- 有至少一项真实后端能力：数据库、认证、文件、AI API、支付或部署。
- 有 AI/RAG 能力或明确说明为什么本产品不需要 RAG。
- 有跨平台决策或最小跨平台版本。
- 有 Agent 工程记录和 Human Gate。
- 有 reference 借鉴说明和验证证据。
- 有风险边界，不把未完成能力包装成已完成。

## 本周回顾

期末答辩不是让学生证明自己"什么都会"，而是证明自己能把一个产品问题、一个技术方案、一组工程证据和一套风险边界讲清楚。Course B 的最终目标不是技术名词的数量，而是学生能用成熟项目作为参照，做出有取舍、能运行、可复盘的 AI 全栈产品。
