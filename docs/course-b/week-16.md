# 第 16 周：期末答辩与技术评审

> 最后一周不是"展示页面好不好看"，而是证明你真的交付了一个 AI 全栈产品：它能运行，有数据，有 AI 能力，有验证证据，有技术取舍，也知道自己的边界。

## 上节课回顾

第 15 周我们给期末项目建立了 Agent 工程规则：`AGENTS.md`、Human Gate、MCP 工具卡、Agent Team 角色表和一次执行 trace。它解决的是"AI 在最后交付阶段如何被管理"的问题。

第 16 周要把所有证据整合起来，进入期末答辩与技术评审。

这周不是让学生展示一个漂亮页面，也不是让学生讲一堆技术名词，而是回答一个更严格的问题：

> 这个 AI 全栈产品是否真的能被运行、理解、验证和复盘？

一个成熟的期末答辩应该能让评委看到：

- 用户是谁。
- 产品解决什么问题。
- 核心路径是否能跑通。
- 数据在哪里。
- AI 或 RAG 如何工作。
- 失败状态如何处理。
- 权限、支付、隐私、成本和部署风险在哪里。
- 从 reference 借鉴了什么。
- Agent 帮了什么，人类在哪里做了判断。
- 项目还没有做到什么。

最后一周的关键词不是"更多功能"，而是"可信交付"。

## 1. 小哲的第一次失败答辩

小哲第一次试讲时准备了很多页面：

- 首页。
- 活动列表。
- AI 推荐页。
- 报名页。
- 小程序截图。
- 管理后台。
- 一张架构图。

他讲了 8 分钟，页面看起来不少，但教师问了几个问题：

1. 你的部署链接在哪里？
2. AI 推荐接口失败时会显示什么？
3. 你的活动数据存在什么表？
4. RAG 是否有失败样本？
5. 小程序版本是怎么验证的？
6. Agent 帮你改了什么，哪些地方你审批过？
7. 如果两个用户同时报名，数据会不会错？
8. 你从 reference 借鉴了什么，不是只列链接？

小哲发现自己答辩材料很"展示型"，但证据很散。页面能看，但无法证明产品可靠；技术能讲，但没有日志和测试；reference 有链接，但没有阅读范围；Agent 用了，但没有 trace。

这就是 Week 16 要纠正的方向：从 Demo 展示转向 release review。

## 2. 期末答辩的核心结构

本课程推荐 8-10 分钟答辩结构：

| 部分 | 时间 | 必讲内容 | 证据 |
|---|---|---|---|
| 产品 Demo | 2 分钟 | 用户、痛点、核心流程 | 部署链接、录屏或现场操作 |
| 技术走查 | 3 分钟 | 前端、后端、数据、AI/RAG、部署、跨平台 | 架构图、代码路径、数据库表 |
| 证据展示 | 2 分钟 | 测试日志、真实调用、RAG eval、部署链接、diff | 命令输出、截图、日志 |
| reference 借鉴 | 1 分钟 | 读了哪里、借鉴了什么、怎么简化到自己的项目 | Reference Card |
| 风险和边界 | 1 分钟 | 还不能做什么、下一步怎么补 | Risk Register |
| 问答 | 3 分钟 | 回答教师和同伴问题 | 现场追问 |

建议顺序是"先跑通，再解释，再证明"。不要先讲 5 分钟架构图，让观众还不知道产品是否能用。

```markdown
- 测试命令：
- AI 调用日志：
```

### 2.2 演示顺序

现场 Demo 可以按这个顺序：

1. 打开线上链接。
2. 说明当前用户身份。
3. 完成核心输入。
4. 展示数据写入或 AI 返回。
5. 展示一个失败或空状态。
6. 展示证据包中的对应日志或测试。

如果一开始就切到代码，观众会失去产品上下文；如果只跑页面不切代码，评委无法判断是否是全栈产品。

## 3. Final Evidence Package

最终证据包应该像一个小型 release package，而不是零散截图。

### 3.1 证据包目录建议

```text
docs/
  final-evidence/
    00-demo-script.md
    01-product-path.md
    02-architecture.md
    03-data-model.md
    04-ai-rag-eval.md
    05-auth-payment-permission.md
    06-cross-platform.md
    07-agent-trace.md
    08-reference-cards.md
    09-risk-register.md
    10-production-gap-card.md
```

学生不一定要完全照这个目录，但必须能快速找到证据。

### 3.2 证据类型

| 证据 | 必须包含 | 常见缺口 |
|---|---|---|
| 运行链接/录屏 | Web 部署地址；小程序/移动端提交录屏或真机截图 | 只能本地跑，部署链接打不开 |
| README | 安装、运行、测试、环境变量占位、核心路径说明 | 没写 env，别人无法复现 |
| 数据模型 | 表结构、关键字段、权限/RLS 或访问边界 | 只展示 UI，不知道数据如何保存 |
| AI 调用证据 | 请求路径、模型/供应商、错误处理、成本或用量记录 | 只说"接了 AI"，没有失败状态 |
| RAG eval | 至少 3 个测试问题、引用来源、失败样本和改进记录 | 只有一次成功问答截图 |
| 支付/认证/权限 | 测试模式日志、双用户权限测试、危险点说明 | 用管理员账号演示一切 |
| 跨平台证据 | Week 14 平台选择、最小版本截图、限制说明 | 只写"未来可做 App" |
| Agent 工程 | Week 15 规则、Human Gate、一次 trace | Agent 做了什么无法复盘 |
| reference 借鉴 | 至少 2 个来源，写清阅读范围和改造方式 | 只列链接，不说明借鉴点 |

如果某个能力不适用于你的产品，可以写"不适用"，但必须说明理由。例如一个纯创作辅助工具可能不需要支付；一个内部知识库可能不需要跨平台发布，但至少要有跨平台决策说明。

## 4. 产品 Demo：先证明能用

产品 Demo 不是营销展示，而是核心路径证明。

### 4.1 Demo 必须包含

1. 明确用户身份。
2. 明确输入。
3. 明确系统处理。
4. 明确输出。
5. 明确数据或 AI 证据。
6. 一个失败或空状态。

### 4.2 Demo 不应该包含

- 长时间介绍背景。
- 不停切换没有关系的页面。
- 展示未接数据的静态页面。
- 临时解释"这个其实还没接上"。
- 只展示成功截图，不展示可操作路径。

### 4.3 Demo Checklist

```markdown
## Demo Checklist

- [ ] 线上链接可打开。
- [ ] 演示账号可用。
- [ ] 核心路径 3 分钟内完成。
- [ ] 数据写入或 AI 调用可见。
- [ ] 失败/空状态可展示。
- [ ] 网络、登录、额度失败有备用说明。
- [ ] 本地录屏作为现场失败备份。
```

### 4.4 现场失败怎么办

现场失败不是灾难，不能解释才是灾难。

如果部署链接打不开，应该能展示：

- 部署平台状态。
- 最近一次构建日志。
- 本地录屏。
- 失败原因判断。

如果 AI 接口失败，应该能展示：

- 错误提示。
- 后端日志。
- mock 或录屏备份。
- 费用、额度或供应商状态说明。

如果数据库失败，应该能展示：

- 表结构。
- 权限规则。
- 最近一次查询日志。
- 是否是网络、认证、RLS 或 schema 问题。

## 5. 技术走查：让评委看见系统

技术走查要围绕产品路径，不要做技术名词堆叠。

### 5.1 五层走查

| 层 | 必讲问题 | 证据 |
|---|---|---|
| 前端 | 用户从哪里进入，状态如何变化 | 页面路径、组件、截图 |
| API | 前端调用哪个接口，如何处理错误 | route 文件、curl、日志 |
| 数据 | 数据表、字段、权限边界 | schema、ER 图、RLS |
| AI/RAG | Prompt、模型、检索、引用、失败样本 | eval、日志、引用 |
| 部署 | 线上如何运行，环境变量在哪里配置 | 部署链接、构建日志 |

### 5.2 代码走查模板

```markdown
## Code Walkthrough

### Core Path
- 用户动作：
- 前端入口：
- API route：
- 数据表：
- AI/RAG 模块：
- 返回结果：

### Error Path
- 失败条件：
- 前端提示：
- 后端日志：
- 测试或截图：
```

### 5.3 不同项目的走查重点

| 项目类型 | 走查重点 |
|---|---|
| AI 创作工具 | Prompt、模型调用、成本、失败状态、输出保存 |
| RAG 知识库 | 文档切分、索引、检索、引用、失败样本 |
| SaaS 工具 | 账号、权限、计费、数据模型、部署 |
| 小程序/移动端 | 平台入口、接口限制、登录、跨平台证据 |
| 自动化工作流 | 触发条件、任务状态、日志、人工审批 |

不要每个项目都讲同一套技术。答辩要服务你的产品。

## 6. AI 与 RAG 证据

AI/RAG 是本课程的核心能力之一。不能只展示一次漂亮回答。

### 6.1 AI 调用证据

必须说明：

- 模型供应商。
- 模型名。
- 后端调用路径。
- Prompt 或消息结构。
- 错误处理。
- 超时处理。
- 成本或用量记录。

示例：

```markdown
## AI Call Evidence

- API route：`app/api/recommend/route.ts`
- 模型：`gpt-...` 或课程可用模型
- 输入：用户兴趣、活动列表摘要
- 输出：推荐活动 + 推荐理由
- 失败处理：500 显示可重试错误
- 用量记录：记录 requestId 和 token 估算
- 不做的事：不在前端保存 API Key
```

### 6.2 RAG eval 最小要求

如果项目使用 RAG，至少准备 3 个测试问题：

| 问题 | 期望答案 | 检索来源 | 实际答案 | 结果 |
|---|---|---|---|---|
| 简单事实题 | 能从文档直接回答 | 文档 A | 正确 | 通过 |
| 组合问题 | 需要多个片段 | 文档 A+B | 部分正确 | 需改进 |
| 失败样本 | 文档没有答案 | 无 | 模型编造 | 失败记录 |

至少要有一个失败样本。没有失败样本的 eval 通常不可信。

### 6.3 RAG 失败定位

RAG 回答错了，可能是：

| 问题层 | 表现 | 处理 |
|---|---|---|
| 数据问题 | 文档本身没有答案或过期 | 更新资料、标注版本 |
| 切分问题 | 相关信息被切散 | 调整 chunk 规则 |
| 检索问题 | 没检到正确片段 | 改 query、embedding、topK |
| 生成问题 | 检到了但回答编造 | 加引用约束和拒答规则 |
| 权限问题 | 检到了不该看的文档 | 加用户权限过滤 |

答辩时如果能说出错误属于哪一层，会比只展示成功回答更有说服力。

### 6.4 Prompt 证据

Prompt 不一定要全部展示，但要说明核心约束：

```markdown
## Prompt Constraints

- 必须基于提供的活动数据回答。
- 不知道时说不知道。
- 推荐理由必须引用活动字段。
- 不输出未提供的时间和地点。
- 输出 JSON，字段包括 `activityId`、`reason`、`risk`。
```

## 7. 数据、权限、支付和隐私

不是每个项目都有支付，但每个项目都有数据和权限。

### 7.1 数据模型说明

最小数据模型说明：

```markdown
## Data Model

### `activities`
- `id`
- `title`
- `description`
- `start_time`
- `tags`

### `registrations`
- `id`
- `activity_id`
- `user_id`
- `status`
- `created_at`

### 关键关系
- 一个活动可以有多个报名。
- 一个用户可以报名多个活动。
- 报名状态不能由前端任意修改。
```

### 7.2 权限说明

必须回答：

- 普通用户能看什么？
- 管理员能看什么？
- 用户能不能看到别人的数据？
- 后端是否校验用户身份？
- 是否有双用户测试？

双用户测试示例：

```markdown
## Permission Test

- 用户 A 创建报名。
- 用户 B 登录后访问用户 A 的报名详情。
- 期望：403 或不可见。
- 实际：
- 证据：
```

### 7.3 支付说明

如果涉及支付，必须使用测试模式，并说明：

- 支付供应商。
- 测试金额。
- webhook 处理。
- 订单状态变化。
- 失败/取消状态。
- 不触发真实扣费。

如果不涉及支付，也可以写：

```markdown
本项目不包含支付，因为当前课程阶段只验证活动推荐和报名路径。后续商业化前需要补订单、支付、退款和 webhook 幂等处理。
```

### 7.4 隐私和密钥

必须说明：

- API Key 不在前端。
- `.env` 不提交。
- 用户上传文件如何处理。
- 是否使用真实用户数据。
- 是否有删除或脱敏机制。

课程项目可以简化，但不能忽略。

## 8. 跨平台证据

Week 14 的产物必须进入期末证据包。

### 8.1 跨平台决策

写清：

- 选择 PWA、小程序或移动端。
- 为什么选择。
- 为什么不选择其他平台。
- 迁移哪条路径。
- 暂不迁移哪些能力。

### 8.2 跨平台运行证据

| 平台 | 证据 |
---|---|
| PWA | 安装截图、离线截图、核心页面访问 |
| 小程序 | 开发者工具截图、接口日志、平台限制表 |
| 移动端 | 模拟器/真机截图、运行命令、权限说明 |

### 8.3 常见追问

1. 你的跨平台版本和 Web 共享同一个后端吗？
2. 如果小程序请求失败，是域名问题、登录问题还是后端问题？
3. PWA 离线时能看到哪些内容？
4. 移动端是否用了真机能力？如果没有，为什么选择 App？
5. 哪些能力仍保留在 Web？

## 9. Agent 工程证据

Week 15 的产物也必须进入期末证据包。

### 9.1 必须展示

- `AGENTS.md` 或项目规则。
- Human Gate 清单。
- Agent Team 角色表。
- MCP 工具卡。
- 一次执行 trace。
- 验证命令和结果。

### 9.2 评委会问什么

1. Agent 实际帮你做了什么？
2. 哪些操作必须人工审批？
3. 有没有工具权限边界？
4. Agent 是否修改过高风险文件？
5. trace 中的验证命令是什么？
6. 如果测试失败，团队怎么处理？

### 9.3 不合格展示

- 只展示聊天截图。
- 只说"我用了 AI 辅助开发"。
- 没有 diff。
- 没有测试。
- 没有 Human Gate。

## 10. reference 生产级差距分析

本周可以选一个生产项目做架构阅读，但不要把它当成可复制模板。

| 参考来源 | 建议阅读 | 借鉴角度 | 不要照搬 |

| `reference/repos/production-apps/cal-com/README.md` | README、`apps`/`packages` 的目录分工、`agents/README.md` 或 `specs/README.md` | 日程/协作类产品如何拆分应用、包和规格记录 | 不要求实现复杂日历同步和企业级集成 |
| `reference/repos/production-apps/dub/README.md` | README、链接/分析/计费相关模块的高层结构 | SaaS 产品如何把核心业务、数据分析、计费和部署证据分开 | 不复制商业计费和增长功能 |

```markdown
- 我的项目已做到：
- 我的项目还没有做到：
- 为什么本课程不要求直接照搬：
- 下一步最值得补的一个缺口：
```

### 10.2 如何讲差距

差距不是扣分项，隐瞒差距才是扣分项。

合格表达：

> 我参考了 Dub 的链接分析和计费边界，但我的项目只做到基础用量记录，没有做商业计费。原因是当前课程重点是验证 AI 推荐和数据路径，下一步如果商业化，应该先补订单、发票、webhook 幂等和权限审计。

不合格表达：

> 我们未来可以做成 Dub 那样。

前者有阅读、取舍和下一步；后者只是愿望。

## 11. 答辩示例：AI 校园活动助手

### 11.1 产品 Demo

学生打开部署链接，搜索"本周适合摄影社新人的活动"。系统返回活动卡片和 AI 推荐理由。学生点击报名，页面显示报名成功。

### 11.2 技术走查

- 前端：活动列表页和推荐页。
- 后端：`/api/recommend` 生成推荐，`/api/register` 写入报名。
- 数据：`activities` 和 `registrations` 两张表。
- AI：后端调用模型，根据活动摘要生成推荐理由。
- 部署：Vercel。
- 跨平台：Week 14 做了小程序最小版本。

### 11.3 证据

- `npm test -- recommend` 通过。
- 三个 RAG/推荐问题，其中一个失败样本是活动时间冲突。
- 小程序开发者工具截图。
- Agent trace 记录了错误状态修复。
- 部署链接可打开。

### 11.4 reference 借鉴

- 从 `vercel-ai-chatbot` 类项目借鉴后端 AI route 和错误状态。
- 从 `supabase` 相关资料借鉴表结构和 RLS 检查。
- 从 `cal-com` 借鉴预约/日程类产品的边界意识。

### 11.5 风险

- 没有接真实支付。
- 权限只覆盖普通用户和管理员。
- 小程序只做最小版本，没有正式发布。
- AI 推荐还没有成本控制。

这个答辩不一定功能最多，但证据链完整。

## 12. 技术评审问题库

答辩时会围绕这些问题追问。

### 12.1 产品和用户

1. 用户是谁？
2. 用户为什么需要 AI，而不是普通表单或搜索？
3. 核心路径是否能在 3 分钟内完成？
4. 当前版本最不能满足用户的地方是什么？

### 12.2 前端和交互

1. 关键页面在哪里？
2. 加载、失败、空状态如何处理？
3. 移动端是否可用？
4. 用户误操作如何恢复？

### 12.3 后端和数据

1. 哪些逻辑必须在后端？
2. 数据模型为什么这样设计？
3. 如果用户量扩大，哪个表最先出问题？
4. 权限在哪里校验？

### 12.4 AI/RAG

1. 模型调用失败时怎么办？
2. Prompt 如何约束模型？
3. RAG 的失败样本是什么？
4. 如何判断是检索问题还是生成问题？
5. 成本或用量如何控制？

### 12.5 支付、认证、权限

1. 是否有双用户测试？
2. 是否使用测试支付模式？
3. 生产密钥在哪里？
4. 用户是否能看到别人的数据？

### 12.6 跨平台和 Agent 工程

1. Week 14 为什么选择这个平台？
2. Week 15 Agent 帮了什么？
3. 哪些操作必须人工审批？
4. trace 是否包含验证证据？

### 12.7 reference 和生产差距

1. 你读了哪些 reference？
2. 借鉴了什么工程判断？
3. 为什么没有照搬？
4. 如果继续做，最值得补的缺口是什么？

## 13. 常见扣分点

| 问题 | 为什么严重 | 如何补救 |
|---|---|---|
| Demo 只展示静态页面 | 不能证明是全栈产品 | 至少展示一次数据读写或 AI 调用 |
| AI 成功一次就算完成 | 没有失败处理和可信边界 | 补错误状态、日志、失败样本 |
| RAG 只展示漂亮回答 | 无法判断检索是否有效 | 补问题集、引用、失败案例和改进 |
| reference 只列链接 | 没有体现借鉴能力 | 写阅读范围、借鉴点和改造方式 |
| 跨平台只写未来计划 | 和 Week 14 断裂 | 补最小 PWA/小程序/移动端证据或清晰决策 |
| Agent 记录只有聊天截图 | 无法审计工作流 | 补任务边界、diff、测试、Human Gate |
| 追求技术堆叠 | 宽而浅，关键路径不稳 | 选择一个最终项目 profile，交付深证据 |
| 线上打不开 | 无法证明交付 | 准备部署日志、本地录屏和修复计划 |
| 没有风险边界 | 把课程项目包装成生产系统 | 明确写出不能承诺的能力 |

## 14. 评分 Rubric

| 维度 | A 档 | B 档 | C 档 |
|---|---|---|---|
| 产品核心路径 | 线上可运行，路径清楚，有成功和失败状态 | 本地可运行，路径基本清楚 | 主要是静态展示 |
| 全栈能力 | 有前端、后端、数据和 AI/RAG 证据 | 有部分后端或 AI 证据 | 只展示 UI |
| AI/RAG 可信度 | 有 eval、失败样本、引用或日志 | 有一次成功调用 | 只说使用了 AI |
| 工程验证 | 有测试、构建、部署日志 | 有部分命令输出 | 没有验证证据 |
| 跨平台 | 有 Week 14 最小版本和限制说明 | 有截图但说明不足 | 只有未来计划 |
| Agent 工程 | 有规则、Human Gate、trace | 有规则但 trace 不完整 | 只有聊天截图 |
| reference 借鉴 | 阅读范围和改造清楚 | 有借鉴说明但不深入 | 只列链接 |
| 风险边界 | 能清楚承认未完成能力 | 有少量风险说明 | 把未完成包装成已完成 |

## 15. 答辩前 48 小时计划

### 48 小时前

- 冻结新功能。
- 确认核心路径。
- 检查部署链接。
- 整理 evidence index。
- 列出高风险问题。

### 24 小时前

- 跑完整构建和测试。
- 录制 3 分钟备用 Demo。
- 准备失败状态截图。
- 检查 README。
- 检查 API Key 和 `.env` 没有提交。

### 6 小时前

- 再次打开线上链接。
- 检查演示账号。
- 关闭无关浏览器标签。
- 准备本地备份。
- 团队排练问答。

### 答辩后

- 记录评委反馈。
- 标记 blocking 问题。
- 如果继续迭代，先补证据缺口，不急着加新功能。

## 16. 最终验收标准

- 产品能演示核心用户路径。
- 有至少一项真实后端能力：数据库、认证、文件、AI API、支付或部署。
- 有 AI/RAG 能力或明确说明为什么本产品不需要 RAG。
- 有跨平台决策或最小跨平台版本。
- 有 Agent 工程记录和 Human Gate。
- 有 reference 借鉴说明和验证证据。
- 有风险边界，不把未完成能力包装成已完成。

## 20. 评委追问回答模板

学生可以提前准备回答模板，但不能背空话。

### 20.1 当被问到"为什么这么设计数据表"

回答结构：

```text
我们的核心路径是 A，所以需要保存 B。
表 1 负责 X，表 2 负责 Y。
两者通过 Z 关联。
当前课程阶段没有拆更细，因为还没有复杂查询和权限场景。
如果继续做，最先要补的是索引/权限/审计。
```

### 20.2 当被问到"AI 失败怎么办"

回答结构：

```text
我们把失败分为三类：超时、供应商错误、无可用答案。
前端会显示可重试错误，不会一直 loading。
后端记录 requestId 和错误类型。
证据在 `docs/final-evidence/04-ai-rag-eval.md`。
当前还没做到成本自动告警，这是下一步。
```

### 20.3 当被问到"为什么没有做支付"

回答结构：

```text
本项目当前验证的是用户路径和 AI 推荐价值。
支付不属于本课程最小闭环，所以没有接真实支付。
如果商业化，下一步会补订单表、测试支付、webhook 幂等和退款状态。
我们没有把未完成的支付包装成已完成能力。
```

### 20.4 当被问到"你从 reference 学到了什么"

回答结构：

```text
我阅读了 X 的 README 和 Y 模块。
它的做法是 A。
我没有照搬代码，而是借鉴了 B 的工程判断。
在我的项目里对应改造成 C。
因为课程项目规模较小，所以没有实现 D。
```

### 20.5 当被问到"Agent 到底做了什么"

回答结构：

```text
Agent 参与的是最后一周的错误状态修复。
我们先写了任务范围和 Human Gate。
允许文件是 A、B、C。
禁止修改认证、数据库和部署配置。
trace 记录了计划、diff、测试命令和剩余风险。
最终判断由团队人工完成。
```

## 21. 评分流程建议

教师可以把评分拆成四步。

### 21.1 第一步：运行性检查

只看：

- 链接能否打开。
- 核心路径能否跑。
- 是否有本地录屏备份。
- 是否能展示失败状态。

如果运行性不成立，后面的技术讲解会大幅打折。

### 21.2 第二步：证据检查

检查 evidence index：

- 是否有测试命令。
- 是否有 AI/RAG eval。
- 是否有数据模型。
- 是否有跨平台证据。
- 是否有 Agent trace。
- 是否有风险清单。

### 21.3 第三步：技术追问

选择 3-5 个问题追问，不要问太散：

- 一个数据问题。
- 一个 AI/RAG 问题。
- 一个权限或安全问题。
- 一个 reference 问题。
- 一个风险和下一步问题。

### 21.4 第四步：复盘判断

最终判断：

- 这个项目是否有真实用户路径？
- 技术方案是否服务路径？
- 证据是否支撑结论？
- 学生是否知道边界？
- 如果继续做，下一步是否清楚？

## 22. 常见现场状况和处理

### 22.1 线上链接打不开

教师可以问：

- 最近一次部署日志在哪里？
- 本地录屏在哪里？
- 本地能否启动？
- 你判断是构建、路由、环境变量还是服务问题？

学生如果能清楚定位，仍可保留部分分数。

### 22.2 AI 接口超时

学生应展示：

- 前端错误提示。
- 后端日志。
- mock 或录屏备份。
- 失败样本记录。

不要临时刷新十次赌成功。

### 22.3 队友讲不清自己模块

团队项目要避免一个人包办答辩。每个模块 owner 至少能回答：

- 我负责什么。
- 我改了哪些文件。
- 我跑了什么验证。
- 当前风险是什么。

### 22.4 评委问到没准备的问题

合格回答不是硬编，而是：

```text
这个问题我们当前没有覆盖。根据现有架构，我判断它会影响 X。
我们目前的证据只能证明 Y，不能证明 Z。
下一步应该先补 A，再考虑 B。
```

承认边界比编造答案更好。

## 24. 从课程项目到真实产品

真实产品还需要补很多课程中没有强制要求的能力：

| 能力 | 课程项目最低要求 | 真实产品还需要 |
|---|---|---|
| 认证 | 演示账号或基础登录 | 密码重置、OAuth、安全审计 |
| 数据 | 基础表和读写 | 备份、迁移、索引、监控 |
| AI | 可调用和错误状态 | 成本控制、质量监控、abuse 防护 |
| RAG | 小样本 eval | 持续评测、权限过滤、文档版本 |
| 支付 | 测试模式说明 | 退款、发票、对账、风控 |
| 部署 | 可访问链接 | 监控、告警、回滚、日志 |
| 跨平台 | 最小版本 | 发布审核、版本管理、灰度 |

学生不需要在课程里完成全部真实产品能力，但需要知道差距在哪里。

## 25. 课堂组织建议

如果是多人班级，可以把 Week 16 分成三段：

1. 快速 Demo：每组 3 分钟，只跑核心路径。
2. 技术评审：每组 5 分钟，教师和同伴追问。
3. 复盘提交：每组根据追问补 final evidence。

教师评分时不要只看现场演示是否顺利。更重要的是：

- 失败时是否知道怎么定位。
- 证据是否能支撑结论。
- 学生是否能承认边界。
- 技术选择是否服务产品。

### 25.1 教师评分记录模板

教师可以在每组答辩时使用下面模板，避免评分只凭现场印象。

```markdown
## Defense Review Record

- 小组：
- 产品名称：
- 核心用户：
- 核心路径是否跑通：是 / 否 / 部分
- 线上链接是否可打开：是 / 否 / 本地备份
- AI/RAG 证据：充分 / 部分 / 不足
- 数据和权限证据：充分 / 部分 / 不足
- 跨平台证据：充分 / 部分 / 不适用
- Agent 工程证据：充分 / 部分 / 不足
- reference 借鉴：清楚 / 一般 / 只列链接
- 最大风险：
- 最值得肯定的取舍：
- 必须补交的证据：
- 建议成绩档位：
```

### 25.2 同伴提问模板

同伴提问不要只问"你用了什么技术"，可以按下面结构：

```markdown
## Peer Review Question

- 我看到你们的核心路径是：
- 我想追问的风险是：
- 我希望你们展示的证据是：
- 如果继续迭代，我建议先补：
```

同伴评审的目标不是挑刺，而是帮助项目暴露真实边界。一个好的问题应该让答辩者展示证据，而不是逼对方背概念。

### 25.3 答辩后的补交规则

如果现场演示失败，但项目本身有修复空间，可以允许补交一次证据包。补交不应该新增功能，只能补：

- 部署日志。
- 修复后的核心路径录屏。
- 失败原因说明。
- 测试或构建命令。
- 风险边界更新。

补交不能把一个未完成产品包装成完成产品。它只能证明现场失败是否属于部署、网络、配置或演示事故。

## 26. 本周回顾

期末答辩不是让学生证明自己"什么都会"，而是证明自己能把一个产品问题、一个技术方案、一组工程证据和一套风险边界讲清楚。Course B 的最终目标不是技术名词的数量，而是学生能用成熟项目作为参照，做出有取舍、能运行、可复盘的 AI 全栈产品。

一个好的期末项目不一定功能最多，但它必须真实：真实路径、真实数据、真实 AI 调用或明确 mock 边界、真实失败记录、真实验证命令、真实风险说明。

如果学生能在 Week 16 清楚回答"我做到了什么、证据在哪里、还没做到什么、下一步为什么这样做"，这门课的目标就达到了。

## 27. 课程结束后的下一步

课程结束不是项目结束。建议学生把项目分成三类后续路线：

| 路线 | 适合项目 | 下一步 |
|---|---|---|
| 作品集路线 | Demo 完整、用户价值清楚 | 补 README、录屏、技术博客 |
| 创业验证路线 | 有真实用户和场景 | 做用户访谈、成本估算、付费测试 |
| 工程深挖路线 | 技术挑战明显 | 补测试、权限、部署、性能和监控 |

不要在课程结束后马上堆新功能。先把证据包整理成可公开、可复盘、可继续迭代的项目资产。
