## 实验目标

1. 能为期末项目写出具体、可执行的 AI 协作规则。
2. 能设计小型 Agent Team，并明确每个角色的输入、输出和禁止事项。
3. 能识别必须人工审批的危险操作。
4. 能记录一次 AI 辅助交付 trace，并用 diff、测试、日志证明结果。

## 实验任务

为你的期末项目建立 Agent 工程交付规程，并用一次小任务验证它。任务可以是修复 bug、补测试、整理 README、改进错误状态、补充安全检查或优化 RAG eval。

必须提交：

- `AGENTS.md` 或等价规则文件。
- Agent Team 角色表。
- Human Gate 清单。
- MCP 或工具权限说明。
- 一次真实执行 trace。
- 安全检查表和测试日志。

## 操作步骤

### 第一步：盘点项目风险

列出本项目中的危险区域：

| 风险区域 | 示例 | 是否需要 Human Gate |
|---|---|---|
| 认证和权限 | 登录、RLS、session |  |
| 支付和订单 | webhook、price ID、订单状态 |  |
| AI 调用 | API Key、成本、提示词注入 |  |
| RAG 知识库 | 内部资料、过期文档 |  |
| 部署配置 | 环境变量、域名、生产数据库 |  |
| 用户数据 | 隐私、文件上传、导出 |  |

### 第二步：编写规则文件

在项目根目录或报告中准备 `AGENTS.md` 草案。若课程或仓库不允许提交到根目录，本实验只提交到报告材料中。

规则必须具体，例如：

```markdown
# 项目 AI 协作规则

- 修改前必须先读取相关文件和当前 diff。
- 不得提交 API Key、Token、密码或生产环境变量。
- 修改认证、支付、RLS、webhook、数据库迁移前必须人工审批。
- 每次改动后必须提供运行命令、测试日志和失败说明。
- AI 不能把失败测试改成通过，也不能删除验收标准。
```

不要只写“保证代码质量”“注意安全”这类无法执行的句子。

### 第三步：设计 Agent Team

角色不超过 4 个：

| 角色 | 输入 | 输出 | 不能做什么 |
|---|---|---|---|
| Planner | 需求、代码状态、限制 | 小步计划和验收标准 | 不能直接改代码 |
| Coder | 已审批计划、写入范围 | diff 和实现说明 | 不能改密钥、账单、生产配置 |
| Tester | 测试命令、验收标准 | 测试日志和失败分析 | 不能跳过失败 |
| Reviewer | diff、日志、需求 | 风险清单和通过建议 | 不能代替人类最终批准 |

如果使用真实 Agent 工具，保留 trace。若没有工具，可以用人工模拟表记录每个角色的输入和输出。

### 第四步：设计 MCP 和工具权限

列出工具权限边界：

| 工具或 MCP | 允许用途 | 禁止用途 | 审批要求 |
|---|---|---|---|
| 文件系统 | 读取项目、修改指定文件 | 读取密钥文件、批量删除 | 大范围修改前审批 |
| Git | 查看 diff、提交记录 | reset hard、覆盖他人改动 | 破坏性操作审批 |
| 数据库 | 查询测试数据 | 修改生产数据 | 写操作审批 |
| 浏览器 | 验证页面和截图 | 输入真实隐私信息 | 涉及账号审批 |
| AI API | 测试功能 | 暴露 Key、无限调用 | 成本和密钥审批 |

### 第五步：执行一次真实任务

选择一个小任务，并记录 trace：

| 阶段 | 记录内容 |
|---|---|
| 需求 | 本次任务是什么，写入范围是什么 |
| 计划 | AI 或人工给出的步骤 |
| 审批 | 人是否批准，是否修改计划 |
| 执行 | 修改了哪些文件或配置 |
| 验证 | 运行了什么命令，结果如何 |
| 审查 | diff 中有哪些风险，是否通过 |

如果任务没有产生代码 diff，也可以提交文档 diff、配置 diff、测试日志或评测表变化。

### 第六步：完成安全与复盘

回答：

1. 这次 AI 帮你节省了什么？
2. 哪些地方必须人工判断？
3. 哪条规则在本次任务中最有用？
4. 还有哪些规则需要补充？

## 提交要求

1. `AGENTS.md` 或规则文件草案。
2. Agent Team 角色表。
3. Human Gate 清单。
4. MCP 或工具权限说明。
5. 一次执行 trace。
6. diff、测试日志、评测表或演示截图。
7. 安全检查表。
8. 如果未使用真实 Agent 工具，提交人工模拟 trace 和限制说明。

## 验收标准

- 规则具体可执行，包含禁止事项和验证要求。
- Agent 角色少而清晰，不互相重叠。
- Human Gate 覆盖认证、支付、权限、密钥、部署、数据等危险操作。
- trace 能说明 AI 做了什么、人审批了什么、如何验证。
- 有 diff、日志、截图、eval sheet 或技术报告作为证据。
- 没有要求 AI 绕过测试、隐藏失败或覆盖他人改动。

## 常见问题

**一定要真的接 MCP 吗？**

不强制。可以设计 MCP 工具权限表。若已经使用 MCP，则提交工具清单、用途和风险边界。

**没有 Agent Team 工具怎么办？**

用表格模拟 Planner、Coder、Tester、Reviewer 的交接即可。重点是角色边界和审批证据。

**规则文件必须放进项目根目录吗？**

如果你的项目允许，建议放入根目录。如果当前仓库或作业限制不允许，提交到实验报告中也可以。

**执行 trace 必须是大功能吗？**

不需要。越接近期末交付的小任务越好，例如补 README、修复一个表单错误、补一条 RAG 评测。

## 评分标准

| 维度 | 分值 | 说明 |
|---|---:|---|
| 规则质量 | 25 分 | 具体、可执行，覆盖验证和禁止事项 |
| Agent Team 设计 | 20 分 | 角色边界清楚，输入输出明确 |
| Human Gate 与工具权限 | 25 分 | 危险操作识别完整，审批要求合理 |
| 执行 trace | 20 分 | 有计划、审批、diff 或日志、验证和审查 |
| 提交规范 | 10 分 | 材料完整，证据命名清晰 |
