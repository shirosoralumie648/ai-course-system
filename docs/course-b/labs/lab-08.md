## 实验目标

让 AI 从“会聊天”变成“懂你的业务资料”。实验结束时，你应有一个 Dify 知识库应用，一份可审查的召回测试记录，以及一个通过后端代理调用 Dify API 的产品页面。

## 实验任务

选择与你的项目相关的资料，搭建 Dify 知识库助手。资料可以是：

- 产品说明
- 退款或服务政策
- 课程资料
- FAQ
- 操作手册
- 你自己写的项目文档

不要上传无关资料凑数。知识库必须服务你的产品或课程项目。

## 操作步骤

### 1. 整理知识库资料

准备 3-5 份短文档，或 1 份结构清楚的长文档。每份资料需要有标题、来源、更新时间和用途说明。

整理测试问题：

- 5 个应该能从文档中回答的问题
- 2 个文档没有答案的问题
- 2 个容易混淆或需要精确引用的问题

### 2. 创建 Dify 知识库

在 Dify 中创建知识库，上传资料并配置：

- 文档切分方式
- Embedding 模型
- 检索参数
- 是否启用 rerank

保存上传完成和知识库配置截图。

### 3. 创建对话应用并挂载知识库

创建 Dify 对话应用，挂载知识库，并设置系统提示词。提示词应要求：

- 优先依据知识库回答
- 找不到资料时明确说不知道
- 不编造政策、价格或承诺
- 必要时引用资料标题或片段

保存应用配置截图。

### 4. 做召回测试

用准备好的问题逐条测试。记录：

| 问题 | 预期资料 | 是否命中 | 回答是否准确 | 备注 |
|---|---|---|---|---|
| 退款期限是多久 | refund-policy.md | 是 | 是 | 引用了正确条款 |
| 是否支持企业发票 | 无 | 否 | 是 | 正确说明资料中没有 |

至少包含 9 条测试，其中至少 2 条失败或不足样本，并写出改进计划。

### 5. 发布 API 并安全对接产品

在 Dify 中发布 API。不要把 Dify API Key 写进前端。正确链路：

1. 前端请求你的后端 `/api/dify-chat`
2. 后端从环境变量读取 `DIFY_API_KEY`
3. 后端调用 Dify API
4. 前端展示回答

保存浏览器 Network 截图，证明前端只调用自己的后端。

### 6. 整理平台 RAG 复盘

写 200-400 字说明：

- Dify 平台帮你省掉了哪些底层工作
- 哪些检索问题仍然需要人工调参
- 知识库资料质量如何影响回答
- API Key 为什么不能放前端

## 提交要求

- 知识库资料清单
- Dify 知识库配置截图
- Dify 应用配置截图
- 召回测试表，至少 9 条
- 至少 2 条失败或不足样本及改进计划
- API 对接页面截图
- 后端代理代码 diff
- API 日志或 Dify 调用日志
- 浏览器 Network 截图
- 密钥检查记录，禁止提交真实 Dify API Key

## 验收标准

- 知识库资料和产品场景相关
- Dify 应用能回答至少 5 个业务问题
- 召回测试包含成功、失败和无答案样本
- API 对接通过后端代理完成
- 前端代码和 Network 中看不到 Dify API Key
- 复盘能说明平台 RAG 的优势和限制

## 常见问题

**知识库资料可以很少吗？**
可以少，但要结构清楚。资料太少时必须设计更精准的问题，不能用泛泛聊天代替召回测试。

**Dify 回答错了怎么办？**
这正是实验重点。记录失败样本，分析是资料缺失、切分不当、检索参数问题，还是提示词没有约束好。

**可以只在 Dify 页面测试，不接入自己的产品吗？**
不可以。验收要求至少有一个通过后端代理调用 Dify API 的页面。

## 评分标准

| 维度 | 分值 | 说明 |
|---|---:|---|

| 应用配置 | 15 | 提示词和知识库挂载是否合理 |
| 召回测试 | 30 | 测试样本是否覆盖成功、失败、无答案 |
| API 对接安全 | 20 | 是否通过后端代理，密钥是否安全 |
| 复盘证据 | 10 | 截图、日志、改进计划是否完整 |
