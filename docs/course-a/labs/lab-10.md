## 实验目标

完成本实验后，你应该能够：

1. 解释一个 Skill 适合解决什么重复问题。
2. 编写包含名称、描述、使用场景、执行步骤和注意事项的 `SKILL.md`。
3. 用自然语言触发 Skill，并观察 Claude Code 是否按规则行动。
4. 根据测试结果修订 Skill，而不是一次写完就不再检查。

## 实验任务

为你的产品原型创建一个项目 Skill。这个 Skill 应该帮助 Claude Code 更稳定地完成一个常见任务。

可选方向：

| Skill 类型 | 示例 |
|---|---|
| 页面检查 | 检查页面文案是否清楚、按钮是否有明确动作 |
| 提交前检查 | 检查是否遗漏验证记录、截图、变更说明 |
| 原型迭代 | 按“需求、限制、改动、验证”的顺序推进小功能 |
| 课程资料整理 | 把杂乱笔记整理成统一格式 |
| 用户反馈处理 | 把访谈记录整理成问题清单和下一步改进 |

## 操作步骤

### 第一步：选择一个重复任务

回顾你最近三次使用 Claude Code 的经历，找一个你反复解释过的要求。

记录格式：

```markdown
重复任务名称：
为什么重复：
以前每次都要解释哪些要求：
如果做成 Skill，希望 Claude Code 自动遵守什么：
```

### 第二步：提炼任务规则

把任务规则写成“必须做”和“不要做”两类。

示例：

| 类型 | 规则 |
|---|---|
| 必须做 | 开始前先确认目标用户和页面位置 |
| 必须做 | 改完后给出人工检查清单 |
| 不要做 | 不要一次改多个无关页面 |
| 不要做 | 不要把没有验证的内容写成确定结论 |

### 第三步：编写 `SKILL.md`

在实验文档中写出完整 `SKILL.md` 内容。你可以按下面模板改写：

```markdown
---
name: prototype-review
description: 当需要检查产品原型页面的清晰度、可用性和提交证据时使用
---

# 产品原型检查 Skill

## 使用场景

当用户要求检查页面、准备提交、整理反馈或确认原型是否可演示时使用。

## 执行步骤

1. 先确认页面目标用户、核心任务和本次检查范围。
2. 阅读相关页面或截图，列出用户必须完成的动作。
3. 从文案、布局、交互反馈、验证证据四个角度检查。
4. 只提出和本次范围相关的问题。
5. 输出“必须修改”“建议修改”“可以保留”三类结果。

## 注意事项

- 不要因为个人审美偏好提出大范围重做。
- 不要改动未被用户授权的文件。
- 发现无法验证的地方，要明确写成“需要人工确认”。
```

如果你的环境不方便真正安装 Skill，也可以提交“项目 Skill 草案”，但必须完成触发测试。

### 第四步：设计触发测试

准备两个 Prompt：

1. 不提 Skill，只让 Claude Code 完成任务。
2. 明确要求使用你写的 Skill 完成同一任务。

示例：

```text
测试 A：请帮我检查这个反馈页面有没有明显问题。
测试 B：请使用 prototype-review 这个 Skill，帮我检查这个反馈页面有没有明显问题。
```

保存两次输出，不要只保存你喜欢的版本。

### 第五步：对比使用前后

用表格比较 Skill 是否带来改善：

| 对比维度 | 未使用 Skill | 使用 Skill |
|---|---|---|
| 是否先确认范围 | | |
| 是否按固定步骤检查 | | |
| 是否给出可执行建议 | | |
| 是否提醒人工验证 | | |
| 是否避免越权修改 | | |

### 第六步：修订 Skill

根据对比结果至少修改一次 `SKILL.md`。常见修订方向：

- 描述太模糊，Claude Code 不容易自动触发
- 步骤太多，执行时容易跳过
- 限制不清楚，导致建议超出任务范围
- 输出格式不固定，难以检查

记录“修改前、修改后、修改原因”。

## 提交要求

1. 重复任务说明。
2. 任务规则表。
3. 完整 `SKILL.md`。
4. 两个触发测试 Prompt。
5. 未使用 Skill 和使用 Skill 的输出记录。
6. 使用前后对比表。
7. 至少一次 Skill 修订记录。
8. 复盘：这个 Skill 以后最适合在什么场景使用。

## 验收标准

- `SKILL.md` 有完整 frontmatter，包含 `name` 和 `description`。
- Skill 步骤具体，能指导 Claude Code 行动。
- 有未使用和使用 Skill 的对比证据。
- 修订记录不是简单改错别字，而是基于测试结果优化。
- 输出能体现项目知识沉淀，而不是普通 Prompt 的复制粘贴。

## 常见问题

### Skill 和 Prompt 有什么区别？

Prompt 是一次性说明，Skill 是可复用的说明书。只要某类任务会重复出现，就值得考虑写成 Skill。

### 我的 Skill 很短，会不会不合格？

不会。短但清楚的 Skill 比长而空泛的 Skill 更有价值。关键是能稳定改变 Claude Code 的行为。

### 没有安装成功怎么办？

提交 Skill 草案和模拟触发测试也可以，但要记录你遇到的安装或路径问题，并说明下一步如何解决。

## 评分标准

| 维度 | 分值 | 说明 |
|---|---:|---|
| 重复任务选择 | 15 分 | 问题真实，适合沉淀为 Skill |
| `SKILL.md` 完整性 | 25 分 | 字段、场景、步骤、限制完整 |
| 触发测试设计 | 15 分 | 两次测试任务一致，便于比较 |
| 对比分析 | 20 分 | 能用证据说明 Skill 是否有效 |
| 修订质量 | 15 分 | 根据测试结果做实质优化 |
| 复盘 | 10 分 | 能说明后续使用场景和边界 |
