## 实验目标

- 学会用任务观察收集反馈，而不是只问「好不好用」。
- 识别 Demo 到产品之间的体验缺口：等待、失败、空状态、数据保存、误操作。
- 基于反馈完成一次有证据的产品迭代。
- 整理一个可以课堂展示的完整原型包。

## 实验任务

邀请 3 位接近目标用户的人试用你的原型。你要给他们一个明确任务，观察他们能否独立完成，并记录卡住的位置。然后从反馈中选择 2-3 个问题完成迭代。

## 操作步骤

### 第一步：准备可试用版本

在邀请用户前，先自己跑一遍核心流程：

| 检查项 | 是否完成 |
|---|---|
| 页面能打开 |
| 核心按钮能点击 |
| 输入为空时有提示 |
| 生成或模拟结果能显示 |
| 出错时不白屏 |
| 页面没有明显测试占位内容 |

如果页面还有「测试数据 1」「按钮」「Untitled」这类占位内容，先改成真实业务语境。

### 第二步：设计用户试用任务

不要让用户随便点。给一个具体任务：

```text
请你把这段课程资料粘贴进去，尝试生成一份考前复习重点。
完成后告诉我：你是否愿意把这份结果继续保存或复制给同学。
```

任务必须包含：

- 用户要输入或选择什么。
- 用户要点击什么。
- 用户应该得到什么结果。
- 你观察什么行为。

### 第三步：收集 3 位用户反馈

每位用户记录：

| 用户 | 是否独立完成 | 卡住的位置 | 用户原话 | 你观察到的行为 | 严重程度 |
|---|---|---|---|---|---|
| U1 | | | | | |

严重程度建议：

- P0：无法继续使用，必须修。
- P1：能完成但明显困惑，本轮优先修。
- P2：体验建议，可以后续优化。

### 第四步：整理反馈优先级

把所有反馈合并成问题池：

| 问题 | 出现次数 | 严重程度 | 修复成本 | 本轮是否修 | 理由 |
|---|---:|---|---|---|---|
| 点击后不知道是否在生成 | 2 | P1 | 低 | 是 | 加 loading 即可 |
| 想登录同步数据 | 1 | P2 | 高 | 否 | 超出本阶段范围 |

本轮至少选择 2 个问题修复，最多 3 个。不要把所有建议都塞进去。

### 第五步：用 AI 协助迭代

把问题池发给 AI，让它先给修复计划：

```text
这是 3 位用户试用后的反馈表。请帮我选择本轮最应该修的 2-3 个问题。
限制：
1. 不新增复杂后端
2. 不做登录和支付
3. 优先修复影响核心流程的问题
4. 请先说明计划，再修改文件
```

执行后保存：

- 修改前截图。
- 修改后截图。
- 文件变化摘要或 diff。
- 再次自测结果。

### 第六步：完成最终验收

用「最终演示脚本」测试原型：

```text
1. 打开页面，说明目标用户和问题
2. 输入一段真实或接近真实的数据
3. 点击核心按钮
4. 展示等待、结果、保存或复制
5. 演示一个错误或空输入提示
6. 说明根据用户反馈修了什么
```

录屏可选，但至少要提交完整截图序列。

## 提交要求

提交以下内容：

1. `lab-08-report.md`：实验报告。
2. 最终原型项目文件、运行链接或本地运行说明。
3. 3 位用户反馈记录。
4. 反馈优先级表。
5. 2-3 个修复项的前后对比截图。
6. 文件变化摘要或 diff。
7. 最终验收清单。
8. 课堂演示用的 1 分钟说明稿。

## 验收标准

- 用户反馈来自真实试用，而不是自己想象。
- 至少 3 位用户，每位都有任务结果和卡点记录。
- 本轮修复项来自反馈优先级表。
- 最终原型能完成核心流程，并处理至少一种异常情况。
- 提交材料能清楚展示「迭代前」和「迭代后」的差异。

## 常见问题

**Q：用户提了很多大需求，我都要做吗？**
A：不用。优先修复阻碍核心流程的问题。登录、支付、社交分享等大功能可以记录为后续计划。

**Q：用户没有反馈怎么办？**
A：不要只问感受。让用户当场完成任务，观察他停顿、重复点击、问你的地方，这些就是反馈。

**Q：可以找同学互测吗？**
A：可以，但要尽量找接近目标用户的人，并记录他们是否真的遇到过这个场景。

| 迭代完成度 | 25 分 | 修复 2-3 个关键问题并有证据 |
| 最终原型可用性 | 20 分 | 核心流程顺畅，异常提示基本完整 |
| 展示材料 | 10 分 | 报告、截图、说明稿齐全 |
