## 实验目标

完成本实验后，你应该能够：

1. 判断一个项目是否真的需要 MCP。
2. 区分本地 STDIO、远程 HTTP 等常见连接方式。
3. 写出不泄露敏感信息的 MCP 配置草案。
4. 为 MCP 服务设计基本验证和故障排查步骤。

## 实验任务

围绕你的产品原型，设计一个 MCP 服务器配置方案。你可以真的配置，也可以只提交安全的配置草案。

推荐选择以下低风险场景：

| 场景 | 适合连接的能力 | 实验重点 |
|---|---|---|
| GitHub 项目管理 | 查看 Issue、整理 PR 说明 | token 权限和只读边界 |
| SQLite 数据查看 | 查询本地测试数据 | 数据路径和查询记录 |
| 浏览器检查 | 打开页面、截图、检查布局 | 验证页面是否可访问 |
| 文件资料库 | 读取指定资料目录 | 路径限制和隐私保护 |

不要在实验提交中写入真实 token、真实密码或个人隐私数据。

## 操作步骤

### 第一步：选择 MCP 场景

写清楚你为什么需要这个 MCP，而不是只说“想试试”。

```markdown
项目：
当前痛点：
选择的 MCP 场景：
希望 Claude Code 多出什么能力：
不用 MCP 时的替代办法：
```

### 第二步：说明工具价值和边界

用表格说明这个 MCP 能做什么、不能做什么。

| 项目 | 内容 |
|---|---|
| 允许做 | 例如读取 Issue 标题、列出本地测试数据 |
| 不允许做 | 例如删除仓库、修改生产数据、读取私人目录 |
| 人工确认点 | 例如创建 PR 前必须人工确认说明 |
| 成功证据 | 例如能列出测试数据表，或能返回页面截图 |

### 第三步：编写 MCP 配置草案

根据你的场景写一份项目级配置草案。以下示例只用于说明结构，请按你的场景修改：

```json
{
  "mcpServers": {
    "project-notes": {
      "command": "npx",
      "args": ["-y", "@example/filesystem-mcp@1.0.0", "./docs"],
      "env": {
        "ACCESS_MODE": "read_only"
      }
    }
  }
}
```

如果涉及 token，用环境变量占位：

```json
{
  "mcpServers": {
    "github-readonly": {
      "command": "npx",
      "args": ["-y", "@example/github-mcp@1.0.0"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
```

配置草案后面必须写字段解释：

| 字段 | 作用 | 风险 |
|---|---|---|
| `command` | 启动 MCP 服务的命令 | 命令来源不可信可能有风险 |
| `args` | 指定包名、版本、路径 | 版本不固定可能导致行为变化 |
| `env` | 传入环境变量 | 不要写真实密钥 |

### 第四步：做安全检查

完成以下检查表：

| 检查项 | 结果 | 说明 |
|---|---|---|
| 没有提交真实 token | | |
| 权限范围最小化 | | |
| 路径限制明确 | | |
| 版本有固定或说明 | | |
| 知道如何停用该 MCP | | |
| 敏感数据不会进入实验材料 | | |

### 第五步：设计验证问题

准备 3 个自然语言验证问题，用于确认 MCP 是否可用。

示例：

```text
请列出当前已配置的 MCP 服务器，并说明每个服务器的用途。
请检查 project-notes 是否只能读取 docs 目录。
请用 project-notes 读取课程资料目录，并返回文件清单，不要修改任何文件。
```

每个问题后面写出你期望看到的结果。

### 第六步：整理诊断记录

如果你实际配置了 MCP，记录连接或诊断过程。如果没有实际配置，也要写“模拟诊断流程”。

诊断记录模板：

```markdown
诊断目标：
我给 Claude Code 的问题：
返回结果或预期结果：
我如何判断是否成功：
如果失败，下一步检查：
```

## 提交要求

1. MCP 场景选择说明。
2. 工具价值和边界表。
3. MCP 配置草案，不能包含真实密钥。
4. 字段解释表。
5. 安全检查表。
6. 3 个自然语言验证问题和期望结果。
7. 实际或模拟诊断记录。
8. 复盘：这个 MCP 是否值得接入你的项目。

## 验收标准

- 配置草案结构完整，能看出服务器名称、启动方式和环境变量。
- 能明确说明为什么选择这个 MCP。
- 安全检查不流于形式，能指出具体风险。
- 验证问题可执行，能帮助判断 MCP 是否连接成功。
- 提交材料中没有真实 token、密码、个人隐私或生产数据。

## 常见问题

### 我没有真实 GitHub token，可以做吗？

可以。使用环境变量占位，重点是配置结构、权限边界和验证方案。

### MCP 配置失败会扣分吗？

不会。只要你记录了失败现象、排查步骤和下一步计划，失败也是有效证据。

### 能不能直接复制网上配置？

可以参考，但必须改成你的项目场景，并解释每个字段。无法解释的配置不要提交。
