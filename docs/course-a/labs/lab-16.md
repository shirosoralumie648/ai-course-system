## 实验目标

完成本实验后，你应该能够：

1. 判断一个任务是否适合 Agent Teams，而不是盲目并行。
2. 为多个 Agent 设计清晰的角色和边界。
3. 用任务板、接口文档和消息记录管理协作。
4. 通过同伴评审发现分工冲突、遗漏和验收风险。

## 实验任务

围绕你的课程最终项目，设计一个 Agent Team 协作方案。你不需要真的启动多个 Agent，但要提交可执行的分工和协作证据。

适合的最终项目任务：

| 项目类型 | 可拆分任务 |
|---|---|
| 学习平台原型 | 课程页、学习记录、反馈表、提交说明 |
| 活动报名系统 | 活动列表、报名表、确认页、管理员视图 |
| 资料管理工具 | 上传说明、标签筛选、详情页、空状态 |
| 校园服务原型 | 需求调研、页面流程、文案检查、演示材料 |

## 操作步骤

### 第一步：判断是否适合 Agent Team

填写判断表：

| 判断问题 | 回答 |
|---|---|
| 任务是否能拆成相对独立模块 | |
| 模块之间是否有清晰接口 | |
| 是否需要并行推进 | |
| 是否存在文件或职责冲突 | |
| 单人 Claude Code 是否已经足够 | |
| 使用 Agent Team 的主要收益 | |

如果任务不能拆分，说明为什么不适合，并选择一个更合适的任务重新设计。

### 第二步：拆分 Agent 角色

至少设计 4 个角色：

| 角色 | 负责内容 | 输入 | 输出 | 不负责 |
|---|---|---|---|---|
| Team Lead | 统一任务、接口和验收 | 项目目标 | 总计划和整合检查 | 直接包办所有实现 |
| Research Agent | 整理用户需求和参考资料 | 访谈记录、课程要求 | 需求摘要 | 编写最终代码 |
| UI Agent | 设计页面结构和文案 | 需求摘要 | 页面草案和文案 | 修改数据逻辑 |
| QA Agent | 检查验收标准和风险 | Spec、页面草案 | 问题清单 | 自行扩大范围 |

你可以根据项目增加 Data Agent、Docs Agent、Demo Agent 等角色。

### 第三步：设计共享任务板

创建一个任务板，至少包含 8 张任务卡。每张卡包含：

- 卡片编号
- 负责人
- 输入
- 输出
- 状态
- 验收标准

示例：

| 编号 | 负责人 | 任务 | 输入 | 输出 | 状态 | 验收标准 |
|---|---|---|---|---|---|---|
| T1 | Research Agent | 整理目标用户问题 | 访谈记录 | 需求摘要 | 待开始 | 至少 5 条用户问题，有证据来源 |
| T2 | UI Agent | 设计首页信息结构 | 需求摘要 | 首页结构草案 | 待开始 | 覆盖核心用户路径 |

### 第四步：定义交付接口

Agent Teams 最容易出问题的地方是“你以为我会做，我以为你会给”。因此必须写接口文档。

接口模板：

```markdown
## Research Agent 交付给 UI Agent

交付物：需求摘要
格式：Markdown 表格
必须包含：用户类型、问题、证据、优先级
交付时间：UI Agent 开始页面设计前
验收人：Team Lead
如果缺失：UI Agent 不开始设计，退回补充
```

至少写 3 个角色之间的交付接口。

### 第五步：模拟协作消息

写一段不少于 6 条的 Agent Team 消息记录，展示角色之间如何协作。

消息格式：

```markdown
[Team Lead] 请 Research Agent 先提交需求摘要，UI Agent 暂停页面设计，等待输入。
[Research Agent] 已提交需求摘要，但第 3 条用户问题缺少证据来源，需要人工确认。
[QA Agent] 注意：当前验收标准缺少移动端检查。
```

消息要体现协作、阻塞、确认和评审，不要写成每个人各干各的。

### 第六步：完成同伴评审

找一位同学评审你的 Agent Team 方案。让对方回答：

1. 哪个角色职责不清楚？
2. 哪两张任务卡可能冲突？
3. 哪个交付接口最容易遗漏信息？
4. 验收标准是否足够判断完成？
5. 如果只能保留 3 个 Agent，建议保留谁？

记录同伴反馈，并写出你采纳了哪些修改。

## 提交要求

1. 最终项目任务说明。
2. Agent Team 适用性判断表。
3. 至少 4 个 Agent 角色分工表。
4. 至少 8 张任务卡的共享任务板。
5. 至少 3 个交付接口文档。
6. 不少于 6 条模拟协作消息。
7. 同伴评审记录和修改说明。
8. 复盘：Agent Teams 适合你项目的哪一部分，不适合哪一部分。

## 验收标准

- 任务确实能拆分，不是为了使用 Agent Team 而强行拆分。
- 每个角色都有明确输入、输出和不负责事项。
- 任务板能看出状态、负责人和验收标准。
- 交付接口能减少角色之间的误解。
- 模拟消息体现真实协作和阻塞处理。
- 同伴评审有具体反馈，并至少采纳 2 条修改。

## 常见问题

### 我没有同学一起做怎么办？

可以请同学只评审文档，不需要参与实现。也可以让老师或助教代为评审。

### Agent 越多是不是越好？

不是。Agent 多了会增加沟通成本。非 CS 项目通常 4 到 5 个角色就足够练习分工。

### 能不能只写分工，不写消息记录？

不可以。Agent Teams 的重点是协作，消息记录能暴露接口不清、阻塞和验收遗漏。

## 评分标准

| 维度 | 分值 | 说明 |
|---|---:|---|
| 适用性判断 | 10 分 | 能说明为什么适合或不适合多 Agent |
| 角色分工 | 20 分 | 至少 4 个角色，输入输出边界清楚 |
| 任务板 | 20 分 | 至少 8 张任务卡，有状态和验收标准 |
| 交付接口 | 20 分 | 至少 3 个接口，格式和缺失处理清楚 |
| 协作消息 | 15 分 | 不少于 6 条，体现阻塞和评审 |
| 同伴评审与复盘 | 15 分 | 有具体反馈和修改说明 |
