# Part 2
## 60 秒做出第一个贪吃蛇

---

# 工具准备

打开 [z.ai](https://chat.z.ai/)

**什么是 z.ai？**
- 智谱 AI 开发的 AI 平台
- 核心能力：GLM 系列大模型
- 集成功能：幻灯片、海报、全栈开发
- **我们用**：全栈开发模块（网页上直接生成可运行代码）

---

# 用一句话生成游戏

在 z.ai 输入框中输入：

```
帮我做一个贪吃蛇游戏：
1. 用方向键控制蛇的移动
2. 吃到食物后蛇会变长，分数增加
3. 撞到墙壁或自己的身体就游戏结束
4. 要有开始和重新开始按钮
5. 界面要简洁好看
```

然后点击「全栈开发」按钮

---

# 震撼时刻

**30 秒后**：
- AI 生成了完整的 HTML、CSS、JavaScript 代码
- 右侧预览窗口直接显示可玩的游戏
- 你可以立即用方向键控制蛇移动

**小林的感受**：
> "我只是说了我想要什么，AI 就帮我做出来了。这种感觉太神奇了！"

---

# 这就是「对话式编程」

**传统编程**：
```javascript
function moveSnake() {
  // 你需要写 50 行代码
}
```

**AI 编程**：
```
"让蛇每 100 毫秒移动一次"
```

**核心区别**：你负责「想」，AI 负责「做」

# Part 3
## AI 原生实战：打造会写诗的贪吃蛇

---

# 什么是「AI 原生」？

**传统应用**：功能固定，逻辑写死
**AI 原生应用**：核心能力由 AI 提供，能理解、生成、创造

**今天的目标**：
让贪吃蛇不只是吃食物，还能：
1. 吃单词
2. 根据单词写诗
3. 根据诗歌画画

---

# 第一步：基础版贪吃蛇

**已经完成**（60 秒挑战）
- 用方向键控制
- 吃食物变长
- 撞墙游戏结束

**接下来**：让它变得更有趣

---

# 第二步：让蛇吃单词

**对 AI 说**：
```
把食物改成随机的英文单词，
蛇吃到单词后，单词会显示在屏幕上方
```

**AI 会做什么**：
- 修改食物生成逻辑
- 添加单词库
- 在界面上显示已吃单词

---

# 代码对比：吃食物 vs 吃单词

**之前**：
```javascript
food = { x: randomX, y: randomY }
```

**之后**：
```javascript
const words = ['apple', 'banana', 'cherry', ...]
food = { 
  x: randomX, 
  y: randomY, 
  word: words[Math.floor(Math.random() * words.length)]
}
```

---

# 第三步：根据单词写诗

**对 AI 说**：
```
当蛇吃到 5 个单词后，
调用 AI API 根据这 5 个单词生成一首诗，
显示在游戏界面上
```

**这就是 AI 原生的魅力**：
- 游戏逻辑由代码控制
- 创意内容由 AI 生成
- 两者完美结合

---

# 第四步：根据诗歌画画

**对 AI 说**：
```
当诗歌生成后，
再调用 AI 图像生成 API，
根据诗歌内容生成一幅画，
显示在游戏结束界面
```

**完整链路**：
吃单词 → 写诗 → 画画 → 一个完整的 AI 原生游戏

---

# 调试技巧：如何向 AI 描述问题

**❌ 坏例子**：
```
"有 bug，修一下"
```

**✅ 好例子**：
```
"当蛇吃到第 5 个单词时，
诗歌没有生成，
控制台显示 'API key not found' 错误，
请帮我检查 API 配置"
```

---

# 好需求 vs 坏需求

| 坏需求 | 好需求 |
|--------|--------|
| "有 bug" | "点击按钮后没反应，控制台报错 XXX" |
| "界面不好看" | "按钮太小，希望改成 48px 高度，圆角 8px" |
| "加个功能" | "希望添加暂停功能，按空格键暂停/继续游戏" |

**核心原则**：具体、可观察、可验证

# Part 4
## AI 能力边界

---

# AI 擅长做什么？

✅ **小而完整的应用**（贪吃蛇、计算器、记账工具）
✅ **快速原型**（验证想法、展示 Demo）
✅ **重复性工作**（生成表单、CRUD 页面）
✅ **创意内容**（文案、图片、音乐）

**判断标准**：
> 5 分钟能说清楚的，AI 能做

---

# AI 不擅长做什么？

❌ **大型系统**（电商平台、社交网络）
❌ **高安全性**（支付系统、医疗系统）
❌ **性能优化**（高并发、低延迟）
❌ **复杂业务逻辑**（多角色权限、复杂工作流）

**原因**：
- 上下文有限（记不住太多信息）
- 缺少全局视角（看不到整个系统）
- 无法保证正确性（可能产生幻觉）

---

# 三个实战案例

| 项目 | 能做吗？ | 原因 |
|------|---------|------|
| 记账工具 | ✅ 能 | 功能简单，逻辑清晰 |
| 协作看板 | ⚠️ 部分 | 基础功能可以，复杂权限需要人工 |
| 支付系统 | ❌ 不能 | 安全性要求高，容错率低 |

---

# 从「能写」到「能用」的三个层次

**Level 1：能跑起来**
- AI 生成的代码可以运行
- 基本功能正常

**Level 2：能用起来**
- 有错误处理
- 有 Loading 状态
- 有数据持久化

**Level 3：能上线**
- 有安全防护
- 有性能优化
- 有监控告警

**本周目标**：Level 1

**共同特点**：核心能力由 AI 提供
