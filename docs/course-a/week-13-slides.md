# Spec Coding 定义

**Spec Coding**（规范编程）= 以规范文档作为开发核心产物的方法论

**核心思路**：

> 先写清楚规范，再让 AI 根据规范生成代码 规范是 source of truth，代码只是规范的实现产物

* * *

# 小林的理解方式

**Vibe Coding**：边走边看

-   想到哪说到哪
-   AI 跟着你的思路即兴发挥
-   快但容易跑偏

**Spec Coding**：按图施工

-   先把设计图（规范）画好
-   AI 照着图纸精确实现
-   慢一点但一次到位

# 核心论点：代码是意图的有损投影

> **Code is a lossy projection of intent.** 代码是意图的有损投影

**什么意思？** 当你把想法变成代码时，大量上下文信息会丢失：

-   **为什么**要这样做
-   **权衡了哪些方案**
-   **考虑了什么约束**

代码只保留了「怎么做」，却丢掉了「为什么这样做」

* * *

# 举个例子

**代码**：

```javascript
if (retryCount > 5) { throw error; }
```

**你只知道**：重试超过 5 次就报错

**你不知道**：

-   为什么是 5 次而不是 3 次或 10 次？
-   这个数字是根据什么业务场景定的？
-   是否考虑过指数退避？
-   有没有测试过这个阈值的合理性？

* * *

# 编程的本质是沟通

> "If you can communicate effectively, you can program." 如果你能有效沟通，你就能编程

**Grove 的观点**：

-   实际编码工作只占开发的 **10-20%**
-   剩下的 80% 是**结构化沟通**
    -   理解用户要什么
    -   和团队对齐方案
    -   定义验收标准
    -   处理边界情况

* * *

# 写规范的人就是程序员

> "Whoever writes the spec — be it a PM, a lawmaker, an engineer, a marketer — is now the programmer."

**颠覆性观点**：

-   随着 AI 越来越擅长把规范转化为代码
-   **真正的编程工作**从「写代码」变成了「写规范」
-   谁能最精确地表达意图，谁就是最有价值的「程序员」

* * *

# 规范拥有类似代码的工具链

规范可以像代码一样：

-   **组合**：规范可以模块化组合，就像代码模块
-   **测试**：规范可以嵌入单元测试，验证行为
-   **Lint 检查**：检测规范中的模糊语言
-   **一致性验证**：跨部门的规范可以做一致性检查

* * *

# OpenAI Model Spec：活的证明

**案例**：

-   OpenAI 发现模型存在 sycophancy（过度迎合用户）问题
-   他们没有重新训练模型
-   而是**修改了规范文档**
-   改动自动传播到整个系统，问题得到修正

**证明了什么？**

> 规范本身可以作为「可执行代码」发挥作用

# Part 2

## Spec Coding 的三层规范结构

* * *

# 三层结构

**第一层：功能规范（What）**

-   用自然语言描述期望结果
-   回答「做什么」

**第二层：技术设计（How - 架构层）**

-   定义架构、数据模型、API
-   回答「怎么做」

**第三层：实现约束（How - 实现层）**

-   版本、框架、代码规范
-   回答「用什么做」

* * *

# 第一层：功能规范（What）

```markdown
## 用户认证功能

### 用户故事
- 作为新用户，我希望能通过邮箱注册账号
- 作为已注册用户，我希望能用邮箱和密码登录
- 作为忘记密码的用户，我希望能通过邮件重置密码

### 验收标准
- 注册时验证邮箱格式和密码强度
- 登录失败 5 次后锁定账号 15 分钟
- 密码重置链接 30 分钟内有效
```

* * *

# 第二层：技术设计（How - 架构层）

```markdown
## 技术设计

### 数据模型
- users 表：id, email, password_hash, created_at, locked_until
- sessions 表：id, user_id, token, expires_at

### API 设计
- POST /api/auth/register → 201 Created
- POST /api/auth/login → 200 OK + JWT
- POST /api/auth/reset-password → 202 Accepted

### 安全要求
- 密码使用 bcrypt 加密，cost factor ≥ 12
- JWT 有效期 15 分钟，refresh token 7 天
```

* * *

# 第三层：实现约束（How - 实现层）

```markdown
## 实现约束

### 技术栈
- Runtime: Node.js 20+
- Framework: Express 5
- ORM: Prisma
- Testing: Vitest

### 代码规范
- 使用 TypeScript strict mode
- 错误处理使用自定义 AppError 类
- 所有 API 端点需要 JSDoc 注释
```

* * *

# 小林的经验

**不用每次都写三层**：

-   **快速原型**：只写第一层就够
-   **团队协作**：至少要写到第二层
-   **生产级项目**：才需要第三层

**她的习惯**：

1.  先写第一层验证需求
2.  确认方向后再补第二层
3.  根据项目规模决定要不要第三层

# Part 3

## 在 Claude Code 中实践 Spec Coding

* * *

# Claude Code 的「万物皆 Markdown」哲学

**核心理念**：

> 规范本身就是代码

**在 Claude Code 中**：

-   **CLAUDE.md**：项目规范的 Markdown 文档
-   **.claude/rules/**：分层规范的 Markdown 文件集合
-   **specs/**：功能需求的 Markdown 描述
-   **对话历史**：本身就是 Markdown 格式

* * *

# 第一步：用 CLAUDE.md 建立项目规范

`CLAUDE.md` = 你项目的「活规范」

**作用**：

-   每次 Claude Code 启动时都会读取它
-   相当于给 AI 一份持久的项目说明书
-   不只是配置文件，而是项目规范的入口

* * *

# 一个好的 CLAUDE.md 应该包含什么？

```markdown
# 电商项目规范

## 项目定位
面向中小商家的 SaaS 电商平台

## 架构决策
- 前后端分离，API-first 设计
- 后端微服务架构

## 核心约束
- 所有金额使用整数（分）存储
- 订单状态机严格遵循：待支付 → 已支付 → 已发货 → 已完成
- 支付相关接口必须幂等

## 开发规范
- 使用 TypeScript strict mode
- API 响应格式：成功 { data }，失败 { error }
```

* * *

# 小林的心得

**CLAUDE.md 不是一次写完就不动了**

她的习惯：

-   每次遇到 AI 犯同样的错误
-   就把对应的规则加进去
-   比如 AI 把金额用 float 存储导致精度问题
-   她就在「核心约束」里加了一条「金额用整数（分）」

**久而久之，这份文档就成了项目的「避坑指南」**

* * *

# 第二步：用 Rules 目录管理分层规范

**为什么需要 Rules 目录？**

-   **按需加载**：只在编辑相关文件时加载对应规范
-   **职责分离**：前端规范、后端规范各管各的
-   **团队协作**：不同成员可以维护不同领域的规范

* * *

# Rules 目录结构示例

```
.claude/rules/
├── 00-architecture.md      # 架构规范（全局）
├── 01-security.md           # 安全规范（全局）
├── 10-api-design.md         # API 设计规范
├── 11-frontend-patterns.md  # 前端模式规范
├── 12-database.md           # 数据库规范
└── 20-testing.md            # 测试规范
```

* * *

# 一个具体的 Rules 文件示例

```markdown
---
globs:
  - "src/api/**/*.ts"
  - "src/services/**/*.ts"
---

# API 设计规范

## 路由设计
- RESTful 风格，使用名词复数：/api/v1/orders

## 响应格式
- 成功：{ data, pagination? }
- 错误：{ error: { code, message } }

## 必须遵守
- 所有写操作需要认证
- 列表接口必须支持分页
```

* * *

# 单文件 vs 分层规范

**单文件 CLAUDE.md**：

-   每次都加载全部内容，浪费 token
-   文件太长，难以维护
-   多人编辑容易冲突

**分层 Rules 目录**：

-   按需加载，节省 token
-   职责清晰，易于维护
-   多人协作不冲突

# 第三步：用 /plan 实现四阶段工作流

**Spec Coding 标准工作流**：

```
Specify → Plan → Tasks → Implement
```

Claude Code 的 `/plan` 命令天然支持这个流程

* * *

# 阶段一：Specify（定义规范）

先写清楚要做什么，不急着写代码

```
/plan
我需要实现订单退款功能，规范如下：

功能需求：
- 用户可以在发货前申请全额退款
- 发货后 7 天内可以申请退货退款
- 退款需要管理员审批

验收标准：
- 退款金额不能超过订单实付金额
- 退款状态机：申请中 → 审批通过 → 退款中 → 已退款
```

* * *

# 阶段二：Plan（技术规划）

Claude 会基于你的规范生成技术方案：

```
📋 退款功能实施计划

1. 数据模型设计
   - 创建 refunds 表
   - 添加订单状态机的退款相关状态

2. API 设计
   - POST /api/orders/:id/refund - 申请退款
   - PUT /api/refunds/:id/approve - 审批退款

3. 业务逻辑
   - 退款资格校验
   - 库存恢复逻辑
```

* * *

# 阶段三：Tasks（任务拆解）

将计划拆分为可独立执行的小任务

Claude Code 会自动帮你拆解，你也可以手动调整

* * *

# 阶段四：Implement（逐步实现）

按任务逐个实现，每完成一个就验证一次

**小林的习惯**：

-   让 Claude Code 做完一个任务就暂停
-   她确认没问题后再继续下一个
-   这种「做一步、停一步」的节奏特别适合复杂功能

# 混合策略

## 从 Vibe 到 Spec 的渐进式过渡

* * *

# 什么时候用 Vibe Coding？

**快速探索场景**：

-   ⚡ 验证一个想法是否可行（30 分钟内的原型）
-   ⚡ 探索不熟悉的技术或框架
-   ⚡ Hackathon 或内部 demo
-   ⚡ 一次性脚本或工具

**小林的例子**： 想试试能不能用 WebSocket 实现实时通知，就直接让 Claude Code 写了个最简单的 demo。10 分钟跑通了，证明可行。

* * *

# 什么时候用 Spec Coding？

**生产级开发场景**：

-   🏗️ 生产级功能开发
-   🏗️ 多人协作的项目
-   🏗️ 需要长期维护的代码
-   🏗️ 涉及安全、支付、数据等敏感领域
-   🏗️ API 设计和系统集成

**小林的例子**： 支付模块、用户认证、订单系统这些核心功能，都用 Spec Coding。因为这些模块出错的代价太高。

# 推荐的渐进式工作流

**三步走**：

**① Vibe 探索**

-   快速验证想法可行性

**② 提炼规范**

-   把探索成果整理成规范

**③ Spec 重建**

-   基于规范实现生产版本

* * *

# 阶段一：Vibe 探索

用 Vibe Coding 快速验证想法：

```

```

不写规范，不管代码质量，只验证可行性

* * *

# 阶段二：提炼规范

验证可行后，把探索中的发现整理成规范

你甚至可以让 AI 帮你：

```
小林：基于我们刚才做的通知功能原型，
帮我整理一份正式的功能规范文档，
包括数据模型、API 设计和验收标准
```

* * *

# 阶段三：Spec 重建

基于规范，用 Spec Coding 方式重新实现生产级版本：

```
@specs/notification-system.md
按照这份规范从零实现，不要参考之前的原型代码
```

**这个流程的好处**： 用 Vibe Coding 的速度验证方向，用 Spec Coding 的质量交付产品

# Q2：规范写多详细才够？

**一份高质量的规范可以只有一页**

关键是回答 8 个问题：

1.  我们在做什么？（功能描述）
2.  输入是什么？（数据来源）
3.  输出是什么？（期望结果）
4.  约束条件是什么？（技术限制、业务规则）
5.  失败模式有哪些？（错误处理）
6.  安全要求是什么？（权限、加密）
7.  性能要求是什么？（响应时间、并发量）
8.  什么测试能证明它工作？（验收标准）

# Q3：AI 遗漏了「显而易见」的功能怎么办？

**小林的解决方案**： 在 `CLAUDE.md` 中设置全局规则

```markdown
## 默认行为（除非规范明确说明不需要）

所有 API 端点必须：
- 添加错误处理和日志记录
- 实现输入验证
- 添加单元测试

所有前端组件必须：
- 支持响应式布局
- 添加加载状态
- 实现错误提示
```

# Q4：小项目也需要 Spec Coding 吗？

**小林的判断标准**：

**不需要 Spec Coding**：

-   快速原型
-   一次性脚本
-   学习实验
-   个人项目

**需要 Spec Coding**：

-   生产级项目
-   多人协作项目
-   需要长期维护的项目

**经验法则**：如果这个功能 3 个月后还要改，就用 Spec Coding
