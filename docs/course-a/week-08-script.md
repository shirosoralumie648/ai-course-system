### 1.2 Demo 和产品的本质区别（8 分钟）

**\[展示 PPT：Demo 和产品的区别\]**

让我们来看看 Demo 和产品的本质区别是什么。

**Demo 阶段**：

-   核心功能能跑通就行
-   只考虑理想情况（Happy Path）
-   用户按照你预期的方式操作

**产品阶段**：

-   要考虑等待（Loading 状态）
-   要考虑失败（错误处理）
-   要考虑异常（网络断开、API 失败）
-   要考虑数据持久化（刷新不丢失）
-   要考虑用户误操作（撤销、确认）

**\[展示 PPT：对比表格\]**

场景

Demo 的表现

产品的表现

点击按钮

直接调用 API

显示 Loading，禁用按钮

API 失败

控制台报错或白屏

友好提示，允许重试

刷新页面

数据丢失

数据持久化保存

示例数据

"测试 1"、"测试 2"

**核心洞察**： 从 Demo 到产品，不是功能的增加，而是**体验的完善**。

### 1.3 什么是「Happy Path」（7 分钟）

**\[展示 PPT：Happy Path\]**

很多初学者做原型，往往只做「Happy Path」（最理想的路径）。

什么是 Happy Path？让我给大家举个例子：

**Happy Path 的思维**：

```
用户打开页面 → 输入商品名称 → 点击生成 → API 成功返回 → 显示结果
```

**真实世界的情况**：

```
用户打开页面 → 输入商品名称 → 点击生成 →
  → 等待 5 秒（用户：是不是坏了？）
  → 网络断开（用户：怎么办？）
  → API 限流（用户：为什么失败？）
  → 终于成功 → 显示结果 → 刷新页面 → 数据没了（用户：？？？）
```

**\[互动提问\]**
大家在测试自己的 Demo 时，有没有考虑过这些情况？

（等待学生回应）

今天这节课，我们要做的就是：**拒绝 Happy Path，完善所有可能的路径。**

## Part 2：完善核心链路（25 分钟）

### 2.1 增加「等待」与「反馈」（8 分钟）

**\[展示 PPT：问题场景\]**

第一个要解决的问题：用户等待时的焦虑。

当用户点击「生成文案」时，AI 往往需要 3-5 秒才能响应。如果界面毫无反应，用户会以为程序坏了，可能会：

-   重复点击按钮
-   刷新页面
-   直接关闭

**解决方案**：添加 Loading 状态。

**\[演示操作\]**

现在让我演示如何让 Claude Code 帮你加上 Loading 状态。打开你的项目，对 Claude Code 说：

```
当我点击生成按钮时，请把按钮变成「生成中...」并设为不可点击，
同时在右侧区域显示一个加载动画。
直到 API 返回结果后，再恢复正常。
```

**\[等待 Claude Code 生成代码\]**

大家看到了吗？Claude Code 做了这些改动：

1.  添加了 `isLoading` 状态变量
2.  点击时设置 `isLoading = true` 并禁用按钮
3.  显示加载动画
4.  API 返回后设置 `isLoading = false`

**\[展示效果\]**

现在点击按钮，你会看到：

-   按钮文字变成「生成中...」
-   按钮变灰，无法再次点击
-   右侧显示加载动画
-   API 返回后，一切恢复正常

这就是用户体验的提升。

### 2.2 处理「失败」与「异常」（8 分钟）

**\[展示 PPT：常见错误类型\]**

第二个要解决的问题：错误处理。

在真实世界里，很多事情会出错：

-   API Key 可能过期
-   网络可能断开
-   AI 服务可能限流
-   请求可能超时

如果不处理这些异常，用户看到的就是控制台报错或白屏。

**\[展示 PPT：错误类型表格\]**

让我们看看常见的错误类型及如何处理：

错误类型

用户看到的提示

开发者日志

网络断开

「网络连接失败，请检查网络后重试」

`Network Error: Failed to fetch`

API Key 无效

「认证失败，请检查配置」

`401 Unauthorized`

请求超时

「请求超时，请稍后重试」

`Timeout: Request exceeded 30s`

服务限流

「请求过于频繁，请稍后再试」

`429 Too Many Requests`

**关键原则**：

-   给用户看友好的提示
-   给开发者留调试线索

**\[演示操作\]**

现在让我演示如何添加错误处理。对 Claude Code 说：

```
如果 API 请求失败了，不要直接在控制台报错，
请在页面顶部弹出一个红色的提示框（Toast），
告诉用户「生成失败，请稍后重试」，
并允许用户重新点击生成。
同时把具体错误信息打印到控制台方便我调试。
```

**\[展示效果\]**

现在如果 API 失败，用户会看到友好的提示，而不是白屏或技术错误信息。

### 2.3 对话历史持久化（9 分钟）

**\[展示 PPT：问题场景\]**

第三个要解决的问题：数据持久化。

小林的 AI 文案生成器每次生成的内容都很有价值，但用户一刷新页面，之前生成的所有内容就消失了。用户抱怨："我刚才生成的那条文案挺好的，想再看看，结果找不到了..."

**解决方案**：使用 LocalStorage 保存数据。

**\[展示 PPT：存储方案对比\]**

在不引入数据库的情况下，我们有几种选择：

方案

适用场景

优点

缺点

LocalStorage

纯前端项目

实现简单，刷新不丢失

无法跨设备同步

SessionStorage

临时数据

更安全

关闭标签页数据就没了

IndexedDB

大量数据

容量大

API 复杂

对于原型阶段，**LocalStorage 是最佳选择**。

**\[演示操作\]**

对 Claude Code 说：

```
请帮我实现对话历史的保存功能：

1. 每次生成文案后，将用户输入和 AI 输出保存到 LocalStorage
2. 每条记录包含：时间戳、商品名称、用户输入、AI 生成结果
3. 页面加载时自动读取历史记录并显示在左侧列表
4. 支持点击历史记录查看详情
5. 支持删除单条记录

数据格式用 JSON 数组。
```

**\[展示效果\]**

现在刷新页面，你会发现：

-   之前生成的内容还在
-   可以点击查看历史记录
-   可以删除不需要的记录

这就是数据持久化的价值。

## Part 3：注入灵魂——模拟真实数据（20 分钟）

### 3.1 为什么需要 Mock Data（5 分钟）

**\[展示 PPT：空荡荡的页面\]**

小林完善了基础链路后，把原型发给朋友看。朋友打开一看：历史记录区域空空如也，示例商品列表里只有「测试商品 1」「测试商品 2」「测试商品 3」...

朋友说："这看着太像半成品了，能不能放点真实的数据进去？这样我才能感受到真实使用场景。"

**\[互动提问\]**
大家想象一下，你向别人展示「电商素材工作台」，结果历史记录里空空如也，或者只有一行 "test / test / test"。别人会怎么想？

（等待学生回应）

对，他们会觉得这只是个玩具，不是真正的产品。

**解决方案**： 「伪造」一些逼真的数据，让你的原型看起来像一个已经运营了半年的真实产品。

### 3.2 让 AI 设计数据结构（5 分钟）

**\[展示 PPT：让 AI 帮你设计\]**

我们不需要自己去想每一个字段叫什么，这件事完全可以交给 AI。

**\[演示操作\]**

对 Claude Code 说：

```
我正在做一个抖音电商素材工作台的原型。

请帮我设计一个 JSON 数据结构，用来描述一个「商品任务」。

这个任务应该包含：
- 商品的基本信息（名字、类目、价格区间）
- 输入的素材（商品特点、目标人群）
- AI 生成的结果（标题、文案、标签）
- 任务状态（进行中/已完成）
- 创建时间

请直接给我一个 JSON 示例。
```

**\[展示 Claude Code 的回复\]**

AI 会根据你的描述，自动帮你构思出合理的字段名和结构。你不需要纠结是叫 `name` 还是 `title`，AI 会帮你决定。

### 3.3 让 AI 批量生产「逼真」数据（10 分钟）

**\[展示 PPT：关键技巧\]**

有了数据结构后，下一步就是让 AI 帮你「填空」，生成一批看起来真实的数据。

**关键技巧**： 你不能只告诉 AI「帮我生成数据」，你需要像给实习生布置任务一样，告诉它**业务背景**和**内容要求**。

**\[演示操作\]**

对 Claude Code 说：

```
请基于刚才设计的结构，帮我生成 15 条逼真的模拟数据。

业务场景要求：

1. 假设这是一家综合百货店，商品涵盖「女装」「数码」「美妆」「家居」「食品」五个类目
2. 生成的标题和文案要非常「抖音风」：
   - 标题要包含 Emoji (🔥, ✨, 💕, 🎉)
   - 文案要用「绝绝子」「亲测好用」「姐妹们」「必入」这种口语化表达
   - 每条文案 80-120 字，要有感染力
3. 商品名称要具体真实，不要用「商品 A」这种
4. 价格区间要符合各类目的实际情况
5. 创建时间分散在最近 7 天内

请直接生成 JavaScript 数组格式，我要复制到代码里用。
```

**\[展示生成的数据\]**

大家看，AI 生成的数据非常逼真：

-   商品名称具体真实："夏季法式复古碎花裙"、"超强降噪蓝牙耳机 Pro"
-   文案很有抖音风格："姐妹们！这条裙子真的太显瘦了！"
-   价格区间合理：女装 89-129，数码 299-399
-   时间分散在最近一周

**小林的经验**： 她发现 AI 生成的 Mock Data 质量取决于提示词的详细程度。第一次她只说「生成 10 条数据」，结果 AI 给的都是「商品 A」「商品 B」。后来她加上了「业务场景」「文案风格」「具体要求」，生成的数据就非常逼真了。

**记住**：对 AI 越具体，结果越好。

### 4.2 怎么测？观察而非引导（8 分钟）

**\[展示 PPT：错误示范\]**

小林第一次让小王测试时，全程在旁边指导："你点这里"、"然后输入商品名称"、"再点生成"...

测完后小王说："挺好用的啊！"但小林心里没底：这是真好用，还是因为我全程指导？

**正确的测试方法**：

**\[展示 PPT：正确示范\]**

```
你："这是一个 AI 文案生成工具，你试着用它给你的商品生成一条抖音文案"
用户:(自己探索) "嗯...这个按钮是干嘛的？"
你:(记录问题，不回答)
用户:"哦我懂了，应该先填这里..."
你:"你在想什么？可以说出来吗？"
用户:"我在想这个『特点』应该填什么..."
```

**关键原则**：

1.  **只给任务，不给步骤**：让用户自己探索
2.  **观察而非指导**：看他们卡在哪里、犹豫什么
3.  **鼓励思考出声**：「你现在在想什么？」「你期望点这里会发生什么？」
4.  **记录而非辩解**：用户说「这里不好用」，不要解释「其实你应该...」，而是记下来

**\[互动演示\]**

现在我需要一个志愿者，来演示一下正确的测试方法。

（选一个学生，让他试用另一个学生的产品，演示观察式测试）

### 4.3 问什么？有效的反馈问题（7 分钟）

**\[展示 PPT：反馈问题清单\]**

测试结束后，不要只问「你觉得怎么样？」这种开放问题。用户往往会客气地说「挺好的」，但你得不到有用的信息。

**小林的反馈问题清单**：

**关于功能价值**：

-   "如果这个工具现在就能用，你会用它吗？为什么？"
-   "你觉得它能帮你解决什么问题？"
-   "和你现在的做法相比，它有什么优势？"

**关于使用体验**：

-   "刚才使用过程中，有哪个地方让你卡住了？"
-   "有没有哪个地方和你预期的不一样？"
-   "如果让你给朋友推荐，你会怎么介绍这个工具？"

**关于改进方向**：

-   "如果只能加一个功能，你最希望加什么？"
-   "有没有哪个地方你觉得多余的、可以去掉的？"
-   "你会给这个产品打几分（1-10）？为什么不是 10 分？"

**\[展示 PPT：最关键的问题\]**

**「为什么不是 10 分？」**

这个问题最关键。它能让用户说出真实的顾虑和不满。

小林用这个问题发现了很多隐藏的问题：

-   小王："因为生成的文案有时候太官方了，不够接地气" → 改进提示词
-   表姐："因为我不知道『特点』和『卖点』有什么区别" → 简化输入项
-   同学："因为没有批量生成功能，一个个生成太慢了" → 新功能方向

### 5.2 快速修复：让 AI 成为你的迭代助手（10 分钟）

**\[展示 PPT：案例 1\]**

确定优先级后，就可以开始修复了。在这个阶段，AI 是你最好的修改助手。

**案例 1：调整提示词，让文案更接地气**

**\[演示操作\]**

对 Claude Code 说：

```
用户反馈生成的文案太官方，不够接地气。

现在的提示词是：「请为这个商品生成一条抖音文案」

请帮我优化提示词，让生成的文案更口语化、更有感染力。
```

### 5.3 迭代节奏：小步快跑（5 分钟）

**\[展示 PPT：小林的迭代节奏\]**

小林发现，**改一点、测一点、再改一点**，比一次性改完所有问题效果更好。

她的迭代节奏：

**第 1 天**：

-   修复 2 个阻断性问题
-   发给测试用户确认是否解决

**第 2 天**：

-   修复 3 个体验问题
-   再次测试，收集新反馈

**第 3 天**：

-   根据新反馈微调
-   准备下一轮迭代

**为什么要小步快跑？**

1.  快速验证：改完立刻能看到效果
2.  降低风险：一次改太多，出问题不知道是哪里导致的
3.  保持动力：每天都能看到进步

**小林的感悟**： 先做到 60 分，再迭代到 80 分。完成比完美更重要。
