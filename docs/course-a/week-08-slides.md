# Demo 和产品的区别

**Demo 阶段**：

-   核心功能能跑通就行
-   只考虑理想情况（Happy Path）

**产品阶段**：

-   要考虑等待、失败、异常
-   要考虑数据持久化
-   要考虑用户误操作

**核心**：从 Demo 到产品,不是功能的增加,而是**体验的完善**

## 完善核心链路

* * *

# 第一步：增加「等待」与「反馈」

**问题场景**： 用户点击「生成文案」,AI 需要 3-5 秒响应 如果界面毫无反应,用户会以为程序坏了

**解决方案**：

-   添加 Loading 状态
-   按钮变成「生成中...」并禁用
-   显示加载动画
-   API 返回后恢复正常

* * *

# 对 Claude Code 说

```
当我点击生成按钮时,请把按钮变成「生成中...」
并设为不可点击,同时在右侧区域显示一个加载动画。
直到 API 返回结果后,再恢复正常。
```

**Claude Code 会做什么**：

-   添加 `isLoading` 状态变量
-   点击时设置 `isLoading = true` 并禁用按钮
-   显示加载动画
-   API 返回后设置 `isLoading = false`

* * *

# 第二步：处理「失败」与「异常」

**问题场景**：

-   API Key 可能过期
-   网络可能断开
-   AI 服务可能限流

**解决方案**： 添加错误处理和用户友好的提示

* * *

# 对 Claude Code 说

```
如果 API 请求失败了,不要直接在控制台报错,
请在页面顶部弹出一个红色的提示框(Toast),
告诉用户「生成失败,请稍后重试」,
并允许用户重新点击生成。
同时把具体错误信息打印到控制台方便我调试。
```

**关键原则**： 永远不要让用户看到技术错误信息,但要给开发者留下调试线索

# 第三步：对话历史持久化

**问题场景**： 用户一刷新页面,之前生成的所有内容就消失了

**解决方案**： 使用 LocalStorage 保存数据

* * *

# 存储方案对比

方案

适用场景

优点

缺点

**LocalStorage**

纯前端项目,单用户使用

实现简单,刷新不丢失,无需后端

无法跨设备同步,容量限制 5-10MB

**SessionStorage**

临时数据,关闭标签页即清除

更安全,不会长期占用空间

关闭标签页数据就没了

**IndexedDB**

需要存储大量结构化数据

容量大(几百 MB),支持复杂查询

API 复杂,学习成本高

**原型阶段最佳选择**：LocalStorage

* * *

# 对 Claude Code 说

```
请帮我实现对话历史的保存功能:

1. 每次生成文案后,将用户输入和 AI 输出保存到 LocalStorage
2. 每条记录包含:时间戳、商品名称、用户输入、AI 生成结果
3. 页面加载时自动读取历史记录并显示在左侧列表
4. 支持点击历史记录查看详情
5. 支持删除单条记录

数据格式用 JSON 数组。
```

# Part 3

## 注入灵魂：模拟真实数据

* * *

# 为什么需要 Mock Data？

**问题**：

-   历史记录区域空空如也
-   示例商品列表只有「测试商品 1」「测试商品 2」
-   看起来像半成品,无法打动人

**解决**： 「伪造」一些逼真的数据,让原型看起来像一个已经运营了半年的真实产品

* * *

# 第一步：让 AI 设计数据结构

**对 Claude Code 说**：

```
我正在做一个抖音电商素材工作台的原型。

请帮我设计一个 JSON 数据结构,用来描述一个「商品任务」。

这个任务应该包含:
- 商品的基本信息(名字、类目、价格区间)
- 输入的素材(商品特点、目标人群)
- AI 生成的结果(标题、文案、标签)
- 任务状态(进行中/已完成)
- 创建时间

请直接给我一个 JSON 示例。
```

* * *

# 第二步：让 AI 批量生产「逼真」数据

**关键技巧**： 不能只说「帮我生成数据」 要告诉 AI **业务背景**和**内容要求**

* * *

# 对 Claude Code 说

```
请基于刚才设计的结构,帮我生成 15 条逼真的模拟数据。

业务场景要求:

1. 假设这是一家综合百货店,商品涵盖「女装」「数码」「美妆」「家居」「食品」五个类目
2. 生成的标题和文案要非常「抖音风」:
   - 标题要包含 Emoji (🔥, ✨, 💕, 🎉)
   - 文案要用「绝绝子」「亲测好用」「姐妹们」「必入」这种口语化表达
   - 每条文案 80-120 字,要有感染力
3. 商品名称要具体真实,不要用「商品 A」这种
4. 价格区间要符合各类目的实际情况
5. 创建时间分散在最近 7 天内

请直接生成 JavaScript 数组格式,我要复制到代码里用。
```

* * *

# 小林的经验

**第一次**： 只说「生成 10 条数据」 结果 AI 给的都是「商品 A」「商品 B」

**后来**： 加上了「业务场景」「文案风格」「具体要求」 生成的数据就非常逼真了

**记住**：对 AI 越具体,结果越好

* * *

# 第三步：使用 LocalStorage 实现「假增删改」

**对 Claude Code 说**：

```
请帮我实现一个数据存储功能:

1. 优先从 localStorage 读取数据
2. 如果 localStorage 为空,则使用刚才生成的 Mock 数据初始化,
   并将它们存入 localStorage
3. 同时帮我写 addTask、deleteTask、updateTask 函数,
   每次操作都要同步更新 localStorage
4. 确保数据变化后页面自动刷新显示

这样用户的操作就能持久化了。
```

# 怎么测？观察而非引导

**❌ 错误示范**：

```
你: "你点这个按钮试试"
用户: "哦好" (点击)
你: "然后在这里输入商品名称"
用户: "好的" (输入)
你: "觉得怎么样?"
用户: "挺好的"
```

* * *

# 怎么测？观察而非引导

**✅ 正确示范**：

```
你: "这是一个 AI 文案生成工具,
    你试着用它给你的商品生成一条抖音文案"
用户: (自己探索) "嗯...这个按钮是干嘛的?"
你: (记录问题,不回答)
用户: "哦我懂了,应该先填这里..."
你: "你在想什么?可以说出来吗?"
用户: "我在想这个『特点』应该填什么..."
```

* * *

# 测试的关键原则

1.  **只给任务,不给步骤**：让用户自己探索
2.  **观察而非指导**：看他们卡在哪里、犹豫什么
3.  **鼓励思考出声**：「你现在在想什么?」「你期望点这里会发生什么?」
4.  **记录而非辩解**：用户说「这里不好用」,不要解释「其实你应该...」,而是记下来

* * *

# 问什么？有效的反馈问题

**关于功能价值**：

-   「如果这个工具现在就能用,你会用它吗?为什么?」
-   「你觉得它能帮你解决什么问题?」
-   「和你现在的做法相比,它有什么优势?」

**关于使用体验**：

-   「刚才使用过程中,有哪个地方让你卡住了?」
-   「有没有哪个地方和你预期的不一样?」
-   「如果让你给朋友推荐,你会怎么介绍这个工具?」

* * *

# 最关键的问题

**「你会给这个产品打几分(1-10)?为什么不是 10 分?」**

这个问题能让用户说出真实的顾虑和不满

**小林的发现**：

-   小王: "因为生成的文案有时候太官方了,不够接地气" → 改进提示词
-   表姐: "因为我不知道『特点』和『卖点』有什么区别" → 简化输入项
-   同学: "因为没有批量生成功能,一个个生成太慢了" → 新功能方向

* * *

# 特殊技巧：「绿野仙踪法」

**场景**： 想验证一个功能是否有价值,但还没来得及实现

**做法**：

1.  在界面上加一个「智能推荐」按钮
2.  用户点击后,你在后台手动挑选几个标签,假装是 AI 推荐的
3.  观察用户的反应:是否会用?是否觉得有价值?

**价值**： 快速验证需求,避免浪费时间开发无用功能

**注意**：只能用于内部测试和需求验证,不能用于真实用户

# 迭代节奏：小步快跑

**小林的迭代节奏**：

**第 1 天**：

-   修复 2 个阻断性问题

# 为什么要小步快跑？

1.  **快速验证**：改完立刻能看到效果,避免方向错误
2.  **降低风险**：一次改太多,出问题不知道是哪里导致的
3.  **保持动力**：每天都能看到进步,更有成就感

**小林的感悟**： 先做到 60 分,再迭代到 80 分 第一版不用完美,能用就行,然后根据反馈快速迭代 **完成比完美更重要**
