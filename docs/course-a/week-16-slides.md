# Part 1
## 什么是 Agent Teams？

---

# 小林的困惑

周一早上，小林接到了一个紧急任务：

> 「用一周时间开发一个完整的在线商城系统」

小林心想：

- 如果用单个 Claude 实例，得一个模块一个模块地做
- 至少要两周时间

**正当小林发愁时...**

---

# Agent Teams 的诞生

技术总监走过来说：

> 「听说过 Agent Teams 吗？可以让多个 AI 同时工作，就像组建一个开发团队一样。」

小林眼前一亮：「这不就是我需要的吗？」

---

# Agent Teams 核心概念

**Agent Teams** 是 Claude Code 的革命性功能

**以前**：你带着一个超级能干的助手工作
**现在**：你带领一支完整的 AI 开发团队

团队成员可以：
- ✅ 同时工作（真正的并行）
- ✅ 互相交流（直接通信）
- ✅ 协同完成复杂任务
- ✅ 各自拥有独立的上下文空间

---

# Agent Teams vs Subagent

| 特性 | Subagent | Agent Teams |
|------|---------|-------------|
| 拓扑结构 | 星型（中心化） | 网状（分布式） |
| 成员通信 | 通过主代理中转 | 成员之间直接通信 |
| 适用场景 | 简单任务分发 | 复杂系统开发 |
| 协作方式 | 独立执行 | 团队协作 |

---

# 团队组成

一个 Agent Team 由四种核心组件构成：

1. **Team Lead**：团队负责人，负责任务拆解和结果综合
2. **Teammates**：团队成员，真正干活的开发者
3. **TaskList**：共享任务板，管理任务状态和依赖
4. **Messaging**：消息系统，成员之间的通信工具

---

# Team Lead（团队负责人）

**职责**：
- ✅ 需求分析与任务拆解
- ✅ 团队创建与管理
- ✅ 任务分配与调度
- ✅ 结果综合与质量把控

**特点**：
- 不直接执行编码任务
- 通常使用 Opus 模型（需要强大推理能力）
- 拥有全局视角

---

# Teammates（团队成员）

**能力**：
- ✅ 独立的 200K token 上下文窗口
- ✅ 完整的工具权限（Read、Write、Edit、Bash 等）
- ✅ 自主任务认领
- ✅ 直接通信能力

**特点**：
- 每个成员都是独立的 Claude 实例
- 可以使用 Sonnet 模型（性价比高）
- 专注于具体实现

---

# 协作流程

```
用户提出需求
    ↓
Team Lead 分析需求，拆解任务
    ↓
创建团队成员，初始化 TaskList
    ↓
    ├─→ Teammate A 认领任务 1 ─┐
    ├─→ Teammate B 认领任务 2 ─┼→ 并行执行
    ├─→ Teammate C 认领任务 3 ─┤
    │                           ↓
    └────────── 成员间通过消息系统协调
                    ↓
       所有任务完成后，Team Lead 综合结果
                    ↓
           向用户输出最终成果
```

# Part 3
## 实战项目：小林的在线商城

---

# 项目需求

**功能需求**：
- 用户系统（注册、登录、个人中心）
- 商品展示（列表、详情、搜索、分类）
- 购物车（添加、删除、修改数量）
- 订单系统（下单、支付、订单查询）
- 后台管理（商品管理、订单管理）

**技术要求**：
- 前端：React + TypeScript + Tailwind CSS
- 后端：Node.js + Express + PostgreSQL
- 状态管理：Zustand
- API 设计：RESTful

---

# 小林的团队规划

**5 人团队**：

- **Teammate A**（架构师）：设计整体架构，定义 API 接口
- **Teammate B**（前端工程师）：实现 React 前端界面
- **Teammate C**（后端工程师）：实现 Express API
- **Teammate D**（数据库工程师）：设计 PostgreSQL 数据库
- **Teammate E**（测试工程师）：编写单元测试和集成测试

**模型分配**：Team Lead 使用 Opus，成员使用 Sonnet

---

# 第一阶段：架构设计

Teammate A（架构师）完成整体设计

**输出内容**：
- 项目结构设计
- 核心数据结构定义
- API 接口设计（合同优先）
- 请求/响应格式规范

**为什么要先设计？**
- 前后端可以并行开发
- 减少集成时的问题
- 接口文档自然形成

---

# 合同优先原则

**反面案例**：
- 前端发送 `{user, pass}`
- 后端期望 `{email, password}`
- 结果：对不上，需要返工

**正确做法**：
1. 先让架构师设计接口
2. 定义请求/响应格式
3. 所有成员确认后再开始开发

---

# 第二阶段：并行开发

所有成员同时开工：

```
┌─────────────────┬─────────────────┬─────────────────┐
│  Teammate B     │  Teammate C     │  Teammate D     │
│  [前端工程师]    │  [后端工程师]    │  [数据库工程师]  │
│                 │                 │                 │
│  正在创建       │  正在实现       │  正在设计       │
│  ProductCard... │  auth.ts 路由...│  Prisma schema..│
│                 │                 │                 │
│  ✓ 创建组件目录 │  ✓ 安装依赖     │  ✓ 初始化 Prisma│
│  ✓ 定义 Props   │  ✓ 配置 JWT     │  ✓ 定义 User 模型│
│  → 实现商品卡片 │  → 实现登录逻辑 │  → 定义 Product │
└─────────────────┴─────────────────┴─────────────────┘
```

---

**Teammate C → Teammate D**：

**Teammate D → Teammate C**：

# 第三阶段：集成和测试

# Part 4
## Agent Teams 最佳实践

---

# 实践 1：合同优先

在团队开始并行工作之前，先定义清晰的「合同」

**合同应该包含**：
- ✅ 函数签名和数据结构
- ✅ HTTP 状态码的含义
- ✅ 错误处理的约定
- ✅ 字段验证规则

**好处**：前后端可以并行开发，减少集成问题

---

# 实践 2：合理分配模型

| 角色 | 推荐模型 | 原因 |
|------|---------|------|
| Team Lead | Opus | 需要强大的推理能力 |
| Teammates | Sonnet | 具体编码任务，性价比高 |
| 简单任务 | Haiku | 文档更新，成本最低 |

**成本对比**：
- Opus 4.6：约 $15/百万输出 tokens
- Sonnet 4.5：约 $3/百万输出 tokens
- Haiku：约 $0.80/百万输出 tokens

---

# 实践 3：控制任务粒度

**经验法则**：每个任务应该让一个成员在 **15-30 分钟内**独立完成

```
❌ 任务太大：实现用户认证系统
   （包含多个子任务，失去并行优势）

❌ 任务太小：创建一个名为 auth.js 的空文件
   （协调时间比干活时间还多）

✅ 合适粒度：实现登录 API 接口
   - POST /api/login 接口
   - 验证用户名密码
   - 返回 JWT token
   - 错误处理
```

---

# 实践 4：避免文件冲突

**分配原则**：尽量让不同成员负责**不同的文件**

```
✅ 好的分配：
- Teammate A：负责 src/auth/ 目录
- Teammate B：负责 src/api/ 目录
- Teammate C：负责 tests/auth/ 目录

❌ 不好的分配：
- Teammate A 和 Teammate B 都要修改 src/app.js
```

---

# 实践 5：提供丰富的初始上下文

Teammates 启动时，对话历史是空的

**错误做法**：
```
创建团队，让成员开始干活
```

**正确做法**：
```
这是一个 React + Node.js 的电商项目，使用 TypeScript。

项目结构：
- src/frontend/：React 前端代码
- src/backend/：Node.js 后端代码
- prisma/：数据库模型

现在创建团队，在 src/auth/ 下添加用户认证功能
```

---

# 实践 6：先研究再实现

不要让成员直接开始编码

**两阶段流程**：
```
阶段 1：研究和设计
├─ 成员 A：调研现有的认证方案
├─ 成员 B：分析项目技术栈
└─ 成员 C：设计数据库表结构
    ↓
成员们通过消息系统讨论，确定最终方案
    ↓
阶段 2：实现
├─ 成员 A：实现后端认证逻辑
├─ 成员 B：实现前端登录页面
└─ 成员 C：编写测试
```

# Part 5
## 适用场景与成本分析

---

# 适合 Agent Teams 的场景

✅ **复杂系统重构**
- 涉及多个模块
- 模块之间有明确边界

✅ **多角度代码审查**
- 需要从多个维度审查代码

✅ **前后端并行开发**
- API 接口事先定义好

✅ **大型项目开发**
- 功能模块多，开发时间紧张

---

# 不适合 Agent Teams 的场景

❌ **简单修改任务**
- 变量重命名、单个 bug 修复
- 原因：启动团队的开销比实际干活时间还长

❌ **高度串行的任务**
- 任务 B 必须等任务 A 完成
- 原因：失去并行优势

❌ **成本敏感的任务**
- Token 预算有限
- 原因：Agent Teams 的成本是单实例的 2-4 倍

---

# 成本分析

| 团队规模 | 相对成本 | 适用场景 |
|---------|---------|---------|
| 1 人（单实例） | 1x | 简单任务 |
| 2 人团队 | 2-2.5x | 中等复杂度 |
| 3 人团队 | 3-4x | 复杂任务 |
| 5+ 人团队 | 5-6x+ | 大型项目 |

**在线商城案例**：
- Agent Teams（5 人）：约 $13
- 单实例：约 $1.65
- 成本倍数：约 8 倍
- 时间节省：从 5 天缩短到 2 天（节省 60%）

---

# 决策流程图

```
是否有多个独立的子任务？
    │
    ├─ 否 → 使用单实例
    │
    └─ 是 →
         │
         子任务是否可以分配给不同文件？
         │
         ├─ 否 → 考虑串行执行或拆分任务
         │
         └─ 是 →
              │
              成本是否可接受（2-4x）？
              │
              ├─ 否 → 使用单实例
              │
              └─ 是 → 使用 Agent Teams ✓
```
