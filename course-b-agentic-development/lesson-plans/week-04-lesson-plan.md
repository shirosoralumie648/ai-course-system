# 第 4 周教案：Context Engineering

## 1. 本讲定位

本讲聚焦 Context Engineering。前三周学生已经接触任务描述、Claude Code、Codex、测试和 diff，本讲把这些经验上升为“上下文工程”：如何为 Agent 提供足够、相关、可验证、不过量的上下文。

本讲为 Lab 03 Project Rules 做准备。Lab 03 中的 `CLAUDE.md` / `AGENTS.md` 可以理解为一部分上下文的持久化。

## 2. 学习目标

学生完成本讲后应能够：

- 说明为什么上下文决定 Agent 输出质量。
- 为小型代码任务整理代码库地图。
- 编写任务上下文、错误日志、测试命令和验收标准。
- 判断上下文过多和过少的问题。
- 要求 Agent 引用证据和说明不确定性。
- 为 Lab 03 准备规则文件所需信息。

## 3. 教学重点

- 上下文不是越多越好，而是要相关、准确、当前、可验证。
- 代码库地图、任务目标、相关文件、错误日志、测试命令、验收标准共同构成高质量上下文包。
- 禁止修改范围和 Human Gate 也是上下文。
- 上下文工程会发展为规则文件、Skill 和 Agent Team 工作流。

## 4. 教学难点

- 学生容易把整个仓库或大量无关聊天记录塞给 Agent。
- 学生容易只给需求不给测试命令。
- 学生容易引用过期文档或错误日志。
- 学生容易把“Agent 自己会找”当作不提供上下文的理由。

## 5. 课前准备

教师准备：

- 准备同一任务的两个输入：一句话坏上下文和结构化 context-pack。
- 准备 Lab 01 或 Lab 02 示例项目目录图。
- 准备 context-pack 模板。
- 准备几个上下文过多、过少、过期和缺少验收标准的案例。

学生准备：

- 带来 Lab 01 或 Lab 02 的实验记录。
- 准备一份自己写过的 Task Packet。
- 能说明自己实验中 Agent 哪一步误解或需要补充信息。

## 7. 教师讲解内容

### 7.1 为什么上下文决定 Agent 质量

Coding Agent 的输出质量依赖它看到的证据。上下文不足时，Agent 可能猜测项目结构、误解需求、漏跑测试。上下文过多时，关键约束会被淹没，过期信息可能污染判断。

好的上下文能让 Agent 明确：

- 当前要做什么。
- 为什么要做。
- 哪些文件相关。
- 哪些文件不能动。
- 当前失败或需求证据是什么。
- 如何验证完成。
- 哪些风险需要人工确认。

### 7.2 代码库地图

代码库地图不需要逐行解释整个项目。它应提供足够导航信息：

- 项目目标。
- 主要目录。
- 关键源文件。
- 关键测试文件。
- 入口命令。
- 当前任务相关路径。

示例结构：

```text
项目：repo-02-feature-development
用途：任务标题过滤工具
关键文件：
- src/todo_filter.py：业务函数
- tests/test_todo_filter.py：单元测试
测试命令：
- python -m unittest discover -s tests -v
本次任务相关：
- 新增 filter_titles_by_status(tasks, status)
```

### 7.3 任务上下文

任务上下文应回答：

- 目标是什么。
- 当前行为是什么。
- 期望行为是什么。
- 谁受影响。
- 相关文件是什么。
- 不应改变哪些行为。

### 7.4 错误日志

错误日志不应只粘贴巨大输出。学生应保留完整日志文件，同时在 Task Packet 中写摘要：

- 失败测试名。
- 错误类型。
- 关键栈信息。
- 当前推测。
- 需要 Agent 验证的问题。

### 7.5 测试命令

测试命令是 Agent 判断完成的重要依据。没有测试命令时，应说明替代验证方式。不能运行测试时，也必须写明原因和风险。

### 7.6 验收标准

验收标准必须可判断：

- 哪些测试通过。
- 哪些文件可以修改。
- 哪些行为必须保留。
- 输出报告应包含什么。
- 哪些风险需要人工确认。

### 7.7 上下文过多和过少

上下文过少的表现：

- 只有“帮我修 bug”。
- 没有路径。
- 没有测试命令。
- 没有禁止修改范围。

上下文过多的表现：

- 粘贴整个仓库和无关聊天记录。
- 混入过期需求。
- 同时要求多个不相关任务。
- 没有突出当前验收标准。

## 8. 学生练习

学生为 Lab 01 或 Lab 02 示例项目写 `context-pack.md` 初稿，至少包含：

- 项目一句话说明。
- 当前任务目标。
- 代码库地图。
- 相关文件。
- 错误日志或需求证据。
- 允许修改范围。
- 禁止修改范围。
- 测试命令。
- 验收标准。
- Human Gate。

同桌互评时重点检查：是否具体、是否过量、是否可验证。

## 9. 为 Lab 03 做准备

教师在结尾说明：第 5 周会把上下文工程的一部分固化为 `CLAUDE.md` 和 `AGENTS.md`。学生本周的 context-pack 可以直接转化为规则文件中的项目目标、目录结构、测试命令、允许和禁止范围、Human Gate。

## 10. 常见问题

**是不是把整个仓库都给 Agent 最好？**  
不是。Agent 可以读取仓库，但任务输入仍需突出相关文件、边界和验收标准。

**错误日志很长怎么办？**  
保留完整日志，但在上下文包中写关键摘要和失败测试名。

**没有自动测试怎么办？**  
写明无法自动测试的原因，提供手动验证步骤，并标记风险。

**上下文包和 Task Packet 有什么区别？**  
Task Packet 偏任务执行输入，context-pack 更强调为 Agent 提供项目证据、文件地图和验证信息。两者可以合并使用。

## 11. 评价方式

本周评价 `context-pack.md`：

| 维度 | 标准 |
| --- | --- |
| 相关性 | 包含当前任务需要的信息，没有大量无关内容 |
| 准确性 | 文件路径、测试命令、错误日志真实 |
| 边界 | 允许和禁止修改范围明确 |
| 验证 | 测试命令和验收标准可执行 |
| 风险 | 标明 Human Gate 和不确定项 |
