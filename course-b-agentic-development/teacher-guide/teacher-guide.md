# 教师授课指南：Agentic Development：AI 原生软件工程实践

## 1. 如何使用本课程仓库

教师备课建议按以下顺序阅读：

1. 阅读 `ai-course-system/README.md`，理解课程体系和当前阶段定位。
2. 阅读 `course-b-agentic-development/README.md`，确认课程 B 的目标、边界和 MVP 范围。
3. 阅读 `course-design/course-design.md`，把握正式课程设计、考核方式和风险对策。
4. 阅读 `syllabus.md` 和 `teaching-calendar.md`，安排 12 周教学节奏。
5. 使用 `lesson-plans/` 准备每周课堂流程。
6. 使用 `teacher-scripts/` 准备课堂讲解话术。
7. 使用 `slides-outline/` 制作或调整 PPT。
8. 使用 `labs/`、`examples/`、`templates/`、`skills/`、`mcp/` 和 `agent-team/` 组织实验。
9. 使用 `rubric.md` 和 `assessment/` 统一实验、作业和期末项目评分口径。

本仓库当前定位是第一阶段可上课材料，不应对学生宣称已经完成完整 V1.0 课程网站或完整 MCP Server 实现。

## 2. 上课前教师要检查什么

每次上课前，教师至少检查：

- 本周主题对应的 lesson plan、teacher script 或 script outline。
- 本周需要展示的示例项目是否存在。
- 固定测试命令能否运行。
- 是否需要隐藏教师参考材料和 `solution-notes.md`。
- 学生需要提交哪些证据。
- 本周是否涉及工具权限、网络访问、依赖安装或密钥风险。
- 助教是否理解本周 Rubric 和扣分点。
- 如 Claude Code / Codex 不可用，替代流程是否可执行。

第 1 周尤其要检查课程定位表达，避免学生误以为本课程只是 Prompt 技巧课或工具演示课。

## 3. 学生课前调查建议

开课前可发放简短问卷，建议包含：

- 是否有 Python 或 JavaScript 项目经验。
- 是否会使用 Git clone、branch、commit、diff。
- 是否能在终端运行测试命令。
- 是否使用过 ChatGPT、Copilot、Claude Code、Codex 或其他 Coding Agent。
- 是否理解 API Key、Token、`.env` 等敏感信息不能提交。
- 是否有可用于课程实验的本地电脑环境。
- 是否愿意在实验记录中公开部分 prompt、diff 和测试日志供教学讨论。

教师应根据调查结果决定是否增加环境准备课、是否安排助教值班、是否提供统一云端或容器环境。

## 4. 第一节课前环境准备

第 1 节课不要求所有学生立即完成 Claude Code 或 Codex 实验，但需要完成基础环境意识建立。建议课前发放以下检查项：

- Git 可用：能执行 `git --version`。
- 终端可用：能进入课程目录并列出文件。
- Python 可用：能执行 `python --version` 或 `python3 --version`。
- Node.js 可用：若后续课程需要，能执行 `node --version`。
- 能打开课程仓库并阅读 `README.md`、`labs/`、`examples/`。
- 理解不得提交 API Key、Token、密码、cookie、私钥和学生隐私数据。

如果工具安装未完成，第 1 节课仍可开展概念、Task Packet 和风险识别训练。不要让第一节课被工具安装完全占用。

## 5. 每节课通用教学流程

建议每节课都采用同一基本结构，形成稳定的工程训练节奏：

| 环节 | 目标 | 教师动作 |
| --- | --- | --- |
| 课前检查 | 确认材料、工具和学生准备情况 | 检查示例项目、测试命令、提交要求和替代流程 |
| 目标说明 | 说明本节课要解决的工程问题 | 用 2-3 个问题引出主题 |
| 概念讲解 | 建立判断框架 | 讲清概念、边界、风险和成功标准 |
| 教师演示 | 展示可审计流程 | 演示计划、修改、测试、diff、Review 或 Human Gate |
| 学生实操 | 让学生形成证据 | 学生按 Lab 或课堂任务操作并记录 |
| 结果提交 | 固化过程记录 | 收集 prompt、计划、diff、测试日志、复盘 |
| 课堂复盘 | 对比成功和失败案例 | 讨论 Agent 错误、人工判断和改进点 |
| 课后作业 | 延伸到个人项目或完整报告 | 明确提交文件、评分标准和截止时间 |

教师每次演示都应刻意停在关键节点，让学生判断是否继续，例如 Agent 提出计划后、准备修改文件前、测试失败后、diff 超出范围时。

## 6. 如何组织 Lab

组织 Lab 时建议采用“先示范、再限制、再放手”的节奏。

先示范：教师用投影展示一次完整流程，包括失败测试、任务描述、Agent 计划、人工确认、修改、测试、diff 审查和复盘。

再限制：学生第一次实验应使用课程给定示例项目、固定测试命令和明确允许/禁止范围。不要一开始让学生自由选择大型项目。

再放手：学生理解流程后，可在阶段作业或期末项目中迁移到自己的项目，但必须保留同样的证据链。

每个 Lab 的最低提交证据包括：

- 任务说明或 Task Packet。
- Agent 输入和输出摘要。
- 修改前后测试日志。
- Git diff 或 PR 链接。
- 人工审查结论。
- 失败、风险和复盘。

## 7. 如何批改 Lab

批改 Lab 时不要只看最终代码是否正确。建议按以下顺序检查：

1. 是否提交了完整文件。
2. 是否有原始失败或基线测试记录。
3. 是否有清楚的任务说明和边界。
4. 是否保留了 Agent 计划或关键输出摘要。
5. diff 是否在允许范围内。
6. 是否运行了固定测试命令。
7. 测试结果是否与提交内容一致。
8. 是否有人工 Review 或自检。
9. 是否说明 Human Gate 或高风险操作。
10. 复盘是否指出具体失败模式，而不是泛泛而谈。

对以下情况应扣分或要求返工：

- 未运行测试却声称通过。
- 删除或弱化测试。
- 修改禁止文件但不说明原因。
- 只提交 AI 输出，没有人工解释。
- 把工具不可用伪造成工具已完成。

## 8. 如何处理工具不可用

如果 Claude Code、Codex 或相关服务不可用，教师不要要求学生伪造工具记录。替代流程应保持同样的工程训练目标：

- 学生记录不可用原因和证据，例如版本检查失败、认证失败或网络不可用。
- 学生手动完成同一任务。
- 学生仍然提交任务说明、diff、测试日志和复盘。
- 学生补写“如果工具可用，我会如何给出 Task Packet”。
- 助教按工程证据评分，不因如实记录工具不可用直接判零。

如果大范围不可用，教师可把课堂重点改为 Task Packet、diff 审查、测试日志分析和 Human Gate 讨论。

## 9. 如何防止学生只复制答案

建议采用多层防护：

- 公开说明课程允许使用 AI，但必须记录 AI 做了什么、学生判断了什么。
- 教师参考材料和 `solution-notes.md` 不直接发给学生。
- Pilot 阶段制作 student-only 包，隐藏教师参考答案。
- Rubric 强调过程证据，缺少过程记录不能获得高分。
- 课堂抽查学生解释 diff 和测试失败原因。
- 同伴互评检查任务边界和 Review 质量。
- 对可疑提交要求现场运行测试或口头解释修改。

本课程的目标不是禁止 AI，而是禁止不可审计、不可解释、不可验证的 AI 使用。

## 10. 如何解释 Agentic Development

教师可以使用以下表达：

Agentic Development 不是“写一句 Prompt 让 AI 自动写代码”。它是把 Coding Agent 放进真实软件工程流程：先给出任务目标和上下文，再设置允许和禁止范围，然后要求 Agent 计划、小步修改、运行测试、输出 diff，最后由人进行 Review 和 Human Gate。

学生要学的不是某个工具按钮，而是如何提出任务、组织上下文、约束工具、验证结果、审查风险和复盘失败。Agent 可以提高效率，但责任不能转交给 Agent。

可以用四层结构解释：

- Chatbot：对话、解释、生成文本。
- Copilot：代码补全和局部辅助。
- Coding Agent：读取代码库、修改文件、运行命令、调用工具。
- Agentic Workflow：规则、权限、测试、Review、CI 和 Human Gate 共同约束 Agent 的工程流程。

## 11. 如何引导学生做复盘

复盘应回答具体问题，而不是写“本次实验收获很大”。教师可要求学生按以下结构写：

- 本次任务目标是什么。
- Agent 做对了什么。
- Agent 做错了什么或遗漏了什么。
- 哪些信息进入上下文后明显改善了输出。
- diff 是否符合允许范围。
- 测试是否真实运行，结果是什么。
- 哪些操作需要 Human Gate。
- 如果重做，会怎样改进 Task Packet、规则或 Skill。

课堂复盘可选择 1-2 个学生案例，重点讨论“为什么这个任务描述有效”或“为什么这个 diff 不应接受”。

## 12. 如何从 Alpha 进入 Pilot

Alpha 阶段目标是小范围验证材料是否能用，不是宣传课程已经完整成熟。进入 Pilot 前建议完成：

- 至少 2-3 名学生或助教完成 Lab 01 和 Lab 02。
- 记录工具安装失败、测试失败、学生误解和评分争议。
- 修订 Lab 文档、教师讲稿和 Rubric。
- 制作 student-only 示例项目包，隐藏 `solution-notes.md` 和教师参考材料。
- 确认第 1-4 周 lesson plan、teacher script / outline 和 slides outline 可支持授课。
- 确认助教能按 Rubric 批改同一份提交并给出接近评分。

Pilot 阶段仍应保留风险说明，不应宣称完整 V1.0 或完整课程网站已经完成。
