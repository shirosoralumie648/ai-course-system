# Lab 03：Project Rules

> **完成比完美重要。** 规则文件不需要一步到位，先写能用的，再迭代。

| 项目 | 内容 |
|---|---|
| **适用周次** | 第 5 周 |
| **预计时长** | 2-3 小时 |
| **核心产出** | CLAUDE.md + AGENTS.md + 有无规则对比记录 + 规则设计说明 + 复盘 |
| **前置条件** | 已完成 Lab 01 或 Lab 02；有一个小型项目可供 Agent 分析 |

**你将学到：**
- 规则文件为什么是 Agentic Development 的工程边界
- 如何编写具体、可执行、可审查的项目规则
- 有规则和无规则时 Agent 输出的实际差异

**实验步骤概览：**

```
① 无规则让 Agent 分析任务，记录输出    ⏱️ ~20min
② 编写 CLAUDE.md                       ⏱️ ~25min
③ 编写 AGENTS.md                       ⏱️ ~20min
④ 有规则再让 Agent 分析同一任务         ⏱️ ~20min
⑤ 对比两次输出，写设计说明和复盘        ⏱️ ~25min
```

**工具不可用怎么办？**
- 可以直接参照 Lab 01 或 Lab 02 的 Agent 输出记录做"模拟对比"
- 规则文件本身不依赖 Agent，手动编写即可
- 在报告中说明"本次对比基于历史记录而非实时运行"

## 1. 实验名称

Project Rules：为项目编写 `CLAUDE.md` 和 `AGENTS.md`。

## 5. 实验背景

无规则文件时，Agent 可能忽略项目结构、测试命令、禁止修改区域和安全边界。规则文件不是装饰品，而是项目级工程协议。

## 6. 使用工具

- Claude Code 或课程指定 Coding Agent。
- Markdown。
- Git diff。

## 7. 示例项目说明

示例项目优先使用 Lab 01 或 Lab 02 的小型项目：

- `../examples/repo-01-small-bugfix/`
- `../examples/repo-02-feature-development/`

项目应有基本目录结构、测试命令和可描述的修改边界。

固定验证命令：

```bash
python -m unittest discover -s tests -v
```

如果选择 `repo-01-small-bugfix/`，应在修复后运行该命令；如果选择 `repo-02-feature-development/`，应在新增功能后运行该命令。若本实验只做规则对比而不修改代码，必须在报告中说明未运行代码测试的原因。

## 8. 实验任务

1. 在无规则文件情况下让 Agent 分析一个任务，观察输出。
2. 编写 `CLAUDE.md` 和 `AGENTS.md`。
3. 再让 Agent 分析同一任务，观察输出差异。
4. 比较有规则和无规则的差别。

规则文件必须包括：

- 项目目标。
- 技术栈。
- 目录结构。
- 允许修改范围。
- 禁止修改范围。
- 测试命令。
- 构建命令。
- 代码风格。
- 安全规则。
- 提交规范。
- Review checklist。
- Agent 工作流程。
- Human Gate。

## 9. 操作步骤

1. 选择一个任务，例如“修复一个 bug”或“新增一个小参数”。
2. 在没有规则文件时让 Agent 分析任务，保存输出。
3. 根据模板编写 `CLAUDE.md` 和 `AGENTS.md`。
4. 再次让 Agent 分析同一任务。
5. 对比两次输出在修改范围、测试、风险识别和审批点上的差异。
6. 修订规则文件。

## 10. 记录要求

必须记录：

- 无规则时 Agent 输出。
- 有规则时 Agent 输出。
- 规则文件设计说明。
- 哪些规则改变了 Agent 行为。
- 哪些规则仍然不够清楚。

## 11. 预期结果

- `CLAUDE.md` 和 `AGENTS.md` 可以被复制到类似项目使用。
- Agent 输出更关注范围、测试、Review 和 Human Gate。
- 学生能解释规则对 Agent 行为的影响。

## 12. 提交要求

- `CLAUDE.md`。
- `AGENTS.md`。
- 对比记录。
- 规则设计说明。
- 复盘。

## 13. 提交检查表

- 是否提交实验记录。
- 是否提交关键 Prompt / Agent 指令。
- 是否提交无规则时的 Agent 输出。
- 是否提交有规则时的 Agent 输出。
- 是否提交 `CLAUDE.md` 和 `AGENTS.md`。
- 是否提交 Git diff。
- 是否提交测试结果或说明本实验未运行代码测试的原因。
- 是否提交失败记录，例如 Agent 仍然忽略规则的案例。
- 是否说明人工判断。
- 是否说明没有完成的部分；如果全部完成，明确写“无未完成项”。
- 是否有复盘。

## 14. 助教验收标准

- 文件是否齐全：规则文件、对比记录、设计说明、复盘。
- 任务是否完成：规则文件覆盖项目背景、允许范围、禁止范围、测试命令和 Human Gate。
- 测试是否真实：如有运行 Agent 或测试命令，记录必须可复查；如未运行测试，应说明原因。
- 是否存在伪造测试结果：不得把未运行的命令写成已通过。
- 是否符合规则边界：规则不得鼓励删除文件、大重构或绕过审批。
- 是否能解释 AI 修改结果：学生应能说明规则如何改变 Agent 输出。

## 15. 常见错误

- 规则只有“请写高质量代码”。
- 没有写测试命令。
- 没有禁止修改范围。
- 没有说明删除文件、依赖修改和外部访问需要 Human Gate。
- 规则过长但不可执行。

## 16. 拓展任务

- 为团队角色补充 Planner / Coder / Tester / Reviewer 规则。
- 把 Lab 01 或 Lab 02 中出现的问题写入规则文件。
- 请同学互评规则是否具体。

## 17. 评分标准

| 评分项 | 分值 | 优秀标准 | 合格标准 | 常见扣分 |
| --- | --- | --- | --- | --- |
| 规则具体性 | 30 | 范围、命令、流程、禁止行为清楚 | 有主要规则 | 大量空话 |
| 权限边界 | 25 | 覆盖文件、命令、网络、依赖、密钥 | 覆盖部分边界 | 无 Human Gate |
| 测试与 Review | 25 | 测试命令和 Review checklist 可执行 | 有测试说明 | 无验证要求 |
| 对比分析 | 20 | 能解释规则影响 | 有基本对比 | 只提交文件不分析 |

## 18. 复盘问题

1. 哪条规则最明显改变了 Agent 行为？
2. 哪条规则写得太模糊？
3. 如果 Agent 违反规则，你会如何处理？
4. 哪些内容应进入 `CLAUDE.md`，哪些应进入 `AGENTS.md`？
