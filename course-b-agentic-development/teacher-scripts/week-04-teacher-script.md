# 第 4 周教师讲稿：Context Engineering

## 0-10 分钟：从前两次 Lab 引入

各位同学，前两周我们分别用 Claude Code 和 Codex 做了 bugfix 和小功能开发。请大家回想一下：Agent 出错时，很多时候不是因为它完全不能处理任务，而是因为我们给它的信息不够清楚，或者边界不明确。

今天我们把这个问题系统化，主题是 Context Engineering，也就是上下文工程。

上下文工程不是把所有材料都贴给 AI，也不是写很长的 Prompt。它的目标是让 Agent 获得完成当前任务所需的准确证据、明确边界和可验证标准。

课堂提问：

- 在 Lab 01 或 Lab 02 中，Agent 有没有误解任务？
- 这个误解是因为缺少哪个信息？
- 如果重新做一次，你会补充什么上下文？

教师总结：

好的上下文能减少猜测，坏的上下文会放大幻觉。今天我们要学习如何组织代码库地图、任务上下文、错误日志、测试命令、验收标准和 Human Gate。

## 10-25 分钟：为什么上下文决定 Agent 质量

Coding Agent 的输出质量高度依赖它看到的证据。它不是项目成员，不知道你脑子里的需求，不知道哪些文件是历史遗留，不知道哪些测试不能改，也不知道哪些操作在你的团队里属于高风险。

如果上下文不足，Agent 可能会猜测。例如你只写“优化这个项目”，它可能会格式化大量文件、重构目录、改依赖，甚至碰到你本来不想改的模块。

如果上下文过多，也会出问题。你把整个仓库、旧需求、无关聊天记录和过期错误日志都塞进去，Agent 可能分不清当前任务重点，甚至被旧信息误导。

所以，上下文工程要解决的不是“多给”还是“少给”，而是“给正确的信息”。

高质量上下文至少包含：

```text
目标 + 代码库地图 + 相关文件 + 错误或需求证据 + 测试命令 + 验收标准 + 修改边界 + 风险与 Human Gate
```

课堂提问：

- 这几个部分中，哪一个最容易被你漏掉？
- 如果没有测试命令，Agent 会怎样判断完成？
- 如果没有禁止修改范围，Agent 可能做什么？

## 25-45 分钟：代码库地图

代码库地图是给 Agent 的导航。它不需要解释每一行代码，也不需要复制整个仓库。它要告诉 Agent：项目是什么，主要目录是什么，当前任务相关文件在哪里，测试如何运行。

以 Lab 02 项目为例，一个简单代码库地图可以这样写：

```text
项目：repo-02-feature-development
用途：任务标题过滤工具
关键文件：
- src/todo_filter.py：业务函数
- tests/test_todo_filter.py：单元测试
测试命令：
- python -m unittest discover -s tests -v
本次任务相关：
- 新增 filter_titles_by_status(tasks, status)
```

教师说明：

这样的地图很短，但它能帮助 Agent 快速定位。比起“你自己看一下整个项目”，它更明确；比起粘贴整个项目，它更聚焦。

课堂活动：

请大家选择 Lab 01 或 Lab 02 项目，用 3 分钟写一个代码库地图。只写与任务相关的目录和文件。

教师抽问：

- 你写了哪些文件？
- 哪些文件你没有写？为什么？
- 你的地图有没有测试入口？

## 45-65 分钟：任务上下文、错误日志和测试命令

代码库地图回答“项目在哪里”，任务上下文回答“这次要做什么”。

一个好的任务上下文应说明：

- 当前目标是什么。
- 当前行为是什么。
- 期望行为是什么。
- 相关文件是什么。
- 哪些旧行为不能被破坏。

如果任务来自测试失败，还要整理错误日志。错误日志不一定要全部贴进任务包，但要写出关键摘要。例如：

```text
失败测试：test_average_empty_list_returns_zero
错误类型：ZeroDivisionError
关键现象：average_score([]) 对空列表执行除法
期望行为：空列表平均值返回 0.0
```

教师说明：

错误日志是证据，不是噪音。我们要保留完整日志，同时给 Agent 一个清晰摘要。

测试命令同样重要。测试命令告诉 Agent 如何验证结果。没有测试命令时，Agent 可能只根据静态阅读判断“应该可以”，这不是可靠完成。

课堂提问：

- 如果错误日志很长，是否要完整粘贴？
- 如果没有自动测试，你应该写什么？
- 如果测试命令运行失败，是否可以写“测试通过”？

教师总结：

不能运行测试时，要写清楚环境原因和风险；不能把未运行的命令写成通过。

## 65-80 分钟：验收标准与 Human Gate

验收标准必须可判断。下面这句话不是好的验收标准：

```text
功能正常。
```

因为它无法判断。更好的写法是：

```text
新增测试通过；原有测试通过；diff 只修改 src/todo_filter.py 和 tests/test_todo_filter.py；不新增依赖；不改变 list_titles(tasks) 行为。
```

这就是可验证的标准。

Human Gate 也是上下文的一部分。它告诉 Agent 在哪些情况下不能继续执行，而要停下来等人确认。

必须进入 Human Gate 的情况包括：

- 修改测试。
- 删除文件。
- 新增或升级依赖。
- 访问外部服务。
- 处理密钥、Token、密码或隐私数据。
- 修改登录、权限、支付或安全敏感逻辑。
- 大规模重构。

教师说明：

Human Gate 的本质是责任边界。Agent 可以建议，但不能替人承担高风险决策。

## 80-95 分钟：上下文过少和过多的对比

请看一个上下文过少的例子：

```text
帮我优化一下这个项目，让它更好。
```

这个输入缺少目标、范围、测试、验收标准和风险边界。Agent 很可能会做一些看似有用但不符合任务的事情。

再看一个上下文过多的例子：

```text
这里是整个仓库、过去三周所有聊天记录、旧需求、无关错误日志和一堆未确认想法。请你修一下当前问题。
```

这个输入的问题是重点被稀释，旧信息可能与当前任务冲突，Agent 难以判断哪条是当前事实。

好的上下文应该像一份工程任务包：

- 当前目标明确。
- 相关文件准确。
- 错误或需求证据真实。
- 测试命令可执行。
- 验收标准可判断。
- 修改边界清楚。
- 高风险操作有 Human Gate。

课堂提问：

- 上下文过少会导致什么风险？
- 上下文过多会导致什么风险？
- 你如何判断某条信息是否应该进入 context-pack？

## 95-115 分钟：学生练习 context-pack

现在请大家为 Lab 01 或 Lab 02 写一份 `context-pack.md` 初稿。结构如下：

```markdown
# Context Pack

## 项目说明
## 当前任务
## 代码库地图
## 相关文件
## 错误日志或需求证据
## 允许修改范围
## 禁止修改范围
## 测试命令
## 验收标准
## Human Gate
```

请注意，今天不要求你写很多文字，但要求每一项具体。文件路径要真实，测试命令要可执行，禁止范围要明确。

同桌互评时，请检查五个问题：

- 是否相关？
- 是否准确？
- 是否过量？
- 是否可验证？
- 是否包含 Human Gate？

教师点评示例：

如果学生只写“运行测试”，教师应追问：“具体命令是什么？”

如果学生写“不要乱改”，教师应追问：“哪些文件不能改？哪些操作必须停止？”

如果学生贴了大量无关材料，教师应追问：“当前任务真正需要哪些证据？”

## 115-120 分钟：总结与作业

今天我们学习了 Context Engineering。请大家记住：上下文不是越多越好，而是要相关、准确、当前、可验证。

一个好的上下文包至少包括目标、代码库地图、相关文件、错误或需求证据、测试命令、验收标准、修改边界和 Human Gate。

下周我们会把一部分上下文固化为项目规则文件，也就是 `CLAUDE.md` 和 `AGENTS.md`。你们今天写的 context-pack 可以直接成为规则文件的素材。

- 提交 `context-pack.md`。
- 标注哪些内容可以进入长期规则文件。
