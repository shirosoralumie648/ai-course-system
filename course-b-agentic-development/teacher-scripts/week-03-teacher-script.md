# 第 3 周教师讲稿：Codex 基础与 Lab 02

## 0-10 分钟：从 Bugfix 过渡到小功能开发

各位同学，上节课我们用 Claude Code 完成了 Lab 01 的 bugfix 流程。请大家回忆一下，我们不是只看最后代码是否改对，而是看了失败测试、任务包、Agent 计划、Git diff、测试结果和人工复盘。

今天我们进入 Lab 02：Codex Code Change。本周任务不是修复一个已有失败测试，而是新增一个小功能。这两类任务有一个关键区别：bugfix 通常从失败测试开始，小功能开发则需要我们主动写出验收标准，并补充新的测试。

课堂提问：

- 修 bug 和新增功能，哪个更容易漏掉测试？
- 如果新增功能没有测试，我们如何证明它真的可用？
- 如果新功能通过了，但旧功能坏了，这算完成吗？

教师总结：

本节课我们关注三件事：第一，Codex 的本地任务流程；第二，小功能开发中的新增测试和回归验证；第三，Codex 与 Claude Code 的证据化对比。

## 10-25 分钟：Codex 是什么

Codex 在本课程中同样被视为 Coding Agent。它可以接收任务、制定计划、读取和修改本地文件、运行命令，并在某些操作前请求权限或等待确认。

我们今天不把 Codex 当作“另一个自动写代码工具”来学习，而是把它放进同样的工程流程中：

```text
任务包 -> 计划 -> 权限确认 -> 修改 -> 新增测试 -> 运行测试 -> 查看 diff -> 工具对比 -> 复盘
```

Codex 的一个重要教学点是 sandbox 和 approval。sandbox 可以理解为工具操作的影响范围，approval 可以理解为高风险动作前的人工确认。它们不是麻烦，而是工程安全机制。

课堂提问：

- 如果 Codex 要安装一个新依赖，你会直接允许吗？
- 如果 Codex 要删除一个看起来没用的文件，你会怎么判断？
- 如果 Codex 要访问外部网络，你需要先确认什么？

教师说明：

任何涉及依赖、删除、网络、密钥、权限、安全敏感逻辑的操作，都不能默认批准。Agent 可以提出理由，但批准权在人。

## 25-40 分钟：Codex 与 Claude Code 的对比

请大家不要简单写“Claude Code 更好”或“Codex 更好”。课程要求的工具对比必须基于证据。

我们可以从以下维度观察：

- 任务输入：工具如何接收 Task Packet。
- 上下文读取：工具如何理解当前项目。
- 计划呈现：工具是否先说明修改文件和步骤。
- 权限请求：工具是否提示高风险操作。
- diff 呈现：学生能否清楚看到实际修改。
- 测试执行：工具是否运行指定测试，结果是否可复查。
- 总结质量：工具是否区分事实、推测和风险。

教师话术：

今天你们的对比记录应写成“在本次 Lab 02 中，我观察到 Codex 在某个环节如何表现；和 Lab 01 中 Claude Code 的记录相比，有哪些差异”。不要写泛化宣传，不要写没有证据的判断。

课堂提问：

- 一个工具对比结论需要哪些证据支持？
- 如果两个工具都能完成任务，我们还需要比较什么？

过渡语：接下来我们看本周的具体功能需求。

## 40-55 分钟：Lab 02 需求与验收标准

本周示例项目路径是：

```text
ai-course-system/course-b-agentic-development/examples/repo-02-feature-development/
```

这是一个任务标题过滤工具。当前已有函数 `list_titles(tasks)`，已有测试应当通过。我们要新增函数：

```text
filter_titles_by_status(tasks, status)
```

这个函数的需求是：

- 返回指定 `status` 的任务标题列表。
- 支持 `pending`、`done` 等状态。
- 没有匹配任务时返回空列表。
- 保留原始任务顺序。
- 不改变原有任务数据结构。
- 不破坏 `list_titles(tasks)` 的行为。

请注意，这些需求都要变成测试或可检查标准。不能只写“实现状态过滤功能”。我们要知道什么输入应该得到什么输出，什么旧行为必须保留。

课堂提问：

- 你会为这个函数写哪些测试？
- “保持原始顺序”应该如何验证？
- “不破坏原有行为”对应什么检查？

教师总结：

小功能开发的最低完成标准是：新增功能有测试，原有测试仍通过，diff 在允许范围内，学生能解释实现和测试覆盖。

## 55-75 分钟：教师演示 Codex 任务流程

我们先进入项目目录，运行基线测试：

```bash
python -m unittest discover -s tests -v
```

基线测试的意义是确认修改前项目状态。如果基线测试已经失败，我们就不能把之后的失败都归因于本次修改。

现在我们给 Codex 输入任务包：

```text
请在当前 Python 项目中新增 filter_titles_by_status(tasks, status)。

需求：
- 返回指定 status 的任务标题列表。
- 保持原始顺序。
- 没有匹配任务时返回空列表。
- 不改变 list_titles(tasks) 的原有行为。

允许修改：
- src/todo_filter.py
- tests/test_todo_filter.py

禁止修改：
- teacher-guide.md
- solution-notes.md
- 删除或弱化已有测试
- 新增外部依赖

请先给出计划和拟修改文件，确认后再小步修改。
修改后运行：
python -m unittest discover -s tests -v
```

教师演示时请在三个节点暂停：

第一，Codex 输出计划后暂停。请学生判断计划是否包含新增测试，是否保留原有行为。

第二，Codex 请求权限时暂停。请学生判断请求是否合理，是否涉及依赖、网络或删除文件。

第三，Codex 修改完成后暂停。先看 `git diff`，再运行测试。

课堂提问：

- 这个计划是否包含测试？
- 允许修改测试文件是否等于可以删除旧测试？
- 如果 Codex 只实现函数但不写测试，你应该如何要求它补充？

## 75-95 分钟：diff、测试和原有行为保护

修改完成后，请运行：

```bash
git diff
```

我们要检查三类内容：

第一，源代码是否新增了 `filter_titles_by_status`，并且实现逻辑清楚。

第二，测试文件是否新增了对状态过滤的测试，同时没有删除或弱化旧测试。

第三，是否没有改动教师材料、参考答案、依赖配置或无关文件。

接着运行测试：

```bash
python -m unittest discover -s tests -v
```

教师说明：

如果新增测试通过，但旧测试失败，这说明新功能可能破坏了原有行为。如果旧测试通过，但没有新增测试，也不能证明新功能满足需求。

接受本次修改前，请学生写出判断：

```text
我是否接受本次修改：
理由：
1. 新增功能测试：
2. 原有行为测试：
3. diff 范围：
4. 权限请求：
5. 仍需注意的风险：
```

## 112-120 分钟：总结与作业

今天我们从 bugfix 进入了小功能开发。小功能开发有三个关键要求：

第一，需求必须写成验收标准。第二，新增功能必须有测试。第三，原有行为必须继续通过测试。

Codex 与 Claude Code 的差异不应写成主观评价，而应写成证据化观察。例如“在本次任务中，Codex 对权限请求的呈现方式是怎样的”“它是否主动运行了测试”“我是否能清楚看到 diff”。

课后提交：

- Lab 02 实验记录。
- Codex Task Packet。
- Codex 计划和输出摘要。
- 权限请求和人工决定记录。
- Git diff。
- 基线测试和最终测试日志。
- Claude Code 与 Codex 对比记录。
