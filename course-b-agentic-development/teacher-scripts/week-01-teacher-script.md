# 第 1 周教师讲稿：AI 原生软件工程导论

## 0-10 分钟：开场与课程定位

各位同学，欢迎进入《Agentic Development：AI 原生软件工程实践》。

这门课的主题不是“让 AI 帮忙写代码”。如果只是让 AI 生成一段函数、解释一段代码，或者帮我们写一份 README，那还停留在普通 AI 辅助层面。本课程要训练的是更接近真实软件工程的能力：如何让 Coding Agent 进入代码库，理解任务，按照规则工作，运行测试，输出 diff，接受 Review，并在关键节点等待人工确认。

请大家从第一节课开始记住一句话：Agent 可以参与工程流程，但不能替代工程责任。工具输出“完成”不等于任务完成；测试通过也不代表所有风险消失。我们要学习的不是相信 Agent，而是设计、约束、验证和审查 Agent。

本课程会涉及 Claude Code、Codex、`CLAUDE.md`、`AGENTS.md`、Skill、MCP、Subagents、Agent Team、测试、Review、CI 和 Human Gate。这些名词今天不需要全部掌握，但大家需要先建立一个总框架：AI 编程已经从简单对话，发展到能够参与真实代码任务的 Agent；而真实代码任务必须有工程边界。

过渡语：接下来我们先讨论一个问题，大家平时到底怎样使用 AI 工具。

## 10-25 分钟：学生 AI 使用现状讨论

请大家思考并回答一个问题：你最近一次使用 AI 辅助编程，是让它做了什么？

可以是解释代码、生成函数、写正则、查报错、写测试、改 bug、写文档，也可以是帮你理解一个开源项目。

课堂提问：

- 有多少同学主要把 AI 当作问答工具？
- 有多少同学使用过代码补全工具？
- 有多少同学让 AI 直接改过项目文件？
- 有多少同学在 AI 改完后看过 Git diff？
- 有多少同学保存过 AI 的计划、测试日志和失败记录？

教师说明：

从这些回答可以看到，大家已经在不同程度上使用 AI 编程工具。但使用 AI 不等于掌握 Agentic Development。很多同学会让 AI 生成代码，却没有明确告诉它能改什么、不能改什么；会看 AI 的解释，却没有运行测试；会接受 AI 的修改，却没有审查 diff。

这正是本课程要训练的能力。未来的软件工程并不是简单变成“人不写代码，AI 写代码”。更准确地说，软件工程正在从“人单独写代码”转向“人与 Agent 在工程流程中协作完成任务”。人的重要能力会从背语法、记 API，逐渐转向提出任务、组织上下文、约束工具、验证结果、审查风险和复盘过程。

过渡语：要理解这种变化，我们先区分四个概念：Chatbot、Copilot、Coding Agent 和 Agentic Workflow。

## 25-45 分钟：四个概念区分

请看这四个概念。它们经常被混在一起，但在工程教学中必须区分。

| 概念 | 主要能力 | 典型使用方式 | 工程边界 |
| --- | --- | --- | --- |
| Chatbot | 对话、解释、总结、生成文本 | 问问题、让它解释报错或生成代码片段 | 不直接读取和修改完整代码库 |
| Copilot | 代码补全、局部建议 | 在编辑器中补全函数、变量、测试片段 | 开发者实时判断和接管 |
| Coding Agent | 读取代码库、制定计划、修改文件、运行命令、调用工具 | 处理 bugfix、小功能、测试、文档、Review 等任务 | 必须受上下文、规则、权限和测试约束 |
| Agentic Workflow | 把 Agent 放入有规则、有测试、有 Review、有 Human Gate 的工程流程 | 团队化、可审计、可复盘的 AI 原生开发流程 | 关注责任、证据链和安全边界 |

Chatbot 的典型例子是：你把一段错误日志贴进去，问“这是什么意思”。它可以解释，但它通常不知道你的完整项目状态，也不会直接修改你的仓库。

Copilot 的典型例子是：你正在写函数，它给你补全几行代码。这个过程中，主动权主要还在开发者手里。你看见建议，决定是否接受。

Coding Agent 不同。它可能读取多个文件，提出计划，修改源代码，运行测试命令，调用外部工具，最后告诉你它完成了任务。它的能力更强，所以风险也更高。它可能误解需求、修改无关文件、删除重要内容、修改测试让结果通过，或者在没有实际运行测试时说“测试通过”。

Agentic Workflow 是本课程真正关注的对象。它不是一个具体工具，而是一种工程流程：Agent 必须在规则中工作，在权限边界内行动，用测试和 Review 证明结果，并在危险操作前等待 Human Gate。

课堂提问：

- 如果一个 AI 只给你解释错误日志，它更像哪一类？
- 如果一个工具在编辑器里补全一行代码，它更像哪一类？
- 如果一个工具能修改文件并运行测试，它为什么需要更强的约束？
- Agentic Workflow 和“让 AI 自动写代码”最大的差别是什么？

教师总结：

本课程不是要大家记住这些词，而是要大家用这些词判断任务边界。不同层级的工具可以做不同任务，需要不同的监督强度。

过渡语：既然 Coding Agent 能参与工程任务，我们接下来画一张任务地图，看看哪些任务适合交给 AI 或 Agent 辅助。

## 45-65 分钟：AI / Agent 可代劳任务地图

在软件工程中，AI / Agent 可以代劳或辅助的任务大致分成 8 类。

第一类是理解类任务。例如解释代码、总结项目结构、梳理模块职责、阅读 README 和测试。这类任务适合作为入门，但仍然需要学生核对文件路径和实际代码。

第二类是规划类任务。例如拆分开发任务、生成修改计划、列出风险和验收标准。这类任务很有价值，因为它可以帮助我们在动手前看清任务，但计划不能直接等于批准。

第三类是编码类任务。例如修复小 bug、新增小功能、改一个参数、补一个边界条件。这类任务适合 Agent，但必须限制修改范围，并要求测试验证。

第四类是测试类任务。例如生成测试、运行测试、分析失败日志、补充边界用例。这类任务能提高质量，但不能允许 Agent 修改测试来掩盖问题。

第五类是审查类任务。例如看 diff、查风险、检查需求符合度、检查安全问题。Agent 可以帮助初步 Review，但最终判断仍然需要人。

第六类是文档类任务。例如 README、API 文档、PR 描述、实验报告草稿。文档任务也需要核对事实，不能让 AI 编造未发生的测试和功能。

第七类是自动化类任务。例如脚本、CI、格式化检查和简单的质量门禁。这里要注意命令权限，不能让 Agent 随意安装依赖、删除文件或访问外部服务。

第八类是工作流类任务。例如设计 Skill、MCP、Agent Team，把重复流程固化下来。这是本课程后半部分的重要内容。

接下来请大家看另一边：哪些任务不能完全交给 AI？

- 删除大量文件。
- 修改依赖。
- 修改权限、登录、支付。
- 处理密钥。
- 合并 PR。
- 发布线上版本。
- 安全敏感改动。

这些任务不是绝对不能让 AI 参与分析，而是不能让 AI 默认执行。它可以解释风险、提出方案、列出 checklist，但执行前必须进入 Human Gate。

课堂提问：

- 为什么“修改依赖”需要人工确认？
- 为什么“测试通过”不能证明登录和支付逻辑一定安全？
- 如果 Agent 发现一个文件似乎没用，能不能让它直接删除？

教师说明：

Agent 的能力越接近真实工程操作，就越需要边界。我们不是要限制效率，而是要避免把不可逆、高风险、不可审计的操作交给工具默认执行。

过渡语：那么，怎样把一个模糊想法变成 Agent 可以安全执行的任务？这就需要 Task Packet。

## 65-85 分钟：Task Packet 概念

Task Packet 可以翻译为“任务包”。它不是一句 Prompt，而是一份结构化的工程任务说明。一个好的 Task Packet 能让 Agent 知道目标是什么、上下文在哪里、能改什么、不能改什么、如何验证、如何汇报，以及哪些操作必须等待人工确认。

Task Packet 至少包含 8 个部分。

第一，目标。要明确要解决什么问题，期望行为是什么。比如“修复 average_score([]) 抛出 ZeroDivisionError 的问题，使其返回 0.0”。

第二，上下文。说明项目背景、相关路径、错误现象、相关测试和已有约束。上下文不是越多越好，而是要相关、准确、当前。

第三，允许修改范围。告诉 Agent 哪些文件可以修改。例如“只允许修改 `src/grade_utils.py`”。

第四，禁止修改范围。告诉 Agent 哪些文件、目录、行为不能动。例如“不允许修改 `tests/`，不允许修改 `solution-notes.md`，不允许新增依赖”。

第五，测试命令。给出必须运行的命令。例如：

```bash
python -m unittest discover -s tests -v
```

第六，验收标准。说明什么结果算完成。比如“5 个测试全部通过，diff 只集中在业务代码，学生能解释修改原因”。

第七，输出格式。要求 Agent 最后输出任务摘要、修改文件、diff 摘要、测试命令和结果、风险与不确定点。

第八，Human Gate。说明哪些操作必须先停下来等人工确认。例如修改测试、删除文件、安装依赖、访问外部服务、处理密钥、大规模重构。

请大家注意：Task Packet 不是为了把 Prompt 写得很长，而是为了让任务可执行、可审查、可验收。

过渡语：下面我们看一个坏例子和一个好例子。

## 85-100 分钟：教师演示：坏任务描述与好 Task Packet

先看坏任务描述：

```text
帮我修一下这个 bug。
```

如果你把这句话交给 Coding Agent，它会面临很多不确定性。它不知道哪个项目、哪个文件、哪个 bug、能改什么、不能改什么、测试命令是什么、完成标准是什么。Agent 可能会自己猜，也可能会修改过多文件。

课堂提问：

- 这句话缺少哪些信息？
- 如果 Agent 想修改测试让它通过，你在这句话里阻止了吗？
- 如果 Agent 想安装新依赖，你在这句话里阻止了吗？

现在看一个更好的任务包：

```text
目标：
修复成绩统计项目中 average_score([]) 抛出 ZeroDivisionError 的问题，并确认 pass_rate 中 60 分应计为及格。

上下文：
项目路径是 ai-course-system/course-b-agentic-development/examples/repo-01-small-bugfix/。
相关文件包括 src/grade_utils.py 和 tests/test_grade_utils.py。
当前测试命令为 python -m unittest discover -s tests -v。

允许修改范围：
只允许修改 src/grade_utils.py。

禁止修改范围：
不要修改 tests/、README.md、teacher-guide.md、solution-notes.md。
不要删除测试，不要新增外部依赖，不要做无关重构。

工作流程：
先说明失败原因、修改计划和拟修改文件，等待我确认后再修改。
修改后运行固定测试命令。

验收标准：
测试全部通过。
diff 只集中在 src/grade_utils.py。
能解释为什么空列表返回 0.0，为什么 60 分计为及格。

输出格式：
请输出任务摘要、修改文件、diff 摘要、测试命令和结果、仍需人工确认的风险。

Human Gate：
如果需要修改测试、依赖、多个目录或访问外部服务，必须先停止并请求确认。
```

教师讲解：

这个任务包的价值在于它让 Agent 的行动可以被检查。我们可以检查它是否只改了允许文件，是否运行了指定测试，是否遵守了禁止范围，是否在高风险操作前停下来。

演示说明：

教师可以打开示例项目，展示 `src/grade_utils.py` 和 `tests/test_grade_utils.py`，但本节课不需要完整完成 Lab 01。重点是让学生看到：一个任务包如何把模糊请求变成工程流程。

过渡语：现在请大家把这个结构应用到自己的问题上。

## 100-110 分钟：课堂活动：学生写自己的 Task Packet

请每位同学选择自己最近遇到的一个代码问题。这个问题可以很小，例如一个测试失败、一个函数边界条件、一个 README 不清楚、一个命令行参数需要新增。不要选择很大的系统重构。

请在 8 分钟内写出一个 Task Packet，至少包含：

- 目标。
- 上下文。
- 允许修改范围。
- 禁止修改范围。
- 测试命令或验证方式。
- 验收标准。
- 输出格式。
- Human Gate。

写完后，请和旁边同学互换。互评时只看一件事：这个任务包是否足以让 Agent 安全开始工作。如果缺少信息，请直接标出来。

教师巡视时可重点看：

- 学生是否写了具体路径。
- 是否有禁止范围。
- 是否有测试命令。
- 是否写了“先计划，再确认”。
- 是否把大任务拆小。

教师抽 1-2 个例子点评：

这个例子的目标比较清楚，但禁止范围还不够。比如你说“修改登录逻辑”，这涉及权限和安全，至少要写明不能修改数据库 schema、不能输出密钥、不能绕过现有认证测试。

或者：

这个例子的测试命令写得很好，但验收标准还需要更具体。不要只写“功能正常”，要写“新增测试通过，原有测试仍通过，diff 不修改已有公共 API”。

过渡语：最后我们把今天的内容收束到后续课程路径。

## 110-120 分钟：总结、后续预告与作业

今天我们建立了本课程的基础框架。

第一，AI 编程工具已经从 Chatbot、Copilot 发展到 Coding Agent。Coding Agent 能读代码、改文件、运行命令、调用工具，所以它必须被工程流程约束。

第二，Agentic Development 不是 Prompt 技巧课，也不是工具演示课。它训练的是任务表达、上下文组织、规则约束、测试验证、diff 审查、权限控制和 Human Gate。

第三，我们画了 AI / Agent 可代劳任务地图。理解、规划、编码、测试、审查、文档、自动化和工作流任务都可以让 AI 参与，但删除大量文件、修改依赖、处理密钥、合并 PR、发布版本和安全敏感改动不能默认交给 AI 执行。

第四，我们学习了 Task Packet。以后大家给 Coding Agent 下任务时，不要只写“帮我修一下”。要写目标、上下文、允许范围、禁止范围、测试命令、验收标准、输出格式和 Human Gate。

后续课程安排如下：

- Lab 01：Claude Code Bugfix。我们会让 Claude Code 处理一个真实失败测试，要求它先计划、再修改、再测试、再输出 diff。
- Lab 02：Codex Code Change。我们会用 Codex 做一个小功能开发，并比较不同 Agent 的交互方式。
- Lab 03：Project Rules。我们会写 `CLAUDE.md` / `AGENTS.md`，把工程规则固化下来。
- Lab 04：Code Review Skill。我们会把 Review 流程封装成可复用 Skill。

作业布置：

1. 完成环境检查。请检查 Git、终端、Python 或 Node.js 是否可用，并记录命令输出摘要。Claude Code 或 Codex 如果暂时不可用，也要记录原因，不要伪造。
2. 完成一份自己的 Task Packet。可以基于刚才课堂练习修订，提交为 `week-01-task-packet.md`。
3. 阅读 `labs/lab-01-claude-code-bugfix.md`。
4. 准备下节课运行示例项目 `ai-course-system/course-b-agentic-development/examples/repo-01-small-bugfix/`。

结束语：

下节课我们会进入第一个真实 Coding Agent 实验。请大家带着今天的判断框架来看：Agent 如何理解任务，准备改哪些文件，实际改了什么，测试是否真实运行，最终是否应该由人接受。
