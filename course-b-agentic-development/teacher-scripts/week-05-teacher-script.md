# 第 5 周教师讲稿：CLAUDE.md / AGENTS.md / Rules

## 0-10 分钟：从上下文包到规则文件

各位同学，上节课我们学习了 Context Engineering。大家已经写过 `context-pack.md`，其中包含项目说明、相关文件、测试命令、允许范围、禁止范围和 Human Gate。

今天我们要把其中一部分内容固化下来，变成项目级规则文件。主题是 `CLAUDE.md` / `AGENTS.md` / Rules。

规则文件的作用不是装饰项目，也不是写给老师看的说明文。它是给 Coding Agent 的工程协议：项目是什么、技术栈是什么、能改什么、不能改什么、测试怎么跑、哪些操作必须人工确认。

课堂提问：

- context-pack 和规则文件有什么区别？
- 哪些信息是每次任务都应该重复出现的？
- 如果没有规则文件，Agent 可能忽略什么？

教师总结：

context-pack 更偏一次任务；规则文件更偏长期约束。今天的目标是让大家写出具体、可执行、可审查的规则，而不是空泛口号。

## 10-25 分钟：什么是项目规则

项目规则是 Agent 在当前仓库工作的基本协议。它应该告诉 Agent：

- 项目目标和当前阶段。
- 技术栈和运行方式。
- 目录结构。
- 允许修改范围。
- 禁止修改范围。
- 测试和构建命令。
- 代码风格。
- 安全规则。
- 提交流程和 Review checklist。
- Human Gate。

教师说明：

请大家特别注意“可执行”三个字。规则不能只写“请写高质量代码”。这句话听起来正确，但没有执行标准。更好的规则是：“修改 Python 业务逻辑后必须运行 `python -m unittest discover -s tests -v`；不得修改 `tests/` 来绕过失败；测试失败必须记录原因。”

课堂提问：

- “不要乱改文件”为什么不是好规则？
- “只允许修改 `src/` 和本任务指定文件”为什么更好？
- “保持代码整洁”如何变成可检查规则？

## 25-45 分钟：CLAUDE.md 与 AGENTS.md 的教学定位

在真实工具生态中，不同 Agent 可能读取不同规则文件。课程中我们重点训练两类：

- `CLAUDE.md`：可作为 Claude Code 的项目规则和工作协议。
- `AGENTS.md`：可作为通用 Coding Agent 的项目约束说明。

两者在课程中的共同目标是：减少重复说明，让 Agent 每次进入项目时都能看到稳定规则。

教师展示模板：

请打开：

```text
ai-course-system/course-b-agentic-development/templates/AGENTS.md
ai-course-system/course-b-agentic-development/templates/CLAUDE.md
```

教师讲解：

模板不是让大家照抄，而是提供结构。你们要根据自己的项目填写具体内容。例如测试命令不能写“运行项目测试”，要写实际命令；禁止范围不能写“敏感文件”，要列出 `.env`、`*.key`、`credentials.*` 等。

课堂提问：

- 模板中哪些部分必须改成项目具体信息？
- 哪些部分可以作为通用安全规则保留？

## 45-65 分钟：无规则与有规则对比

现在我们做一个对比实验。先在没有规则文件的情况下，让 Agent 分析一个任务。例如：

```text
请分析这个项目中如何修复成绩统计 bug。
```

观察它是否主动提到测试命令、禁止修改范围、Human Gate 和安全风险。

然后加入 `CLAUDE.md` / `AGENTS.md`，再次让 Agent 分析同一任务。

教师说明：

我们不是要证明规则文件一定让 Agent 完美，而是要观察规则是否改变了 Agent 的注意力。如果 Agent 开始主动提到测试、diff、禁止修改测试和人工确认，说明规则产生了影响。

课堂提问：

- 有规则前后，Agent 的计划有什么不同？
- 它是否更明确地提到允许和禁止范围？
- 它是否仍然忽略了某些规则？

教师总结：

规则文件不是一次写完就永远正确。它需要根据 Agent 的失败案例不断修订。

## 65-85 分钟：规则文件中的 Human Gate

Human Gate 必须写进规则文件。因为危险操作不是只在某个任务中出现，而是在任何工程任务中都可能出现。

规则文件中可以这样写：

```text
以下操作必须先停止并请求人工确认：
- 删除文件或目录。
- 大规模重构。
- 修改依赖。
- 访问外部服务。
- 读取、输出或提交密钥、Token、密码和隐私数据。
- 修改认证、权限、支付或安全敏感逻辑。
- 测试失败但想继续提交。
```

教师说明：

Human Gate 不应写成“重要操作要小心”。要列出具体触发条件。Agent 看到具体条件，才更可能停止。

课堂活动：

请学生为自己的规则文件写一段 Human Gate，至少包含 6 个触发条件。

教师点评时检查：

- 是否覆盖删除、依赖、网络、密钥、安全敏感逻辑。
- 是否说明 Agent 应该停止并请求确认。
- 是否避免写成空泛提醒。

## 85-105 分钟：Lab 03 操作说明

Lab 03 的任务是 Project Rules。学生需要：

1. 在无规则文件情况下让 Agent 分析一个任务，保存输出。
2. 编写 `CLAUDE.md` 和 `AGENTS.md`。
3. 再让 Agent 分析同一任务，保存输出。
4. 对比两次输出。
5. 修订规则文件。

提交物包括：

- `CLAUDE.md`。
- `AGENTS.md`。
- 无规则时 Agent 输出。
- 有规则时 Agent 输出。
- 规则设计说明。
- 复盘。

教师强调：

Lab 03 不只看你有没有文件，还看规则是否具体、可执行、可审查。只写“请写高质量代码”“不要出错”“遵守最佳实践”是不合格的。

课堂提问：

- 如果规则没有测试命令，会造成什么问题？
- 如果规则没有禁止范围，Agent 可能怎样扩大任务？
- 如果规则没有 Review checklist，学生如何判断 diff？

## 105-115 分钟：学生开始编写规则

请大家选择 Lab 01 或 Lab 02 示例项目，开始写规则文件初稿。

最低要求：

- 项目目标。
- 技术栈。
- 目录结构。
- 允许修改范围。
- 禁止修改范围。
- 测试命令。
- 安全规则。
- Review checklist。
- Human Gate。

教师巡视时重点检查：

- 测试命令是否真实。
- 文件路径是否具体。
- 禁止范围是否清楚。
- Human Gate 是否具体。

## 115-120 分钟：总结与作业

今天我们把上下文工程推进到项目级规则。请记住，规则文件的价值在于让 Agent 每次工作前都看到稳定边界。

课后请完成 Lab 03，并提交规则文件、前后对比记录和复盘。下周我们会继续讨论权限、Hooks 与安全边界，把规则中的 Human Gate 进一步细化。
