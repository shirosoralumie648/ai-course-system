# 第 2 周教师讲稿：Claude Code 基础与 Lab 01

## 0-10 分钟：回顾与导入

各位同学，上节课我们讨论了从 Chatbot 到 Coding Agent 的变化，也学习了 Task Packet 的结构。今天我们要把这个结构真正用到代码库任务中。

本节课的主题是 Claude Code 基础与 Lab 01。请大家注意，本节课不是为了证明 Claude Code 一定能一次写对代码，也不是让大家把 bug 全部交给工具。我们的目标是观察一个 Coding Agent 如何读项目、如何理解失败测试、如何提出计划、如何修改文件、如何运行测试，以及我们如何审查它的 diff。

请大家先回忆一个问题：如果你只输入“帮我修一下 bug”，这个任务缺少什么？

课堂提问：

- 它有没有说明项目路径？
- 有没有说明允许修改哪些文件？
- 有没有说明禁止修改哪些文件？
- 有没有说明测试命令？
- 有没有说明什么情况下必须等人工确认？

教师总结：

今天我们会把这些缺失项补上。Lab 01 的核心不是“让 Claude Code 修好一个小 bug”，而是训练一条可审计流程：先有失败证据，再有任务包，再看计划，再确认修改，再看 diff，再运行测试，最后由人决定是否接受。

过渡语：我们先明确 Claude Code 在本课程中的定位。

## 10-25 分钟：Claude Code 是什么

Claude Code 是面向代码库任务的 Coding Agent。它和普通 Chatbot 的区别在于，它不仅可以回答问题，还可以在代码库中读取文件、理解项目结构、提出修改计划、编辑文件、运行命令并总结结果。

这听起来很强，但也意味着风险更真实。一个只会聊天的工具如果答错了，通常只是给出错误建议；一个能改文件和跑命令的 Agent 如果误解了任务，可能会修改无关文件、删除测试、引入新依赖，或者在没有真实测试证据时声称已经完成。

所以我们使用 Claude Code 时，要把它放进工程流程，而不是让它自由发挥。本节课采用的基本流程是：

```text
运行基线测试 -> 提供 Task Packet -> 要求先计划 -> 人工确认 -> 小步修改 -> 查看 diff -> 运行测试 -> 人工接受或拒绝
```

请大家把这条流程写下来。后续所有 Lab 都会反复使用类似流程，只是工具、任务和交付物不同。

课堂提问：

- 为什么要先运行基线测试？
- 为什么要先看计划再允许修改？
- 为什么测试通过以后仍然要看 diff？

教师说明：

基线测试告诉我们修改前项目处于什么状态。计划告诉我们 Agent 准备做什么。diff 告诉我们 Agent 实际做了什么。测试告诉我们修改后是否满足最低验证要求。四者缺一不可。

过渡语：下面我们进入 Lab 01 的示例项目。

## 25-40 分钟：示例项目与初始测试

本次实验使用课程仓库中的示例项目：

```text
ai-course-system/course-b-agentic-development/examples/repo-01-small-bugfix/
```

这是一个小型 Python 成绩统计函数库。它包含业务代码和测试代码。我们先不急着让 Agent 修改，而是先看项目结构。

教师演示说明：

请打开示例项目，展示以下文件：

- `src/grade_utils.py`：业务函数。
- `tests/test_grade_utils.py`：单元测试。
- `README.md`：项目说明。
- `teacher-guide.md` 和 `solution-notes.md`：教师或助教材料，学生实验前不应查看参考答案。

现在我们运行固定测试命令：

```bash
python -m unittest discover -s tests -v
```

教师讲解：

请注意，初始测试失败不是坏事。这个项目就是为实验设计的，失败日志是我们给 Agent 的重要上下文。我们要记录失败测试名、错误类型和期望行为。

课堂提问：

- 哪些测试失败？
- 失败指向的是业务代码还是测试代码？
- 此时是否应该修改测试？

教师总结：

本实验中，测试是验收标准的一部分。除非课程明确要求，否则不允许修改测试来让结果通过。我们要修业务代码，而不是让测试失去意义。

过渡语：现在我们准备给 Claude Code 输入任务。

## 40-60 分钟：给 Claude Code 输入 Task Packet

我们不能只写“请修复这个项目”。Lab 01 的 Task Packet 应包含目标、上下文、允许范围、禁止范围、测试命令、工作流程和 Human Gate。

教师可朗读或展示以下任务描述：

```text
这是课程 B Lab 01：Claude Code Bugfix 的实验项目。

项目背景：
- 这是一个小型 Python 成绩统计函数库。
- 当前测试失败是课程故意保留的业务逻辑 bug。

当前测试命令：
python -m unittest discover -s tests -v

当前失败现象：
- average_score([]) 触发 ZeroDivisionError。
- pass_rate([59, 60, 80]) 没有把 60 分计入及格。

允许修改范围：
- src/grade_utils.py

禁止修改范围：
- tests/
- README.md
- teacher-guide.md
- solution-notes.md

工作流程：
1. 先输出失败原因、修改计划和拟修改文件。
2. 等待我确认。
3. 再小步修改代码。
4. 再运行固定测试命令。
5. 最后输出 diff 摘要、测试结果和风险。

Human Gate：
如果需要修改测试、删除文件、新增依赖、访问外部服务或大规模重构，必须先停止并请求确认。
```

教师说明：

这段话的作用不是让 Prompt 看起来复杂，而是给 Agent 一个明确边界。我们之后可以根据它的计划判断是否放行。

现在请大家观察 Claude Code 的计划。不要急着让它修改。

课堂提问：

- 它是否理解了两个失败点？
- 它计划修改哪些文件？
- 它有没有提到运行测试？
- 它是否要求修改测试或参考答案？

如果 Claude Code 的计划不合理，教师应示范如何拒绝：

```text
这个计划超出了允许范围。请不要修改 tests/，重新给出只修改 src/grade_utils.py 的最小修复计划。
```

过渡语：当计划合理后，我们才允许它小步修改。

## 60-80 分钟：小步修改与 diff 审查

现在假设我们已经允许 Claude Code 修改。修改完成后，不要只读它的总结。我们必须看 Git diff。

教师演示命令：

```bash
git diff
```

教师讲解：

diff 是 Agent 实际行为的证据。Agent 可能总结得很好，但真正重要的是它改了哪些文件、哪些行、哪些逻辑。

看 diff 时至少检查五件事：

第一，修改文件是否在允许范围内。Lab 01 只允许修改 `src/grade_utils.py`。

第二，是否修改了 `tests/`。如果修改了测试，即使测试通过，也不能直接接受。

第三，修改是否对应失败现象。空列表平均值和 60 分及格边界应当能在 diff 中对应到逻辑变化。

第四，是否引入无关重构。比如重命名大量函数、改变公共 API、增加外部依赖，都不应出现在这个小任务中。

第五，代码是否可解释。学生必须能用自己的话说明为什么这样改，而不是只说“Claude Code 说可以”。

课堂活动：

请学生两人一组阅读示例 diff，回答：

- 改了哪个函数？
- 这个修改解决哪个失败测试？
- 有没有超出允许范围？
- 你会接受这个修改吗？为什么？

过渡语：diff 合理之后，还要运行测试。

## 80-95 分钟：运行测试与记录结果

请再次运行固定测试命令：

```bash
python -m unittest discover -s tests -v
```

教师说明：

测试通过时，请保存输出。测试失败时，也请保存输出。失败日志不是丢脸的内容，而是下一轮分析的输入。

如果测试失败，我们不说“差不多完成”。我们要把失败日志交回给 Agent，要求它基于新的证据分析，而不是让它猜。

可以使用下面的追问：

```text
测试仍然失败。请基于以下失败日志重新分析原因。
不要修改 tests/。
请先给出下一步计划，等待确认。
```

课堂提问：

- 如果 Claude Code 没有实际运行测试，却说“应该通过”，你应如何记录？
- 如果测试通过但 diff 修改了测试，你能接受吗？
- 如果测试失败但 Agent 说完成，你应如何处理？

教师总结：

我们接受修改的条件不是“工具说完成”，而是“diff 在范围内，测试证据真实，学生能解释修改，风险被记录”。

## 95-115 分钟：学生实操 Lab 01

接下来请大家开始自己的 Lab 01 操作。课堂内至少完成以下步骤：

1. 进入示例项目。
2. 运行初始测试并保存失败日志。
3. 写出或复制并修订 Task Packet。
4. 让 Claude Code 输出计划。
5. 记录计划并判断是否允许修改。
6. 如果时间允许，完成修改、diff 审查和测试。

教师巡视提示：

我会重点看你们有没有先运行测试，有没有禁止修改测试，有没有保存 Claude Code 的计划，有没有查看 diff。不要只追求最后测试通过。

如果你的 Claude Code 不可用，请不要伪造。你需要记录不可用原因，然后手动完成同一任务，保留 diff 和测试，并补写如果工具可用你会如何下任务。

## 115-120 分钟：总结与作业

今天我们完成了第一个 Coding Agent 实验的核心流程。

请大家记住：Claude Code 的价值不是“替你写完代码”，而是作为受控协作者参与工程任务。你必须给它上下文和边界，必须看它的计划，必须审查它的 diff，必须运行测试，必须做人工判断。

课后请提交：

- `lab-01-report.md`。
- 初始失败测试日志。
- Claude Code 计划和关键输出摘要。
- Git diff 或 PR 链接。
- 修复后测试日志。
- 复盘，说明 Agent 做对了什么、做错了什么、你如何判断是否接受。
