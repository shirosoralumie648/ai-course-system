# 第 9 周教师讲稿：自定义 MCP Server

## 0-10 分钟：从使用 MCP 到设计 MCP

各位同学，上周我们学习了 MCP 的基本概念：tools、resources、prompts，以及工具调用的安全边界。今天我们进一步讨论如何设计一个课程专用 MCP Server。

请注意，本课程当前不要求大家实现生产级 MCP Server。我们的重点是接口设计：每个工具解决什么问题，输入是什么，输出是什么，有什么风险，哪些地方需要人工审批。

课堂提问：

- 为什么课程 MCP Server 不应该提供任意 shell 执行能力？
- 一个工具接口如果没有输入输出说明，会带来什么问题？
- 设计 MCP Server 时，为什么要先写安全边界？

教师总结：

自定义 MCP Server 不是“把所有能力都开放给 Agent”。它应该是把有限、清楚、可审计的课程能力交给 Agent。

## 10-25 分钟：课程 MCP Server 的目标

课程 MCP Server 的目标可以概括为三点。

第一，帮助 Agent 获取课程资料。例如某个 Lab 的要求、Rubric、模板和示例路径。

第二，帮助 Agent 做受限检查。例如检查学生项目是否包含必要文件，或者运行教师指定的测试命令。

第三，帮助教师和助教生成结构化反馈草稿。例如根据 Rubric 和 diff 生成 Review 报告。

教师说明：

这些目标都与教学流程有关。我们不需要一个能做任何事情的 Agent 工具箱。我们需要的是围绕课程任务的安全工具。

课堂提问：

- 哪些课程任务适合做成 MCP tool？
- 哪些内容更适合做 resource，而不是 tool？
- 哪些反馈只能作为草稿，不能自动成为最终评分？

## 25-45 分钟：核心接口设计

我们可以设计五个核心工具。

第一，`search_course_docs(query)`。用途是搜索课程文档。输入是查询词，输出是文档路径和摘要。风险是搜索结果可能不完整，因此必须返回来源路径。

第二，`get_assignment_requirement(assignment_id)`。用途是获取实验要求。输入是实验编号，例如 `lab-01`。输出是目标、步骤、提交物和评分要点。

第三，`check_project_structure(path)`。用途是检查学生项目结构。输入是项目路径，输出是缺失文件、存在文件和建议。风险是不能读取密钥文件。

第四，`run_course_tests(project_id, test_profile)`。用途是运行课程允许的测试命令。输入是项目 ID 和测试配置，输出是命令、退出码、摘要和日志路径。风险是不能执行任意 shell。

第五，`generate_review_report(diff, rubric_id, test_evidence)`。用途是生成 Review 草稿。输入是 diff、Rubric 和测试证据，输出是结构化 Review。风险是不得编造测试结果。

教师强调：

每个工具都要写清输入、输出、权限和失败情况。没有失败设计的工具，不能进入工程流程。

## 45-65 分钟：输入输出规范

设计工具时，请避免模糊输入。例如：

```text
run_tests(command)
```

这个接口很危险，因为它可能执行任意命令。更好的设计是：

```text
run_course_tests(project_id, test_profile)
```

其中 `test_profile` 只能从教师预设列表选择，例如 `python-unittest-basic`。

输出也要结构化。不要只返回“测试通过”。更好的输出包括：

- 实际命令。
- 退出码。
- 通过和失败数量。
- 关键失败摘要。
- 日志路径。
- 是否存在未验证项。

课堂提问：

- 为什么输出“pass”不够？
- 如果工具无法运行测试，应该返回什么？
- 工具输出中为什么要包含日志路径？

## 65-85 分钟：信任边界与安全策略

课程 MCP Server 至少有三类输入来源：

- 课程仓库内的教师材料。
- 学生提交的项目和报告。
- 外部文档或工具输出。

这些来源的可信度不同。教师材料相对可信，但也可能过期；学生提交内容不能默认可信；外部文档可能包含 prompt injection 或版本不一致。

安全策略包括：

- 默认只读课程资料。
- 对学生项目采用路径白名单。
- 禁止读取 `.env`、密钥、凭证和隐私数据。
- 运行测试时只允许预设命令。
- Review 报告必须区分事实、推测和证据不足。
- 任何评分或合并决策必须 Human Gate。

教师说明：

MCP Server 设计中最危险的错误是“为了方便，把权限放开”。课程项目宁可功能少，也要边界清楚。

## 85-105 分钟：课堂任务：设计一个 MCP 工具

请大家选择一个工具，写出完整设计。格式如下：

```markdown
## 工具名称

## 使用场景

## 输入

## 输出

## 权限边界

## 失败情况

## 安全风险

## Human Gate

## 示例调用
```

可以选择：

- `search_course_docs`
- `get_assignment_requirement`
- `check_project_structure`
- `run_course_tests`
- `generate_review_report`

教师巡视重点：

- 输入是否具体。
- 输出是否结构化。
- 是否限制 shell、路径和网络。
- 是否说明失败情况。
- 是否明确 Human Gate。

## 105-115 分钟：设计评审

请 1-2 位同学展示工具设计。全班从以下角度评审：

- 这个工具是否有明确目的？
- 输入是否过宽？
- 输出是否可审计？
- 是否可能泄漏密钥或隐私？
- 是否可能让 Agent 绕过测试或评分？
- 哪些决策必须由人做？

教师总结：

好的 MCP 工具应该小而清楚。它不追求万能，而追求边界可解释、输出可验证。

## 115-120 分钟：总结与作业

今天我们完成了自定义 MCP Server 的设计训练。请记住，MCP Server 设计的核心不是“能调用多少工具”，而是“每个工具是否有明确边界和可审计输出”。

课后请提交一个最小 MCP Server 设计草案，至少包含 3 个 tools 或 resources，并说明输入输出、安全风险和 Human Gate。

下周我们会进入 Subagents 与 Agent Team，讨论多个 Agent 如何分工，以及如何避免责任不清。
